## 摘要

构建一个以科研项目、材料和持续工作为中心的主应用：用户既能自己编辑，也能与助手协作，还能委托有边界的长期工作。系统提供统一研究助手入口，按需调用多个执行器和专业角色；研究结论能够追溯到具体材料版本、读取范围、规则依据和检查记录。

本版采用的总体架构是：**Oleafly 作为唯一主应用与执行调度底座，research-file-workbench 保留科研文件与证据领域核心，按实测缺口吸收 Super-agent 的持续委托、事件归属与可靠恢复机制。** 不直接并排运行三套产品，不再添加第二个拥有相同任务控制权的总控。

优先复用 Oleafly 的编辑、编译、供应商、ACP、任务存储、调度、隔离、审阅应用和后台宿主；复用现有工作台的保留源件、基线、读取回执、期刊世界、检查与失效机制。新增代码集中在项目关联、受限工具接入、研究策略、证据展示和可追溯接力。记忆是可重建的检索辅助，不是第二套事实库。

首个交付切片是“一个执行器、一个受控项目、真实工具调用、版本绑定结果”。先证明这一切片在权限拒绝、输入变化、取消和重启下仍可解释，再扩展受控文本改稿、多执行器接力和持续委托。

### 2.2 Oleafly：完整底座而非编辑器外壳

Oleafly 使用 Tauri、Rust 与 React/TypeScript；协作核心是 Loro。已存在供应商 runtime、ACP、任务数据库与调度、执行隔离、审批、预算、审阅应用、CLI 和后台 daemon。Research Tasks 仍需按其实验性开关和具体执行器验证，不能由“官方欢迎页能打开”推导集成已完成。[O1][O2]

| 能力 | 复用范围 | 不作出的承诺 |
| --- | --- | --- |
| 编辑与文档工程 | 现有项目、语言服务、编译器选择、预览、历史及共享文档 | 不把 DOCX 转换视为原生保真编辑 |
| 模型与执行端 | 供应商 API、ACP 客户端、已有 CLI 适配及密钥管理 | 不保证所有端的恢复、费用、取消和工具能力一致 |
| 研究任务 | brief、TaskStore、scheduler、generation、审批、运行与恢复路径 | 不把任务完成当科学验收 |
| apply 与隔离 | 工作树或 staged 副本、磁盘/共享文档路由、journal 和恢复 | 不把副本目录视为 OS 权限边界，不把故障回滚等同任意撤销 |
| 文献检索与引用 | 既有 Zotero 和 arXiv、Semantic Scholar、Crossref、PubMed、OpenAlex 路径 | 不另建同一检索管线；服务配额需按接入时政策配置 |
| 用量与预算 | 用量/费用记录、价格估算、已知费用与时间预算处理 | 不承诺未知计费时美元硬封顶，也不把所有等待算入绝对截止时间 |
| 轻量诊断 | 保留上游 evidence 检查作为任务辅助，单列检查范围与失败原因 | Bibliography 存在解析/读取失败退为空集合后标 Pass 的静态路径；不能把其绿色状态升级为核验通过 |

**O9：Bibliography 空结果与假通过路径。** 在本次固定提交中，`evidence/bib.rs::new_entries` 对修改后 `.bib` 的解析失败返回空集合；空输入经 `verify_entries` 仍返回空检查项；`evidence/mod.rs::check` 将空检查项标为 `EvidenceStatus::Pass`。若没有其他新增条目产生警告，解析失败因此可能显示为 Bibliography 的 Pass。另有 `read_text` 无法读取/超出大小限制后被跳过，以及 bibliography 后台任务 JoinError 退为空集合的路径。[O9]

这是**已核对的局部源码控制流，尚未故障注入复现**，不表示整个任务或全部 evidence 检查必然通过，也不表示所有空结果都错误。网络查验失败/超时在 `bib::verify_entries` 中会产生 `bib.lookupFailed`，不能将该行为混写成同一静默成功路径。

融合侧必须区分“本来没有适用条目”“适用条目已完成检查”与“解析/读取/执行失败而没有结果”。在上游返回值不足以区分时，保留原始诊断状态并明确标注范围未证实，不能从空集合推断完成覆盖。若将该诊断用于自动验收，先在原检查链修复错误传播并完成 A-18；不在领域核心再写一套 Bibliography 检查器。

### 2.3 Super-agent：机制参考而非即插即用的第二底座

公开代码自述为研究原型，其运行装配依赖 DeepSeek Harness。值得吸收的是 Mandate、Ticket、Assignment 的分离，以及输入归属、持久化 Effects、Outbox、执行恢复和需要人介入时才通知的设计。它并非只有 Router 提示词，也不是可以不做适配就替代所有 ACP/CLI 的通用库。[S1][S2]

采用原则：先验证 Oleafly 是否已有等价能力，再移植缺口对应的机制。保留一个任务执行权威，不运行第二套独立领取、重试、取消和完成同一任务的 Executor。其现有高权限运行模式、提示词级范围约束和可变运营记录，不直接继承为我们的原稿保护、操作批准或不可变科研证据机制。

### 2.4 研究核心：保留已有实现而不是重建证据库

现有核心已支持源字节保留、项目与不可变基线、对象读取回执、保留页面证据、期刊世界版本、显式绑定、声明几何检查、处置历史与依赖失效。初始摸排基线中的 MCP `workbench-mcp-0.3.0` 已注册 18 个读写工具，复用 `WorkbenchService`；当前实现保持默认 18 个工具，并新增 `--read-only` 的 11 工具只读入口。[W1][W2]

它的限制同样是设计输入：单个项目仍以一个 DOCX 源件为主；完整 DOCX 布局语义、通用多源科研项目、TaskPacket/完整接力治理、受控 DOCX 改稿和独立人工 S1 验收尚未全部交付。已有 80 条对象标注与 80 条页映射是 Agent 辅助记录，不能称为空，也不能称独立人工验收；Mac WPS 历史渲染链存在，但不清除旧 Windows Phase 0 的失败。[W4]

## 3. 产品形态与使用流程

### 3.1 一个主入口，三种工作方式

| 工作方式 | 用户体验 | 系统行为 |
| --- | --- | --- |
| 直接工作 | 自己编辑、查看材料、选择规则和结果 | Oleafly 提供文档工程；证据面板显示当前关联与历史 |
| 助手协作 | 问一段材料、解释一项检查、请求候选修改 | 仅把实际读到的范围、源件版本和工具结果交给模型 |
| 有界委托 | 交办综述、核查、实验或持续跟踪目标 | 策略层明确范围，执行层运行；结果、待决问题和未完成项可追溯 |

“一个主大脑”是统一的交互、目标与任务归属，不要求一条永不结束的模型会话，也不要求八个角色常驻。用户可从任务、材料或证据入口切换工作，执行器的变化不能抹掉版本依据和未解决问题。

### 3.2 主应用中的信息布局

复用现有编辑、对话、Research 和设置入口。领域扩展优先增加“材料与证据”“期刊与规则”“历史与接力”视图，而不是另造任务面板、费用面板或供应商配置。

结果卡应同时显示：执行状态、材料/规则版本、实际读取范围与覆盖缺口、检查裁决、当前适用性、待作者处理事项。一次运行可以结束，但结果仍可能缺证据、已过期或尚未获准应用。

### 3.3 首批工作流

1. **读取与解释**：选择已导入项目，读取指定对象或已有页映射，回答问题并给出精确回执；没有读到的内容不算已读。
2. **期刊核查**：使用显式绑定的世界版本运行支持范围内检查，分别展示依据、裁决、缺口和处置；新指南只提示更新，不偷偷替换绑定。
3. **受控文本改稿**：针对 Oleafly 原生文本项目在隔离副本产生候选，经现有 review/apply 协调应用；DOCX 路线另受专用合同约束。
4. **持续跟踪**：在用户明确授权后，按目标和事件产生候选工作，去重、受预算约束，并只在结果有用或需要用户行动时通知。

上述第 3、4 项是后续交付，不作为首个受限工具切片的前置规模。文献侦察、实验与汇报是产品演进场景，不以角色名存在冒充自动化已可用。

## 4. 核心架构决策

| 决策编号 | 本版采用的决策 | 原因与退出条件 |
| --- | --- | --- |
| D-01 | Oleafly 为唯一主应用 | 复用完整文档与 Agent 底座，不维护两套并列桌面产品 |
| D-02 | 每项执行只有一个调度所有者，初期为 Oleafly | 启动、取消、重试、并发、恢复和状态由同一路径负责；若评估替换，须明确迁移及关闭旧路径 |
| D-03 | 保留现有 Python 领域核心与数据合同 | 不因 UI 换壳重写源件、版本、规则和检查；扩展前先证明现有接口不足 |
| D-04 | Super-agent 初期为机制参考 | 按持续授权、事件归属和恢复缺口吸收，不整包启动第二控制面 |
| D-05 | 记忆为派生索引，证据引用现有核心记录 | 不新建通用 EvidenceRecord/RuleVersion 真源；失效由实际依赖派生 |
| D-06 | 原生文本修改经 Oleafly review/apply | 保留共享文档、基线、generation 与恢复语义，不用裸文件覆盖取代 |
| D-07 | 首阶段即落实受限工具与计费准入 | 模型提示、工具说明和置信度不构成操作权限 |
| D-08 | 恢复先辨别动作是否已发生 | 不以本地幂等键、总费用或同名提交代替外部完成证明 |
| D-09 | API、ACP、CLI 按能力准入 | 不承诺透明跨执行器恢复；不支持的能力显式拒绝或经用户选择降级 |
| D-10 | 先验证最小工作流，再加组件 | “上游已有”不是永久禁止替换的理由；替换必须证明收益大于维护与迁移成本 |
| D-11 | 产品运行状态、科研裁决与作者确认分开 | ready/completed、诊断通过、证据适用和作者批准互不代替 |
| D-12 | 自用范围优先，不假设商业分发 | 保留上游许可与署名；以后分发或为第三方托管时重新评估范围 |

这些是正式整合版的架构选择。预算数值、具体执行器、允许外发的材料、后台常驻与无人值守写入仍是第 16 节的运行决策，不从本表推导已获授权。

## 5. 系统分层与进程边界

### 5.1 目标结构

```text
Oleafly 主应用
  ├─ 编辑 / 编译 / 预览 / 对话 / Research / 设置
  ├─ 研究策略与关联适配层（按需新增）
  │    ├─ 目标、持续委托、事件归属、角色选择
  │    └─ 项目关联、证据引用、接力与结果投影
  ├─ 唯一执行调度：ResearchTask + TaskStore + scheduler
  │    └─ API / ACP / 经能力验证的 CLI 路径
  ├─ 既有 isolation / sandbox / review / apply
  └─ 受限科研工具适配
         └─ research-file-workbench / WorkbenchService
              ├─ projects：保留源件、基线、读取与页面证据
              ├─ journals：世界、绑定、检查与处置
              └─ 当前性、覆盖缺口与失效派生

可选记忆与检索 → 引用领域记录，不写第二份事实
后台运行       → 复用 App / Daemon 所有权交接，按授权启用
外部事件       → 可信来源分类、去重、范围准入 → 策略层
```

### 5.2 责任分配

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Oleafly UI 与宿主 | 项目交互、窗口、进程生命周期、结果投影 | 前端计算第二套 evidence validity，或直接修改领域数据库 |
| 研究策略层 | 选择做什么、何时建议做、使用哪个角色和证据 | 自建第二套启动/取消/重试队列；复制当前任务状态 |
| Oleafly 执行层 | 运行所有权、代次、并发、审批、取消、持久化与已有恢复 | 裁定科研事实、替作者批准稿件或规则 |
| 领域核心 | 保留字节与记录、业务校验、基线/世界/绑定、检查与读取回执 | 创建通用 Agent 编排平台、管理所有供应商 |
| 关联适配层 | 关联 ID、准入上下文、将现有响应投影到主应用 | 写第二份 world/check；绕过核心提交边界 |
| 记忆索引 | 摘要、检索、排序、来源召回与失效提示 | 用最新摘要覆盖源件、裁决或历史确认 |

### 5.3 初期运行与通信

保留 Python 核心进程，通过现有 stdio MCP 候选接入；必要的限制能力必须在服务或可信操作边界实施。开发期间使用仓库虚拟环境，交付时再选择受管理的 sidecar 包装。不要为第一切片先合并 Rust/Python 数据库或重写 Python 核心。

领域服务由受控生命周期启动并绑定指定应用库；启动要核对服务身份、合同与方法版本。若以后使用 HTTP，沿用捕获字节、动态本机地址和会话边界，不把“localhost”视为对同权限 Agent 的自动隔离。不得改为接收任意作者文件路径并写回。

Oleafly 已有后台宿主、任务所有权和交接机制；不能从架构文档没写 Source/Trigger 推断它没有任何常驻循环。真正需评估的是特定外部事件的持续摄取、语义归属、重复输入处理与授权范围。纯事件适配器不会必然造成双调度，只有它同时领取和控制同一执行时才发生所有权冲突。[O2][O8]

## 6. 数据权威与证据合同

### 6.1 每类事实一个权威，不是所有事实一张表

| 事实 | 当前或目标权威 | 关联方式 |
| --- | --- | --- |
| 编辑中的原生文本项目 | Oleafly 项目/共享文档及变更机制 | Oleafly project ID、当前变更代次和实际内容版本 |
| 一次 Agent 执行 | Oleafly TaskStore | task ID、execution generation、执行器与运行记录 |
| 保留的 DOCX 源件与基线 | 现有 ProjectStore | project_id、baseline_id、source_sha256 等真实返回字段 |
| 读取行为 | 保留读取记录和精确响应 | read_record_id、task_id、回执、请求选择与实际交付范围 |
| 世界、规则及项目绑定 | 现有 journal 存储 | world_version_id、binding_id、baseline_id |
| 检查原始裁决 | 现有不可变检查记录 | check_id、世界/绑定/基线与方法依赖 |
| 当前适用性与更新提示 | 领域服务从当前依赖派生 | 不将前端缓存或记忆标签持久化为第二真源 |
| 作者处置与确认 | 现有处置记录；后续专用批准合同 | 明确主体、对象与版本，不从模型摘要推断 |
| 记忆和搜索排名 | 可重建索引 | 引用实际保留记录；每次使用时解释当前范围 |

Oleafly project 与工作台 project 的关联是待实现的小型映射，不是假定两个 ID 相同。映射改变必须显式处理；原始记录不随前端项目重命名而搬家或覆盖。两侧的 task_id 也不假定同义：工作台保存读取任务与回执，Oleafly 拥有 Agent 执行生命周期；关联它们不等于新增第二调度器。

### 6.2 不新增通用证据真源

原设计稿中“可直接建表”的 EvidenceRecord、VersionPointer、RuleVersion、CheckReceipt 不作为实施 schema。现有核心已经保存对应事实，新层只保存必要的关联与派生索引。具体字段以 [MCP 合同](../contracts/s1/mcp-surface.json)、[World 合同](../contracts/journals/world-contract.json)和服务响应为准。[W1][W2]

一次结果至少应能沿引用恢复：所属项目与基线、保留源件、规则世界与绑定（若涉及检查）、实际读取或检查记录、生成记录的方法版本和覆盖范围。页级证据还依赖 render bundle、PDF/页面身份及映射方法，不能只留下源文件哈希。

内容哈希标识字节，不替代版本、绑定和方法身份。相同字节的新 baseline 对某些源观察仍可适用，但不会自动继承所有 render bundle 的精确基线绑定。不得以一条“新版本使全部旧证据失效”或“哈希相同全部沿用”替代逐类依赖规则。

### 6.3 分开呈现四个判断维度

| 维度 | 语义 | 规则 |
| --- | --- | --- |
| 规则依据 basis | 明确要求、候选观察、冲突或其他现有合同含义 | 模板候选不自动成为正式要求 |
| 原始裁决 verdict | 当前 checker 包括 compliant、violation、observed_match、observed_difference、cannot_determine、not_checked | 保留原枚举，不压扁成 pass/fail 后丢失依据差别 |
| 当前适用性 validity | 记录对当前基线、绑定与方法是否仍适用 | 从依赖派生，不写入旧检查以制造新事实 |
| 处置 disposition | 操作者的说明、延期等后续处理 | 不覆盖原裁决，也不等于规则修订 |

新检查只能引用保留的 world，不能另存一份 world 真源；服务已有校验会拒绝在新检查中持久化派生的 validity、updates 或 dispositions。前端、TaskStore 与记忆系统同样不应复制这些业务事实。[W2]

### 6.4 版本变化与运行范围

| 变化 | 允许的行为 | 不允许的推断 |
| --- | --- | --- |
| 新稿 B2 成为当前基线 | 保留 B1 记录；按现有绑定规则处理新检查与失效 | B1 的通过自动适用于 B2 |
| W2 导入但项目仍绑 W1 | 继续保留 W1 的依据与裁决，提示 update_available | 自动重绑、重判或将旧裁决改为错误 |
| 显式绑定 W2 | 新执行按新绑定，旧记录的当前适用性按依赖变化派生 | 重写旧检查的世界或原 verdict |
| 方法版本改变 | 新执行使用当前方法；历史响应原样恢复 | 为恢复旧响应重新运行已废弃算法 |
| 同字节新 baseline | 按各对象的依赖规则判断 | 仅靠 hash 继承全部页面或绑定证据 |
| 任务启动后范围变化 | 核对实际响应依赖；不将新范围结果归为旧任务范围 | 一次调用前后读取状态即可获得原子固定范围保证 |

`run_check(project_id)` 当前不接受 expected baseline/world 参数。首切片要核对真实返回的依赖并解释范围变化；如需“只允许检查任务启动时 B1/W1”，必须扩展业务提交边界，实现原子的 expected-dependency 校验并版本化合同，而不是仅在 Agent prompt 中写 B1/W1。[W3]

版本必须从实际返回记录读取。下表同时保留初始源码摸排使用的历史基线和当前工作区实现，避免把旧实验的合同身份误读为现行版本。

## 7. 执行器、工具权限与材料外发

### 7.1 先验证能力，再允许任务启动

内建 API、ACP 和独立 CLI 的运行路径不等价。每个首批执行器至少需验证：实际可取得的工具、参数 schema、网络与文件边界、取消传播、费用计量、会话恢复和子任务能力。必要工具不可用时应阻止该类任务，不能以空工具集继续并返回看似成功的报告。

Oleafly 的聊天 MCP 配置不等于研究任务 MCP 配置；任务路径有单独的 server 选择和 bridge。ACP 恢复失败后可能转入新会话，任务 MCP 对子 Agent 能力也有限制。接力或角色切换不能默认继承原会话的权限、计费能力或已读上下文。[O5]

### 7.2 现有 MCP 边界与需要补齐的部分

`rfw-workbench-mcp` 当前是可信本地单操作者入口，启动后注册全部 18 个工具；它没有已实现的任务级工具 allowlist 或项目 ACL。read-only annotations 是能力说明，不是授权检查。库内路径校验也不等于某个任务获得整座库的访问权。[W1]

自主接入必须在可信入口实施工具及对象范围限制，并使执行器不能直接绕过该入口修改领域库或作者目录。仅从模型菜单隐藏工具、不显示数据库路径，均不足以成为不可绕过的边界。首轮用独立测试库；若执行器仍持有任意 shell 与宿主写权限，应将结果标为受信协作验证，不宣称强隔离。

当前 `revise_rule → WorkbenchService.revise` 会记录 `local-operator` 和 `human_decision`。这是现有单操作者合同，不是自主 Agent 的身份认证。初期不向自主执行器开放该操作；后续若开放提案，应将“模型建议”与“人确认形成修订”分为明确、版本化的操作。[W5]

### 7.3 首个切片的权限矩阵

| 工具或动作 | 初期准入 | 必须检查的范围 |
| --- | --- | --- |
| method_versions | 允许 | 服务身份、合同与方法版本 |
| project_detail / manuscript_workspace / project_history | 允许目标项目 | 项目、选定基线和关联的保留材料 |
| read_objects / saved_read | 允许目标项目 | 选择器、已披露内容、read record 与 bundle 归属 |
| check_record / world_review / diff_worlds / source_page | 按关联允许 | 检查、世界、源页必须属于获准上下文 |
| library_state | 独立测试库可用；共享库需真实过滤 | 不能泄露其他项目目录和资料 |
| run_check | 允许指定项目保存内部检查记录 | 实际基线/绑定/世界/方法依赖；不修改原稿 |
| import_world / import_manuscript / update_manuscript / bind_project | 人工预置或逐次明确授权 | 输入身份、预期基线、操作目的与确认 |
| revise_rule / record_disposition | 初期留给操作者 | 模型不可代签人工修订或自行延期问题 |
| 作者决定与 render bundle 登记 | 保留现有操作者通道 | 不把 Agent 输出包装成独立人工证据 |
| 任意 shell、Git push、邮件/IM 外发 | 默认不开放 | 后续单独授权、可观察执行与结果回执 |

允许保存读取回执和检查记录，不代表允许编辑作者源件。“只读原稿”与“绝不写任何内部状态”是不同要求。

### 7.4 参数、代次与取消

当前 MCP SDK 对部分未知参数采用忽略行为，拼错可选选择器可能扩大读取范围；现有合同已声明这一限制。受限入口应依据实际 schema 明确拒绝未知字段，不能静默删除后继续。业务参数与版本语义变化要同步合同和测试，不能在前端补默认值掩盖。[W1]

取消应阻止新的受控操作，并让执行器及其子进程停止或进入明确状态；提交边界要核对任务代次与权限。已提交的读取或检查不得因任务取消而抹除，可保留为历史产物。外部系统已经接受的请求未必可撤回，取消按钮不意味着邮件召回、远端计费回滚或副作用不存在。

### 7.5 数据外发与不可信内容

本地 MCP 并不代表推理本地完成；返回片段可能进入所选供应商的模型请求。任务需显示执行器、允许发送的材料类别和范围。切换模型或 CLI 时重新核对该范围，不自动继承“可以发送全文”的权限。

论文、指南、邮件、网页、工具输出和检索摘要都是数据，不是系统指令或用户授权。外部事件的 actor、来源与授权依据要由接入边界确认，不能因文本写着“请执行”就变成用户命令。日志和观测默认不记录密钥或完整稿件；诊断采集应可脱敏、可关闭。

## 8. 预算、取消与运行观测

### 8.1 准确描述已有预算

Oleafly 的 TaskBudget 有时间、美元上限、运行次数和单次运行超时字段；已有预算执行与用量记录，不是只有价格元数据。但这些能力不等于跨所有执行器的 token、工具次数、美元和绝对时间硬封顶。[O3][O4]

| 项目 | 固定源码中的行为 | 融合产品需要说明或补齐 |
| --- | --- | --- |
| 时间累计 | BudgetClock 累计活动时间，支持 pause/resume | UI 区分活动耗时、等待时间与真实经过时间 |
| 时间耗尽 | scheduler 进入停止处理，允许收尾；硬停止阈值另算 | 不写“到点立即停止”；验收收尾及强制停止的实际路径 |
| 费用上限 | 可取得费用且达到 usd_cap 时触发取消 | 已发生费用与调用中费用可能滞后；不是调用前绝对封顶 |
| 未知费用 | spend 为 None 时不触发金额上限 | 显示未知，并按 8.2 的准入策略处理 |
| 次数 | max_runs 限制运行，不等同所有模型或工具调用 | 若需要 step/tool 次数上限，单独定义并验证实现 |
| 费用观测 | 已有 usage history、估算与聚合 | 先验证执行器计量覆盖，避免父/子调用重复记账 |

本次源码的费用探测缓存间隔为 30 秒，预算模块定义 5 分钟/20 步收尾参数与 7 分钟硬停止参数；scheduler 在发现时间耗尽后设置后续硬停止期限。这些数字是固定版本实现线索，不是本文建议的全局默认值，也不证明每个执行器已按同样方式停止。若要求绝对截止时间，应新增明确合同而不是改名解释现有活动时间。[O3]

### 8.2 未知计费的默认处置

正式接入的默认策略是：**不能可靠计费时暂停新的付费调用，等待用户选择。** 用户可以明确选择使用已知计量的执行器，或接受“费用未知但调用次数/活动时间受限”的有限运行。后者不得显示为金额硬封顶。运行中丢失计量能力也应进入同一可见状态，而不是继续假定费用为零。

“降级只读”不是费用保护：即使不写文件，模型推理、检索或嵌入仍可能产生费用。文件权限与付费调用准入必须分别控制。未知价格或 token 不完整时，不能把“单价乘 token”称为已知上界；即便可估算，也要显示估算、已结算和未知部分。

如未来确需更强的金额约束，应在调用前核对可信价格及请求上限、预留预算，并汇总并发调用和子任务的在途占用。若执行器不支持可约束的请求上限或准确归集，就不能承诺硬封顶。该能力需单独实现和验证，不在本版假设已存在。

### 8.3 阶段 1 的最低运行限制

在首次模型调用之前，确定执行器、材料范围、网络/写入权限、时间策略、取消路径及未知计费策略；需要的调用上限未实现时，不以配置字段存在作为已生效证据。首切片串行运行，避免同时引入并发预算仲裁。

本版不固定每任务 200k token、每天 3 个任务或 120 秒心跳等缺少实测依据的数值。心跳表示进程或任务活性，不直接等价于模型有进展；长编译、审批等待和不可中断外部调用要分别标识。重试仅限已识别瞬时错误，记录上限、退避与最终失败；未知副作用遵循第 10 节。

### 8.4 复用观测，按缺口扩展

先复用 Oleafly 的任务事件、用量/费用记录、CLI/daemon 日志和现有 UI。LLM trace、跨进程链路、领域工具耗时与隐私过滤是否不足，应由首切片实际排障证明。Langfuse、Phoenix 或 OpenTelemetry 仅在出现明确缺口时评估；不宣称 Oleafly 没有任何成本追踪，也不默认部署第三套服务。

最低可观察信息包括：任务与代次、执行器、工具准入结果、使用的基线/世界、调用及拒绝、计量状态、取消原因、回执引用和未解决项。日志不能替代不可变领域记录，观测组件也不拥有预算审批权。

## 9. 文档修改、审阅与应用

### 9.1 区分作者输入与编辑项目

工作台的作者原稿目录继续作为只读输入，源件捕获为保留字节。第一阶段不改稿。后续原生文本编辑针对明确选定的 Oleafly 项目或应用拥有的副本，按用户批准进入既有 apply 路径；不得因为选用了 Oleafly 就取消原核心的作者输入保护。

DOCX 的受控改稿需要专门的文本/对象定位、批准绑定、修改后检查与渲染合同。Pandoc/文本转换或 diff 预览不能证明 Word/WPS 语义和版式保真，不能将文本工作流的完成线套用到 DOCX。

### 9.2 复用现有 apply，而不是复刻文件写回

```text
隔离副本中生成候选
  → 记录 changed_files、基线与产物身份
  → 展示候选差异、编译/检查结果及覆盖范围
  → 用户选择
  → Oleafly 变更准入 + apply_review
  → 磁盘校验或共享文档协调
  → 记录实际应用结果；必要时重新编译/检查
```

磁盘路径在提交前核对 before/after 哈希；共享文本经 SharedDocument 的写入与合并逻辑处理。现有源码存在保留较新用户内容并应用候选修改的路径，不能一概写成“用户只要改过正文就全部拒写”。需分别验证非共享文件变更拒绝、共享文本非冲突合并、冲突与建议状态。[O6]

批准应绑定实际审阅的候选及执行代次。若合并后的材料不同于事先编译/检查的候选，旧检查不能冒充合并后检查；应标明变化并按操作合同重新确认或验证。共享合并的用户可见语义必须实测，不以静态分支存在推导所有冲突都安全解决。

### 9.3 故障恢复与普通撤销不是同一能力

现有 apply journal 记录 Preparing、Applying、Sharing、Applied 等阶段，包含备份、恢复校验和回滚路径。多文件写入及共享文档发布不是凭一个 phase 字段就成为跨系统原子事务。恢复按实际日志和内容核对，不能简化成“所有 Applying 都无条件回退”。[O6]

成功应用后的人工撤销应走现有文档历史或定义明确的逆向变更流程，并处理其后的用户编辑。故障回滚不自动提供永久备份或“一键零成本撤销”。本版不自动 `git add`、commit 或 push；这些操作有各自的用户意图、内容范围和回执。

现有 selected_paths 是文件粒度。若以后需要行级接受，候选输出及其哈希必须对应用户实际选中的组合，并重新经过同一审阅/应用链；不得借未审阅的新草稿绕过批准。编译成功只证明相应编译检查，不证明事实未变、引用支持或科研结论正确。

## 10. 持续工作、持久化副作用与恢复

### 10.1 三种身份分离

| 身份 | 含义 | 生命周期 |
| --- | --- | --- |
| 持续委托 | 用户允许系统持续推进的目标、范围与通知规则 | 可跨多个任务；暂停/撤回需明确处理 |
| 业务工作项 | 某个待完成目标及追加输入、阻塞问题与结果 | 可经历多次执行，不随进程重启丢失 |
| 单次执行 | 某个执行器的一次运行与代次 | 由 Oleafly 调度、取消、恢复并记录 |

这一区分借鉴 Super-agent，但不要求首切片立刻增加三套表。当前一项工作对应一个任务即可；当真实持续委托需要跨任务存在时，再增加最小业务身份和任务引用。新层不得直接调度另一组 worker，也不得把其业务状态覆盖 ResearchTask 的运行状态。[S1]

### 10.2 外部动作协议

优先复用已有可靠动作路径，例如 Oleafly apply journal。仅对缺少可靠记录的新增外部动作补齐：稳定动作身份、提交前授权核对、持久化意图、执行、回执和恢复核对。不要把所有纯计算或查询包装成通用消息平台。

目标操作过程如下；它是待实施协议，不是已存在的统一 API：

1. 明确业务动作、授权、目标、内容版本及预期条件；持久化意图，与本地待执行状态按所需事务一起提交。
2. 通过唯一执行所有者领取，核对执行代次、当前权限和范围；向支持的外部接口传稳定幂等键。
3. 执行动作并保存动作级结果：远端 ID/查询键、实际提交哈希或可核对的目标状态。
4. 重启后检查意图与回执；已确认成功则恢复记录，不重复动作；确认未发生且仍获授权才可重试。
5. 结果未知且无法可靠查询时，保持待核对状态，停止自动重发并明确需要什么证据或人工决定。

本地唯一键只能防本地重复排队，不能保证远端恰好执行一次。状态目录锁、Outbox 和接收端去重分别保护不同边界，不能合称已证明端到端 exactly-once。[S2]

### 10.3 动作身份与执行代次

同一业务动作的重试应保留动作身份，不因换了执行进程就生成新幂等键；真实的新动作则必须有新的身份。身份构造要采用明确编码，不能将若干字符串直接拼接后散列而不定义字段和边界。

执行 generation 用于拒绝旧执行继续提交，不等于业务动作身份。新一代恢复原动作时，先查询旧动作结果与当前授权，不能因为代次改变就当作可以再次外发。内容、目标或批准变更意味着动作语义可能改变，应重新确认而不是复用旧成功回执。

### 10.4 动作级核对要求

| 动作 | 可接受的核对依据 | 不足以确认的依据 |
| --- | --- | --- |
| 文件应用 | 既有 apply 计划、目标内容、项目代次与共享文档状态 | 只有路径存在，或只有某个旧副本哈希 |
| 远端邮件/IM/评论 | 服务支持的幂等机制或明确的动作 ID 查询；说明保留期限和查询范围 | 本地已排队；搜索暂时没找到就视为未发送 |
| 收费 API | 请求/响应级 ID、服务支持的状态查询或可核对回执 | 累计 spend 增加；总 token 数；本地没有成功日志 |
| Git commit/push | 明确仓库、分支、提交对象、父提交和内容；远端 ref 状态 | 只用 commit message 或 `git log --grep` 命中 |
| 文献入库 | 应用内条目 ID、来源标识、版本/附件及冲突规则 | 只有 DOI 相同就假定所有版本和附件完全一致 |

不支持幂等或状态查询的 API 可以使用，但必须接受更弱的恢复保证，并在未知结果时停下来核对，不能在文档中为它补上不存在的能力。

### 10.5 取消、重试与故障实验

重试只针对已识别的瞬时故障，明确每层重试上限和最终处理，避免 provider、工具和外层任务同时重试放大动作。人工重试也不能自动清除未知外部结果。

应覆盖以下崩溃窗口：意图落盘前、落盘后未执行、外部成功但本地回执缺失、回执已存但 UI 未更新、旧代次迟到、取消与提交竞争。对已经发生的动作保留历史，不为使状态整齐而删除。Super-agent 的 Effects/Outbox 实现可作为参考，但其真实服务去重和跨故障行为仍需在选定适配器上验证。

### 10.6 输入归属与已投递/已取得的区别

持续任务的新输入要先判断属于已有工作还是新工作，保留稳定事件身份与归属。发送给执行器并不等于它已在模型步骤中取得，更不等于理解或执行完毕。Super-agent 有 delivered/readAt 分离及重启重排机制，这是值得借鉴的具体能力；不能把缺少对应遥测的 ACP/CLI 自动标为已读。[S3]

适配器能够确认模型取得时才记录该事实；只能确认投递时就停留在投递层。恢复对未确认取得的输入使用可去重的再次交付或明确重建上下文，不丢输入、不伪造理解证明。该输入轨迹与工作台的材料读取回执分别记录，再按执行身份关联。

### 10.7 候选工作流框架的 checkpoint 边界

LangGraph 的 checkpointer 可保存线程的图状态快照，不能概括成“只保存 `@task` 返回值”。跨进程重启保留还取决于所选存储后端；内存 checkpointer 不提供重启保留。在 Functional API 中，恢复从 entrypoint 开头重放，已保存的 task/subgraph 结果由 checkpoint 恢复；这不是所有 API 都从同一函数开头执行的通用规则。[E3][E4]

官方文档明确要求将副作用和非确定性操作封装在 task 中，并针对未完成 task 的再次执行使用幂等键或核对既有结果。[E4] 由这一恢复机制可推知：即便使用持久 checkpointer，外部动作成功而结果尚未记录的窗口仍需第 10.2—10.4 节的动作级协议处理；框架持久化不自动保证外部副作用恰好一次。这是基于官方机制的设计判断，不是本机故障注入结果，也不改变 LangGraph 非首阶段依赖的选择。

## 11. 记忆、检索与跨执行器接力

### 11.1 四类上下文的用途

| 类别 | 内容 | 保存原则 |
| --- | --- | --- |
| 工作上下文 | 当前目标、获准工具、选定材料与本轮返回 | 按 token 需要组装；不等同已验证记忆 |
| 会话记录 | 用户交互与工具响应关联 | 复用执行端能力；需要历史精确响应时引用核心记录 |
| 项目记忆 | 研究问题、候选结论、争议、引用、任务进展 | 可检索摘要指向源件/读取/检查，不覆盖原事实 |
| 跨项目偏好 | 用户确认的写作、通知与操作偏好 | 记录范围、确认来源和修改方式；不是科研证据 |

不先选 Mem0 或向量数据库再定义需求。先用现有记录、显式引用和检索路径完成实际工作；只有跨材料召回质量、规模或延迟出现可测缺口时，才评估额外索引。

### 11.2 记忆不是事实裁决

项目摘要应记录类型、所属项目、来源记录引用及适用范围；实验设想或模型推断应明确标记为假设，不能伪造一个 evidence_id 使其看似有依据。纯偏好可以没有科研证据引用，但必须有独立类型和确认范围。

使用记忆时回查对应记录的当前适用性和真实支持范围：源件未过期不代表摘要正确，读取过也不代表结论成立。若只有部分依据仍适用，应显示哪些支持和哪些缺失，而不是靠一个布尔值覆盖所有记录。当前有效性可以按依赖缓存作性能优化，但不可变成独立事实；缓存失效规则须可验证。

冲突不能简单按“人工确认优先，否则取最新”消解。先区分是否同一对象、版本、范围和方法；不同范围可并存，真正矛盾保留各自来源与待决问题。摘要更新不删除历史原文，也不让较新的模型推断覆盖作者决定。

本版将外部记忆项目的可复用机制限定为派生索引边界，不引入完整记忆运行时：

- **D-MEM-01：** 记忆是可重建、带 `source_refs` 的检索辅助，不是第二事实真源。
- **D-MEM-02：** Oleafly 保持唯一主应用和任务调度权威；记忆项目不得拥有另一套任务完成语义。
- **D-MEM-03：** `source bytes`、`baseline`、`read receipt`、`world`、`check`、`validity`、`coverage`、`disposition` 和作者确认不得由记忆系统复制或重命名。
- **D-MEM-04：** 吸收 Mem0/LangMem 的 semantic、episodic、procedural 分类与生命周期，Letta Code 的大小/深度/只读 guard、operation lock、冲突可见化，以及 Graphiti 的 `valid_at`/`invalid_at` 与 episode provenance；不整包引入其 runtime。
- **D-MEM-05：** Qdrant、Graphiti、LlamaIndex、GraphRAG 和 Zep 只有在召回、规模、延迟或时间关系出现可测瓶颈后才做隔离 PoC；没有基线数据不新增依赖或服务。
- **D-MEM-06：** 抽取、embedding、索引或召回不可用必须返回 `memory_unavailable`（或等价显式诊断）；不得静默变成空成功，也不得改变正式证据判断。

记忆条目至少记录作用域（project/task/agent/user）、类型、来源引用、依赖版本、状态（active/stale/expired/retracted/conflict）、历史和召回解释。基线、规则世界或方法变化后旧记忆默认标为 stale；删除和撤回停止新召回但保留可审计历史。记忆索引失败、冲突和过期行为纳入 A-19 验收，不以向量库的 payload filter 代替版本校验。

### 11.3 接力的三种模式

1. **原会话恢复**：执行器证明可以恢复，再核对材料与权限。
2. **新会话携资料继续**：原会话不可恢复，明确重建上下文，保留任务关联和未完成项。
3. **换执行器接力**：重新做能力、材料外发与操作权限准入，记录新的执行关联。

三者不能都显示成“无缝继续”。不迁移不可见推理，也不假定新执行器继承旧执行器对材料的理解。App/Daemon 接管是运行宿主所有权变化，与模型间接力不同。

### 11.4 最小接力包

接力包只需包含或引用：目标及验收条件、当前未完成项、项目/基线/世界/绑定和方法、精确读取与检查记录、覆盖缺口与争议、已完成或未知的副作用、仍有效的授权、执行器与恢复方式。摘要负责导航，原始记录负责追溯。

现有回执的 `client_id=workbench-mcp` 标识服务入口，并不认证具体模型。若产品要回答“哪次执行读了什么”，需要把真实执行身份与核心记录做可验证关联；不能把 client_id 改称 Agent 身份就宣称完成。完整接力记录仍是待实施能力，不重新定义核心读回执来伪装已交付。

## 12. 研究角色与持续委托

### 12.1 角色是能力配置，不是常驻进程清单

| 角色 | 典型交付 | 可判定的完成条件 | 边界 |
| --- | --- | --- | --- |
| 文献侦察 | 来源明确的候选文献与检索记录 | 时间范围、查询、去重和未覆盖来源可复查 | 数量多不等于召回完整；不预设无标注依据的命中率阈值 |
| 精读摘要 | 问题/方法/结果/局限及源片段引用 | 引用可回到实际材料，缺失项明确 | 页码存在或 DOI 正确不证明引文支持结论 |
| 方法与实验设计 | 假设、指标、实验与反证计划 | 可证伪条件、变量和可执行验证步骤明确 | 仍是建议，不冒充已做实验 |
| 代码与复现 | 受控环境中的代码、数据身份、运行和结果记录 | 实际命令、依赖、误差标准及失败可核对 | 环境锁定不保证所有运行可复现；网络与数据权限另控 |
| 写作与润色 | 候选草稿与语义/事实变化提示 | 经选定检查和人工审阅，走既有 apply | 编译成功不证明事实未变；DOCX 单独开放 |
| 引用与格式核查 | 引用与规则问题、覆盖缺口、候选修正 | 依据与裁决区分，修正可审阅 | 现有九类几何检查不等于所有期刊规范 |
| 审稿模拟 | 有依据的风险与问题清单 | 观察、推断、缺失材料分开 | 不以“凑齐五类意见”作为质量或真理标准 |
| 协作与汇报 | 与记录一致的进展、阻塞和下一步 | 指向真实任务/证据，不把进行中写成完成 | 不从聊天摘要补造实验、读稿或作者决定 |

同一个执行器可以承担多个角色，但角色名不授予额外工具。切换角色后是否新建会话、如何隔离上下文，取决于执行器实际能力和任务风险。初期只选完成首切片所需角色，不强制一次实现全部八类。

### 12.2 主动性从显式委托开始

持续委托至少明确：目标、项目范围、允许触发源、可自动采取的动作、费用与资源策略、需人工确认的边界、暂停/撤回方式、通知条件。置信度可以排序候选，不产生授权。

先接一个明确需要的定时或文件变化场景，再扩展邮件、IM 或 GitHub。事件应有稳定来源身份与去重键，辨别新增信息、已有工作追加输入和新工作；自己的写入事件要避免反复触发同一任务。来自文稿或邮件正文的指令不得扩大委托。

当状态未变化、没有可用结果、也不需要人决策时保持安静；发现实质结果、失败、预算或权限阻断、需用户选择时再通知。免打扰、批量摘要与频率由用户使用体验决定，不凭固定置信度阈值宣称可靠。

### 12.3 持续授权不代替动作批准

委托“跟踪课题”不等于获准改正文、修订规则、发邮件或 push。策略变更、权限撤回和任务取消要到达实际提交边界；只给运行中 worker 一条通知不能保证下一次操作拒绝。Super-agent 当前对在途 Mandate 的处理语义可以参考，但不能直接当作我们的即时撤权保证。[S1]

## 13. 组件采用与维护策略

### 13.1 先复用，再证明新增价值

| 领域 | 当前选择 | 引入其他组件的条件 |
| --- | --- | --- |
| 编辑、编译、预览、文献入口 | Oleafly 现有能力 | 可复现的工作流缺口；保留引擎和项目变更语义 |
| 协作 | 保留现有 Loro 路径，不增加 Yjs/Automerge | 明确整体迁移理由与历史兼容方案；单人使用不意味着可盲删共享文档层 |
| 任务调度与持久化 | TaskStore + scheduler + 已有运行路径 | 用真实工作流证明现有机制不足，明确唯一所有者和迁移成本 |
| LangGraph / Microsoft Agent Framework / OpenAI Agents SDK | 仅借鉴 typed state graph、checkpoint、interrupt/resume、handoff、guardrail 和 capability manifest；首阶段不作为运行时依赖 | E5/E6 证明现有 TaskRuntime 无法表达真实窄流程或 provider 能力，且 adapter 不拥有 TaskStore/evidence |
| Temporal / Restate / Inngest / Dapr / Prefect / Dagster | 当前不引入第二 durable workflow 或数据编排权威 | E1/E2 真实复现 Oleafly 无法解释的跨天恢复、外部 effect 或多 worker 缺口，并书面确定唯一 owner 与迁移边界 |
| Super-agent | 固定版本作授权、assignment、handoff、outbox、恢复机制参考 | 局部移植须补接口与测试；整包路线须证明 DSH 宿主和唯一控制权的必要性 |
| 证据存储 | 现有 ProjectStore、journal 存储与 WorkbenchService | 支持新材料或语义时版本化扩展，不另建万能证据表 |
| 记忆与向量检索 | 先用可重建派生 memory schema、现有记录和轻量索引 | 有标注查询集、召回/定位收益、stale/delete/conflict/unavailable 证据及删除重建方案；Qdrant 只做隔离 PoC |
| 模型网关与凭据 | Oleafly provider/ACP 和现有密钥机制 | 必须证明不能由当前供应商适配解决的路由或治理需求 |
| 可观测 | 先用已有任务/usage/log；按需吸收 OTel/OpenInference 语义作为旁路 | 真实排障证明缺口后，在 Langfuse 与 Phoenix 中二选一做脱敏本地 PoC；telemetry 不拥有任务或证据状态 |
| OS 隔离 | 复用 Oleafly 已有沙箱，验证所选执行端实际采用 | Docker 等可在实验依赖环境确有需求时评估；不得自动挂载宿主或暴露 daemon socket |
| 外部检索 | 复用现有来源和缓存路径 | 配额、认证、检索质量及持续增量需求另行验证 |
| 事件、队列与事件库 | 先用 Oleafly/SQLite append-only event、outbox/inbox、dedupe、backoff、replay、consumer checkpoint | E1/E2/E7 证明本地事务无法承担跨服务/多 worker 需求后，再选一个 broker 或事件库；不同时引入 BullMQ/NATS/KurrentDB/Eventuate |

“只要上游有相似功能，引入任何替代组件都负收益”不是本版原则。组件是否适用，要看缺口、接口、运行成本与迁移风险。相反，“现成框架丰富，所以都接上”也不是复用：一份重复的状态和运维面就是新增复杂度。

不使用“自研只占 10%—15%”或“超过 20% 就错误”作为质量指标。集成、迁移、合同和测试也是真实工作；是否该自研取决于产品差异和可维护性，不取决于未经定义的代码占比。

### 13.2 外部政策与候选生命周期

原生 OpenAlex 搜索已存在，不应再列为尚未添加的来源。[O7] 2026-11-03 复核官方文档时，旧限流地址已跳转到新的 Authentication 页面：区分无 key、免费 key/预付费、年度计划的请求速率，并以每日使用预算管理用量；因此“10 req/s、10 万次/日、免 key”不能作为适用于所有调用者的一组现行限制，“免费 key 仅 Premium 可得”也不成立。免费 key 需完成邮箱验证，部分复杂请求另有限速。每日预算耗尽与请求过快均可能返回 429，须结合预算和限流信息区分处理；不能把预算耗尽当作短暂降速即可恢复。[E1]

Crossref 在 2026-07-21 官方公告中明确按单记录/列表请求和 API pool 区分速率，并说明 HTTP 429 表示限流；应读取 `x-rate-limit-limit`、`x-rate-limit-interval` 及 `x-rate-limit-type`，暂停后降低请求速率。公告还说明会按 `mailto` 邮箱聚合限流，多个进程或 IP 共用邮箱不意味着各有独立额度。不保留“429 无官方依据”或“无公布速率”的结论，也不把所有 503 自动归因于限流。无需故意耗尽生产配额来证明官方已说明的 429 语义。[E2]

具体配额不是架构常量。实际接入时记录来源文档、核对日期、认证层级、请求类型、响应头和实际采用配置；分别处理每日预算耗尽、瞬时限流、服务不可用与权限错误。服务重试还须满足第 10 节的副作用条件，不能看到可重试状态码就盲目重发写操作。

本文不沿用未重新核实的“某候选已闭源/停止支持”等排除理由，也不把不同框架一概描述为必须同一数据库或部署形态。候选进入实施前，分别检查当前版本、许可证、维护、部署和数据流；这里保留的是选择方法，不是未经验证的最新生态清单。

### 13.3 Fork 与升级

Oleafly fork 尽量保持小而可定位的领域扩展；上游通用缺陷修复与业务功能分开。每次升级至少重查任务模型/存储、runtime、MCP 工具、apply/共享文档、沙箱和 daemon 所有权。不得为追上上游而重写旧源件、世界、读取响应或检查记录。

维持现有依赖声明和模块边界：可复用 Python 产品逻辑在 `src/`，机器合同在 `contracts/`，测试在 `tests/`，操作脚本在 `tools/`，文档在 `docs/`，验证证据在 `reports/`，可重建临时数据在 `var/`。不把领域逻辑塞进桌面壳，也不以新的工具代理重新实现一份领域规则。

## 14. 分阶段实施与交付

阶段按风险与依赖排序，不预设缺乏工作量依据的周数。每阶段独立可展示，未达到完成线就不以新增角色或组件掩盖基础问题。

### 阶段 0：固定版本与可重现开发环境

- 保留现有改动，检查构建资源；使用隔离的 Oleafly 数据目录和工作台测试库。
- 从固定 revision 完成源码依赖安装、构建和开发启动，核对实际运行版本。
- 核对官方预览、开发分支和领域核心三个身份，不混用用户日常库。
- **完成线**：开发启动与退出可重复，来源版本明确，不影响原库；这尚未由本次调研证明。

### 阶段 1：一个执行器的受限工具与证据闭环

- 人工预置一个测试项目与规则绑定，选择一个执行器，先做真实 MCP 握手、列工具和方法版本核对。
- 完成 E3 的真实 `initialize → list-tools → call` 闭环，记录协商能力、请求 ID、取消/超时和服务重启后的 typed failure；必要工具缺失必须阻止任务。
- 实施第 7 节的工具/对象范围准入，拒绝未知参数，限制人工归因操作；核对执行器不能走旁路。
- 启用明确的时间、取消与未知计费策略；需要的调用上限先实现再承诺。
- 执行读取与支持范围内检查，在 Oleafly 展示实际回执、依赖、缺口与历史。
- 核对轻量诊断的覆盖与失败语义；Bibliography 的空结果/Pass 不作为独立完成证据。显示或使用该诊断前覆盖 A-18 的异常场景。
- **完成线**：声明工具确实可用，拒绝可观察，版本变化不被掩盖，用户无需第二套桌面应用即可回查结果。
- **不做**：自动改稿、持续外部事件、长期向量记忆、多 Agent 并行、新调度框架。

### 阶段 2：变化、失败、取消与接力

- 用受控输入覆盖 B1→B2、W2 未重绑/显式重绑、方法变化、未知参数和失效证据。
- 先完成 E1-E2：在现有 `TaskStore` 上验证 intent/effect/settled 事件、稳定 `event_id`、去重、旧 generation 拒绝、step boundary、backoff 与 blocked/incomplete 语义；不以第二队列替代故障实验。
- 验证缺工具、服务重启、取消竞争、任务恢复及历史响应恢复；必要时实现原子 expected-dependency 边界。
- 完成 E4 的 ACP 能力协商、取消、resume 与 `fresh-with-handoff` 区分；不自动继承旧会话批准、权限或已读状态。
- 在第一个执行器成立后，再接第二个执行器，区分原会话恢复、新会话继续和跨端接力。
- 对本阶段新增的副作用立即补幂等与未知结果处理，不等待持续自治阶段才考虑。
- **完成线**：不丢版本依据、不篡改历史、不把未知结果写成成功，也不以新会话假装旧会话恢复。

### 阶段 3：原生文本的受控改稿

- 对明确的 Oleafly 原生文本项目生成候选，复用 review/apply、共享文档和项目变更准入。
- 分别验证磁盘冲突拒绝、共享非冲突合并、冲突呈现、实际应用后的验证与 journal 恢复。
- 如需行级接受或普通撤销，明确候选组合和逆向变更合同，不绕过已有机制。
- **完成线**：审阅对象、应用对象和验证对象可以关联，不覆盖用户后续修改，不自动提交或推送。
- **DOCX 路线**：在专用 S2B/批准/保真合同满足后另行进入，不以文本改稿验收替代。

### 阶段 4：持续委托与检索记忆

- 选择一个真实持续目标和一个触发源，落实委托身份、输入去重、工作项与执行关联、暂停/撤回和通知规则。
- 对涉及的外部动作补第 10 节协议及故障实验；对项目记忆补来源和当前适用性回查。
- 建立最小 memory schema、namespace、召回基线和 stale/delete/retract/conflict/unavailable 实验；只有代表性查询集证明轻量索引不足时才启动记忆组件 PoC。
- 若跨进程排障确有缺口，先执行 E9 的脱敏 OTel/OpenInference 旁路实验；collector/backend 失败不得改变任务或证据结果，且 Langfuse 与 Phoenix 只能二选一。
- 只有发现查询质量或排障缺口时才加入向量索引、专门 trace 等组件。
- **完成线**：持续任务在授权范围内推进，恢复不盲目重复动作，不用摘要替代证据，不无意义打扰用户。

### 阶段 5：外部渠道与更多研究工作流

- 按实际需求接邮件/IM/GitHub，完善来源认证、材料外发、动作幂等和通知回执。
- 再引入代码复现、实验设计、更多角色和多项目并行；逐项验证数据、环境和预算边界。
- **完成线**：新来源或角色不扩大既有授权，不出现第二调度权，不依赖手动修数据库才能恢复。

### 路线反证与停止条件

如果两个系统同时控制同一任务的 retry/cancel，集成就没有完成；如果必须自动放宽权限才能演示，应先修准入；如果要改写冻结证据才能迁移，应停止该方案。若真实实验表明完整 DSH 或其他执行底座明显更合适，可以重新决策，但必须显式替换权威与迁移历史，而不是叠加运行。

### 15.2 证据层级

unit 检验纯逻辑；contract 检验接口和拒绝语义；component 使用真实局部组件，例如临时 SQLite；system 运行真实进程与实际连接；e2e 覆盖主应用、选定执行器、领域服务和用户可见结果。mock provider、假 CLI、Node DOM 或跳过外部服务的测试不能称为真实模型端到端验证。

每次记录源码版本、环境、输入/材料身份、命令、结果、skip/warning、失败与未执行范围。故障注入和真实外部服务验证分开；通过前者不承诺所有供应商或网络条件都符合后者。不得为了门禁通过更换冻结样本、回写旧报告或将未知项填成成功。

### 15.3 变更工作流

代码或合同变更按 [开发指南](engineering/development-guide.md) 和仓库规则执行完整检查：Ruff format、Ruff lint、mypy、pytest、Phase 0 validate；对新增边界补针对性测试。涉及浏览器或桌面交互另做实际 UI/system 验证。失败原因分别记录，测试数量不替代产品验收。

文档整合只做文件、引用、身份与一致性检查，不把已有测试日志重新标成此轮运行结果。
