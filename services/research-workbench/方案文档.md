## 1. 产品定义

本章定义完整产品；第 2 节区分长期边界、计划能力和阶段范围；第 4 节定义共同约束；第 5—9 节说明格式与业务合同；第 12.6 节规定操作允许变化及验证方式；第 15 节规定开发顺序。不得用某一阶段的限制代替长期产品定位。

### 1.1 完整产品目标与可靠读取基础

完整的第一需求是规范模型对 DOCX、PDF、LaTeX、Origin、draw.io、SVG 等科研文件的操作，而不只是读取。模型提出操作意图，经过验证的格式适配器执行并返回证据；不让临时脚本直接处理生产文件。首个里程碑从 DOCX 读取开始，防止只提取部分文字就判断整份稿件的内容、格式和排版。

用户决定由哪个人或 Agent 修改、何时审核及如何接力；产品提供工具与共享记录，不启动、分派、轮询或管理 Agent。已授权操作中的前置检查、文件处理、改后验证和记录仍由引擎自动完成，不要求用户逐步指挥。外部 Agent 平台可以通过 MCP 自行组织流程，但不属于本产品的实现范围。

问题不在 Python 这门语言，而在于没有覆盖范围、页面证据和遗漏说明的读取结果被当作全文依据。受控解析器可以用 Python 实现；临时提取脚本的输出不能作为产品的权威文档表示。

可靠读取必须向用户和模型同时提供以下证据，DOCX 是第一批验收对象：

1. **原稿结构**：文本属于哪个区域，与公式、图表、域、引用、样式及分节设置有什么关系。
2. **实际页面**：指定 Word/WPS 环境导出的 PDF 和页面图像，以及可核实的页面尺寸、分栏和对象位置。
3. **证据关联**：结构对象和页面位置之间的映射，注明可靠匹配、歧义、未映射等状态。
4. **读取边界**：哪些内容已经解析，哪些仅保留原始对象或页面外观，哪些不支持、读取失败或尚未核验。

“保真读取”是以上证据链与覆盖报告的要求，不是保证任意 DOCX 都能完整理解、精确定位或跨渲染器一致。

### 1.2 期刊与表达检查建立在读取之后

可靠读取之后，再检查目标期刊规范、学术表达、作者术语和证据边界；需要修改时，再进入作者确认和安全写回。修改权限属于执行约束，不代替可靠读取，也不把产品永久限制成只读检查器。

产品不做开放式论文生成器。允许模型基于已确认事实提出段落或句子的候选表达，禁止编造事实、无依据扩写和未经批准直接写入正文。

~~~
原稿
  -> 只读部件清单与结构解析
  -> 指定环境的页面渲染
  -> 结构—页面关联与覆盖报告
  -> 用户与模型通过各自入口按需读取证据
  -> 加载期刊、样本和作者规则
  -> 提出问题与候选修改，记录依据、依赖和风险
  -> 展示风险与审核材料，由用户安排审核；按项目政策检查所需记录
  -> 作者查看已审核/未审核项，批量批准具体计划
  -> 按文字、格式、对象或结构的专用合同处理内部副本
  -> 重读实际结果、重新渲染与复核
  -> 检查基线与依赖仍有效后，条件式发布内部新基线
  -> 投稿清单和审计报告
~~~

核心原则：

- 不把纯文本、Markdown 或模型摘要当成 DOCX 的完整替代物。
- 结构证据和页面证据分别记录；页面上看见对象不等于已理解其内部数据。
- 未支持、未映射、未渲染和未读取的部分必须显式呈现，不能用“没有发现问题”代替。
- 文件操作按类型和格式采用专用合同；DOCX 文字补丁不拆开重建原稿，格式、对象和结构修改不冒充文字补丁。原始文件始终受保护。
- LaTeX 保持独立源文件链路，按模板编译，不由 Word 转换得到。
- 公式、图表、引用、域、样式和编号默认受保护；所有后续修改必须能回滚、能解释、能核对。
- 原稿目录零污染：不放备份、缓存、截图、临时脚本、编译产物、日志或隐藏配置；具体存储和导出合同见第 19 节。
- 共享项目状态不是共享一段模型摘要。原件、证据、推断、候选与复核记录分开；不可变只表示可追溯，不保证内容正确。
- 支持不同 Agent 接力，不等于自动管理 Agent 团队。用户安排分析和审核；模型不能签发用户批准，核心只执行文件保护、审核政策和发布检查。不同模型或对话不自动证明审核独立，未审核不得标为通过。

### 1.3 五个产品模块

| 模块 | 目标 | 核心产物 |
|---|---|---|
| 科研文件操作引擎 | 模型通过专用适配器规范读取、修改和渲染，不自行重建生产文件 | 内容与页面证据、能力声明、操作与复核结果 |
| 期刊模板与规则库 | 内置经审核的期刊模板，允许上传及更新，自动提取可观察要求 | 模板预览、规则事实与候选、已确认规则包、每刊摘要和版本差异 |
| 学术表达检查 | 改前加载规则，改后检查语言、术语、段落职责及事实边界 | 候选表达、规则命中、语义风险和人工确认项 |
| 变更与交付管理 | 规范审批、内部版本、恢复和导出，不污染作者目录 | 批准记录、版本差异、可恢复版本、用户选择的交付物 |
| 共享工作区与审查记录 | 让用户安排的不同 Agent 取得正确版本和相关依据，避免依赖聊天摘要接力 | 当前稿件与基线、版本化证据、修改与审核记录、未解决问题、实际读取范围、冲突与失效状态 |

第五模块复用同一个核心服务中的项目、证据和执行记录，不另建批准系统或状态真源。Proposal 与 Review 是工作记录，不表示内部有固定执行者、复核者或自动调度团队。

v1.2 的五项体验能力落在现有模块内：资料包组织所需材料，作者决定减少重复争论，预检提前发现不能执行的修改，缓存减少重复计算，书签保存接力位置。它们不自动派任务、不自动改稿、不代替证据或批准，也不增加五个子系统。

“支持某格式”必须细化为读取结构、页面预览、文字修改、格式修改、对象操作、结构编辑、生成、导出及验证等能力，分别声明支持范围与失败行为；不承诺所有格式都可任意增删改查。删除段落或对象属于经批准的副本结构编辑，移除项目资产属于内部管理，两者都不授权删除作者原始文件。

## 2. 产品范围与版本边界

### 2.1 产品主链路

以下是完整产品的目标范围，不代表已经实现；具体计划能力、阶段和验证条件以第 2.6 节为准。

- 各格式采用专用适配器，模型通过受控接口提出操作，不直接执行临时脚本修改原件。
- 内置经过来源、使用条件与能力核验的期刊模板；用户可导入新模板或新版，提取规则并渲染预览。
- 支持按阶段选择 Word 或 LaTeX 作为原稿真源。
- 支持规则包大厅：每刊一个独立版本化的规则包，项目按包名和版本绑定引用。
- 首先提供 Word 原稿的只读结构解析、实际页面、对象关联和读取覆盖报告。
- 为模型提供统一文档读取入口，保留区域、对象类型、来源和未覆盖状态。
- 用版本化共享工作区保存研究目标、源证据、候选、实际修改和审核记录；用户安排 Agent 按任务取用材料，风险与未审核项明确展示，人工批量批准具体修改。
- 支持正文文字问题定位和作者确认后的安全替换。
- 支持 Word 或 WPS 独立导出 PDF。
- 支持 PDF 页数、页面尺寸、图表、题注、关键句、数字和单位复核。
- 支持 Zotero 条目、Zotero 样本库和 CSL 成文格式核验。
- 支持 Python、SVG、draw.io 图件的源文件和投稿文件登记。
- 支持 LaTeX 源文件依赖图、受保护范围识别和按模板编译。
- 输出投稿前清单、修改日志、规则来源和复核报告。
- 内部版本和中间文件统一管理，所有阶段遵守第 19 节工作区零污染与受控交付合同。

### 2.2 MVP-Docx-Fidelity-0.1：唯一首版完成线

第一版以 DOCX 可靠读取为完成线，同时建立该读取所需的状态与证据基础，不修改稿件：

- 原始文件指纹、OOXML 部件与关系清单。
- 区域、内容对象、格式来源和布局设置索引。
- Word 或 WPS 指定环境的 PDF 与页面图像。
- 结构对象与页面证据的关联，保留多对多、歧义和未映射状态。
- 覆盖报告：已解析、部分解析、不支持、失败、未核验分别列出。
- 模型统一读取接口：按区域、对象和页面查询，明确分页、截断与未读范围。
- 只读完整性检查，以及经独立人工标注的回归样本验证。
- 不可变源快照、初始项目基线、实际读取范围和能力范围内的版本化 EvidenceItem；导入不等于事实核验通过。
- 可信桌面操作可重新导入外部稿件，或更新目标、作者边界及已有规则版本的绑定元数据，按第 4.11 节建立新读取基线；不修改稿件，不要求 0.2 的候选或改稿批准，也不提前提供模板提取和规则检查。
- 观察、推断和候选分离；持久证据与可重建缓存分离；以显式版本依赖识别相关结果失效，不实现完整知识图谱或多 Agent 调度平台。
- 读取结果以轻量任务资料包按需组织，保存用户明确填写的当前稿件/项目要求、读取型接力书签与缓存有效性信息；不自动学习作者习惯、不猜测完整语义依赖，也不开放修改预检或试改。

验收以第 13.1 节、第 13.6 节及第 13.7 节的 S1 适用项为准。IJAM 是首个真实稿件样本，不是首版唯一测试样本；无需先完成任何期刊规则包。改写效果、去 AI 味和自动投稿均不是首版成功指标。

### 2.3 MVP-Word-0.2：检查与受控编辑

在 0.1 的证据表示上分两步完成：先交付模板初次导入、规则提取、渲染、来源核验、每刊摘要与升级差异，再加入表达规则检查、结构化候选、风险标记、用户安排的审核与记录、具体计划批量批准、副本字节级文字补丁和改后重新取证。第 5 节的文字写回合同在本阶段验收，不要求 0.1 实现写入器。

0.2 允许已授权 MCP 客户端提交 Proposal、读取审核材料及提交 Review，由用户决定谁做、何时做及是否另找 Agent 审核。核心提供确定性检查、风险与研究方向检查材料、依赖失效、幂等恢复和条件式发布；审核采用第 4.7 节的用户控制或项目严格模式，不启动固定团队。完整主张图谱后置；自动 Agent 编排不在产品路线内，也不因共享工作区扩大格式编辑范围。

0.2 检查格式，但不自动调整任意版式。字体、缩进、分栏、对象等写操作属于后续独立能力，不能用 w:t 文字补丁合同冒充已经支持。S2A 将已发布规则与适用决定加入资料包；S2B 再增加 change.preflight、局部表达决定、修改/审核资料与接力书签。预检只检查当前计划，不试改、不占用批准，不因预检存在就开放新的写操作。

首个期刊规则包仍为 IJAM；Engineering Letters 为第二规则包草案。Zotero/CSL 完整核验、外部图件管理和 LaTeX 编译分别后置，不与两个 MVP 的完成线混写。

### 2.4 长期产品边界

- 不做开放式论文续写。
- 不做脱离原文事实的整段生成；允许以已确认事实为边界的候选表达，须检查和批准后才可写入。
- 不做 AI 检测分数或所谓人类化分数。
- 不把 Word 转成 LaTeX。
- 不把 LaTeX 转成新的 Word。
- 不承诺任意格式或任意对象的完整理解与编辑；未知、不支持和失败必须明确报告。
- 不使用未经适配器验收的临时脚本读写生产文件，不在失败时静默改用低保真转换流程。
- Zotero 引用不随通用域刷新；若后续支持插件刷新，须采用独立授权与验证合同。
- 不用知网或 iThenticate 分数作为产品结果。
- 不做在线协作编辑器。
- 不实现 Agent 启动、分派、自动反方/仲裁、多模型投票、反复讨论到一致、团队调度或 Agent 任务租约系统；外部工具可通过 MCP 安排接力，但不能绕过本产品的文件与权限合同。
- 不做完整 Word、Overleaf 或 Origin 替代品。
- 不混合比较 Word 和 WPS 的 PDF。
- 模型不替用户签发批准；桌面和模型入口均不得绕过操作保护、版本检查与零污染要求。

### 2.5 阶段性限制与当前实现决策

- 0.1 仅交付可靠读取、页面与覆盖证据及其版本化状态基础，不生成候选改写、不写回稿件、不调整排版、不输出投稿包，不以期刊检查通过作为读取验收。
- 0.2 先做一个期刊的模板与规则，再做表达检查和受控 DOCX 文字替换；不提前加入字体、间距、分栏等格式修改，也不新增或删除章节、公式、图表等结构。
- 0.2 不输出带修订痕迹的稿件，不使用 JATS 作为投稿输出；0.1 和 0.2 均不生成审稿回复。这些是阶段限制，不写成永久产品禁令。
- Origin 首期仅登记资产及已有导出文件；后续按宿主条件逐项验证操作，不永久限定为人工导出。
- 当前 DOCX 读取与文字补丁合同不采用 python-docx 或 OfficeCLI 作为生产解析器、写回器，理由与验证范围见第 5 节。这是有范围的组件决策，不是对实现语言的永久禁止；若改选组件须修订合同并重新验收。
- 后续格式、对象、结构编辑和新文件生成仍是规划，需要专用合同与回归样本后单独交付；不能因写入产品目标就自动归入 0.2。

### 2.6 格式 × 操作能力矩阵（全部为规划）

本表描述拟交付范围，不代表现成引擎已经支持。标记 S1 为阶段 1，S2A 为阶段 2A（模板与规则），S2B 为阶段 2B（表达、复核与文字写回），S3 为阶段 3，S4 为阶段 4；“候选”表示 S4 内仍待确认的子能力，不是本阶段全部完成的承诺。“未排期”不表示永久禁止，也不允许对外宣称可用。

## 3. 四层规则体系

本节从 MVP-Word-0.2 起生效。规则引擎是读取服务的下游；没有足够读取证据时，相关规则返回“无法判断”，不能视为检查通过。规则采集可以并行推进，不阻塞 0.1。

### 3.0 规则包的组织：大厅、引用与绑定

规则不做成一坨全量清单。每个期刊一个独立的规则包，各自维护、各自定版本；产品提供一个规则包大厅（0.2 首发为本地目录加索引），陈列可引用的包；项目声明引用哪个刊的包并绑定版本。

- **大厅**：应用数据目录内的 `rulepacks/` 加 `index.json`，不创建在作者项目目录。每个条目记录刊名、包版本、规则条数、状态（draft / verified）、来源快照哈希和上次验证日期。
- **包的内容只含随刊变化的两层**：期刊投稿须知规则（3.1）和期刊样本倾向（3.2）。作者术语与证据边界（3.3）是项目级文件，跨刊复用，不进任何刊包；稿件内部一致性（3.4）是引擎内置检查，与刊无关。
- **引用与绑定**：应用内部项目记录声明 `rulepack: <包名>@<版本>`，默认不往作者目录写 project.yaml。运行时加载绑定包和作者规则；升级须明确确认，旧项目不静默换版。报告记录包 ID、版本和逐条来源。
- **首发检查器数量预算**：每个包首发启用的自动检查项上限 20 条，按真实命中和误报迭代。模板事实、候选规则、未覆盖项不受此数量限制，不为凑预算删除已提取信息。规则包是数据，不允许借规则文件执行任意脚本。

~~~text
rulepacks/
├─ index.json                  # 大厅索引
├─ ijam/
│  └─ 1.0.0/
│     ├─ rulepack.yaml         # 包元数据 + 规则条目
│     ├─ sources/              # 页面快照、模板探针产物
│     ├─ templates/            # 不可变模板原件及导入记录
│     ├─ extracted-rules.yaml  # 观察事实、推断候选、待确认项
│     ├─ rendered-pages/       # 模板页面证据
│     ├─ journal-summary.md    # 从规则生成、可追溯的每刊摘要
│     ├─ review-status.yaml    # 发布状态与人工核验
│     └─ checksums.sha256
└─ engineering-letters/
   └─ 0.1.0-draft/
~~~

### 3.1 期刊投稿须知规则

这是最高优先级的规范来源，属于硬规则。

包括：

- 文章类型、标题、摘要和关键词要求。
- 字数、章节顺序和标题层级。
- 图、表、公式和参考文献格式。
- 图片格式、分辨率、宽度和颜色要求。
- 页边距、字体、行距和页面尺寸。
- 数据、代码、伦理、基金、利益冲突和作者贡献声明。
- 是否需要 highlights、graphical abstract、cover letter 和补充材料。
- 投稿文件命名和文件分组要求。

每条规则记录：

- 官方来源 URL。
- 来源快照或文件哈希。
- 规则版本和验证日期。
- 适用的文章类型。
- 自动检查方式。
- 是否可以自动修复。
- 是否必须人工确认。

### 3.2 已发表论文样本规则

已发表论文用于观察目标期刊的实际表达方式：

- 摘要如何起句和收束。
- Introduction、Methods、Results、Discussion 如何分配段落职责。
- 结果动词和断言强度。
- 常用术语、缩写和数字表达。
- 图表题注和正文引用方式。

样本规则属于“期刊样本倾向”，不能直接当成硬性投稿要求。

样本必须按以下条件分类：

- 期刊。
- 文章类型。
- 研究领域。
- 发表年份。
- 语言。
- 是否为正式发表版本。

系统只提取结构、统计模式和规则候选，不复制整句，不把样本短语作为作者稿件的自动替换来源。

### 3.3 作者术语和证据边界规则

作者规则用于防止同一对象反复换名，以及防止实验结果被扩大解释。

至少包含：

- 对象的规范名称和允许别名。
- 方法、数据集、指标和实验环境的固定名称。
- 缩写首次定义和后续写法。
- 数字、单位、小数位和统计口径。
- 允许使用的断言动词。
- 当前证据支持的范围。
- 明确禁止扩大的结论。

示例：

~~~
对象：Fabric MVCC
规范名称：Fabric MVCC conflict
允许别名：MVCC conflict
禁止随意替换：concurrency failure

主张：共享统计写入移出主交易路径后，消除了该共享键引起的冲突
证据：Table 7、配对消融结果
适用范围：当前 workload
禁止扩大：通用吞吐提升、所有并发场景均有效
~~~

#### 3.3.1 作者决定的作用域与适用性

复用现有作者决定记录，不另建自动学习系统。决定分为“表达偏好/风格例外”和“研究目标/事实边界相关决定”：前者可以减少已确认的风格提醒；后者保留作者判断和相关证据状态，不能因被作者确认就变成科学事实 PASS，也不能掩盖错误数字、引用不支持、文件损坏或证据不足。

| 作用域 | 含义 | 开放阶段 |
|---|---|---|
| DOCUMENT | 当前指定稿件及明确的适用版本/条件 | S1：仅保存用户明确填写的术语、目标和边界，暂不运行表达例外引擎 |
| PROJECT | 当前研究项目，仍须按语言、文章类型等适用条件筛选 | S1：显式项目要求，不跨项目扩散 |
| LOCAL | 已可靠定位的特定句子或对象 | S2B：作者接受/拒绝风格建议、局部例外，绑定工件版本与定位证据 |
| SECTION | 当前指定章节 | S2B：按章节定位与职责限制作用范围 |
| PROFILE | 作者在其他项目的偏好 | 后置，须单独选择应用范围；不从一次拒绝自动推导 |

决定至少保存 ID/版本、类型、内容、作用域、适用对象与条件、用户确认来源/时间、原因、相关规则/证据引用（适用时）和失效条件。Agent 可以提出建议，只有可信用户确认才成为作者决定；普通 MCP 不能直接发布偏好或覆盖证据状态。更新形成新记录并保留历史；涉及当前基线绑定时按第 4.11 节更新，不能用修改“记忆”绕过版本检查。

一次拒绝默认只针对本次问题和具体位置，不自动形成全篇/项目例外。明确保存为 LOCAL/SECTION 决定后，源文字、对象定位或已记录章节职责变化须重判适用性，无法确认则显示待确认且不继续抑制提醒。规则升级后核对依赖规则的决定，不一律作废无关偏好，也不沿用已不适用例外。S2A 只支持目标期刊样本倾向、可选格式和待确认事项的项目/稿件级决定；作者偏好不得覆盖官方硬要求，待确认要求也不会因保存决定而升级为已确认规则。

问题去重仅合并展示。按项目、工件版本、可靠定位/前像、规则或检查项 ID/版本及问题类型形成可重建的问题指纹；同一问题保留各次检查、Review、来源和处置引用。不同审核者不必制造重复卡片，但 PASS、FAIL、UNCERTAIN 不互相抵消，不按票数或最后写入者自动解决。版本或规则变化时重判适用性；没有可靠映射不把相似文字的问题合并。S1 只处理已存在的读取问题；表达与审核问题去重在 S2B 开放。

### 3.4 稿件内部一致性规则

检查同一稿件内部是否前后一致：

- 数字和单位。
- 图表、公式和章节编号。
- 正文引用和参考文献。
- 对象名称和缩写。
- 摘要、正文和结论的关键事实。
- 实验条件、样本量、基线和比较对象。
- 基金、作者贡献、利益冲突等声明。

### 3.5 规则严重级别

~~~
ERROR       明确违反投稿须知或破坏文档结构
WARNING     存在证据、术语或一致性风险
ADVICE      学术表达和段落组织建议
HUMAN       必须由作者判断，系统不自动改写
~~~

每条问题同时显示：

- 规则来源。
- 规则类型。
- 严重级别。
- 命中的原文。
- 修改原因。
- 是否改变事实。
- 建议动作。

### 3.6 模板初次导入与版本更新

模板引擎不是手工录规则的替代界面，而要实际提取模板已使用的结构和格式。每次首次导入或上传新版都执行以下流程：

0.2 首先验收 Word 模板。LaTeX 或其他尚无适配器的模板可以登记原件，但解析、渲染和规则提取必须标为未支持/待处理，不能占位宣布成功；相应能力随阶段 4 扩展。

1. 在应用内部保存模板原件、来源、期刊、文章类型、投稿阶段、版本和内容哈希；内置分发前核验使用条件。
2. 按原生格式解析结构，旧 .doc 的转换作为独立派生步骤记录，原件不变。
3. 在指定 Word/WPS 或模板要求的 LaTeX 环境中渲染，保存页面证据和环境。
4. 按对象提取声明值、继承结果、实际观测及无法解析项，不只提取正文文字。
5. 将模板事实与官方投稿说明、模板内文字说明合并，形成候选规则；逐条保留证据指针。
6. 标记冲突、适用范围和人工待确认项，确认后发布版本化规则包。
7. 输出模板原貌、分类规则明细和一段每刊摘要；摘要只概括有来源的规则，附版本、适用阶段和未确认事项。
8. 新版额外输出新增、删除、变更与需要重新核验的规则；旧项目继续绑定旧版。用户升级绑定后，重判依赖相关规则的作者决定及检查结果，保留无关偏好；旧例外或旧 PASS 不自动迁移，官方硬要求不能由作者例外覆盖。

至少覆盖以下分类：页面尺寸、单/双栏、页边距、分节分页与分栏切换、标题层级、作者与单位格式、摘要与关键词区域、字体字号、粗体斜体、首行及悬挂缩进、行距与段前段后间距、表格与题注、公式及数学对象、编号、交叉引用、中英文标点、参考文献格式。这里是能力检查目录，不保证单一模板包含全部要求；每类必须输出提取结果或缺口。

提取结果分为三层，不能混写：

- 模板事实：指定对象实际声明或显示的格式，有明确原始证据。
- 规则候选：从多个对象推断出的适用模式，可能存在例外。
- 已确认要求：经权威文字要求、可验证模板结构或人工核验后，按适用范围发布。

某个样例词用了斜体，不自动推广成全文规则；仅看到一条参考文献，不宣称推导出全部文献类型的样式。无法从模板推导的规则保留待确认，不假装“全部提取完成”。

每条规则记录 rule_id、规则类型、对象类型、文章类型、稿件阶段、语言、声明、来源及哈希、证据位置、观察/推断标记、核验状态、例外、冲突、检查方式和是否允许自动修复。置信度可作辅助，不能替代来源或核验。

模板预览与规则展示必须可互相定位：规则跳到相应对象或候选页；不可靠的定位显示歧义，不绘制虚假精确高亮。

### 3.7 引用格式与冲突处理

交叉引用不全局强制上标。文献引用、图表引用、公式引用、章节引用和脚注标记分别管理，由绑定期刊、稿件阶段和引用类型决定基线/上标、括号、顺序及标点位置。来源不足时不得套用另一刊或通用偏好。

官方投稿要求、模板可验证结构、同刊样本、作者规则和通用建议的来源层次沿用 17.5；出现同阶段官方资料相互矛盾时标记冲突，不默选一种并报告合规。作者术语与事实边界是独立内容约束，不能为满足模板句式而改变实验结论。

## 4. 工作流、共同约束与执行权限

### 4.1 首个里程碑的工程流程

~~~
1. 只读接收 DOCX，记录源文件哈希和读取会话
2. 枚举包内所有部件及关系，登记外部依赖和未知对象
3. 解析结构、区域、样式来源和布局设置，保留受保护边界
4. 在应用内部任务目录建立隔离的 render-copy，用指定 Word/WPS 环境导出 PDF
5. 保存页面图像和可用文本层，记录字体、修订显示及域处理状态
6. 关联结构对象与页面证据；无法关联时保留原对象及原因
7. 生成覆盖报告、未解决项和可供模型按需查询的文档索引
8. 保存初始基线、版本化证据、来源依赖与实际读取记录；导入状态不冒充核验通过
9. 复用索引与读取记录提供按需资料目录、显式作者要求和读取型书签；不推断完整语义依赖
10. 验证源文件与作者目录未被任务改变，按第 13.1、13.4 节及 13.6—13.7 的 S1 适用项验收
~~~

只有后续 0.2 才加载项目绑定的期刊规则包，生成问题与候选建议，并在作者确认后执行副本写回。读取结果本身不授予编辑权限。

### 4.2 第一版界面

第一版不做完整编辑器，不自行实现 DOCX 排版引擎。

三栏用于核实“读到了什么、在哪里、还缺什么”：

- 左侧：文档区域与对象树、读取覆盖问题。
- 中间：指定渲染器的 PDF/页面预览；只有可靠关联才显示精确高亮，歧义位置显示候选页或对象范围。
- 右侧：原始结构、格式来源、关联依据、覆盖状态和未识别原因。

需要在 Word/WPS 中查看时，打开独立查看副本，不内嵌进程；能可靠定位才跳转，否则说明不能精确定位。预览存在不等于模型已查看该页，界面和读取记录必须区分。

首版允许查看对象、查看页面、确认人工核验和导出读取报告，不提供接受改写按钮。0.2 再增加规则问题、建议差异、接受/拒绝及例外说明。

0.1 提供独立的“更新读取基线”入口，展示新旧来源、目标或绑定的差异，由用户确认后切换；不包装成改稿批准。0.2 的候选、批准和发布记录显示具体版本，绑定后撤销与结果未知均有独立提示。

0.1 展示当前基线、证据来源、读取缺口和失效原因，可按任务查看资料目录、作者显式要求及读取型书签；0.2 增加待处理列表，按待修改、待审核、有争议、等待批准、已应用待验证、已完成及已过期等条件查看记录。这些是组合筛选视图，不是新的状态真源，也不向 Agent 自动派单。界面分别显示语义审核、文件验证、有效性、授权及执行状态；批准前展开风险、未审核项和适用政策，不用一个“已通过”掩盖未审核、过期证据或缺少批准。

模板库页面在 0.2 展示模板原貌、规则明细、每刊摘要和版本差异。项目界面始终区分原始文件、内部工作版本、已核验待发布版本、当前基线和已导出版本；展示存储占用、可清理空间和恢复边界，不把应用内部几十个文件当成交付目录。

### 4.3 所有格式与入口共用的执行约束

以下约束由桌面核心服务执行，对用户界面、MCP 及未来的辅助客户端同样适用；各格式专章只能收紧或具体化，不能绕过：

- **能力与合同**：先确认实际格式、对象、操作和环境受到支持，再选择专用合同；未定义合同或未通过验收的写操作不得开放。
- **来源与版本**：每次任务绑定不可变源快照、已用依赖及规则版本；外部改动建立新快照，旧页面关联与批准不静默迁移。
- **范围与保护**：文字、格式、对象、结构和新文件生成分别声明允许变化及影响范围；可以读取不代表可以修改，数量变化必须与具体操作预期一致。
- **批准与身份**：模型只提交候选或执行请求；修改批准由可信用户操作产生，按第 4.4 节校验。
- **内部处理与验证**：先在应用管理的副本和任务目录执行，重读实际结果并通过本次必需检查后，按第 4.9 节条件式发布；产物生成、验证通过和成为当前基线是不同状态，失败和中断不能伪报完成。
- **隔离与零污染**：原稿及作者目录默认只读，内部项目数据、版本和临时产物不得外溢；第 19 节是存储与交付的权威合同。
- **明确交付**：内部生成、用户批准、版本核验和向外导出是不同动作；导出只写作者明确选择的目标。
- **诚实返回**：每个步骤报告完成范围、未执行范围、证据和失败原因；禁止静默换成重建、降质转换或临时脚本再宣称同一操作成功。

执行通道需限制模型和子进程绕过核心服务直接改原稿的路径。只暴露 MCP 或提供 AGENTS.md 不是隔离证明；缺少宿主权限约束时明确为非强制接入，不能声称实现禁止绕过。受控模式下不满足隔离或零污染条件就拒绝相应任务。

源文件内的文字、批注或模板说明属于被处理的数据，不作为用户批准、权限提升或执行任意脚本的指令。即使这些文字被抽入 EvidenceItem、缓存、规则候选或复核上下文，其不可信来源仍须保留；不得借共享状态自动提升为项目规则、触发外部工具或代表作者批准。官方模板要求按第 3 节的来源核验流程发布，不执行其中面向 Agent 的指令。0.1 对稿件只读，但建立内部索引、缓存和报告会写应用数据空间，不能称为“完全不写磁盘”。

### 4.4 用户批准、计划绑定与版本状态

模型可以读取规则、提交候选并请求执行已批准计划，但不能批准自己的修改。用户通过桌面界面或独立可信通道查看原文/对象、候选差异和影响，再产生服务端可校验的批准记录。普通模型接口不提供可自签的 edit.approve；也不能通过填写 approved=true 获得批准。

批准至少绑定：

- 项目 ID、源文件哈希与内部快照版本。
- 源 Baseline、具体 Proposal/批次及证据版本引用。
- 原文/原对象的前像和候选结果，或新文件生成的具体规格。
- 操作类型、参数、允许变化范围、依赖、完整计划 plan_hash 和有序候选清单 ordered_proposal_hashes（含各 proposal_hash）；单候选也使用单项计划。
- 已使用的规则版本、审核政策版本及模式、前置检查与要求的验证条件；保留批准时展示的未审核项、争议及用户处置。
- 用户身份、批准时间、有效期、撤销状态及执行记录。

用户应批准可见的具体计划，不批准由模型日后任意填充的空白操作，也不代表授权产品安排后续 Agent。任何影响已批准结果或范围的变更都使批准失效；源快照、绑定规则或审核政策版本变化后重新检查和批准。用户控制模式可在明确展示未审核或争议项后批准具体计划，授权不改变审核结论；严格模式下批准也不能绕过必需 Review 的发布要求。仅验证环境变化时至少重新执行相关前置检查，若影响计划、保护条件或结果预期也须重新批准。

服务执行时校验批准来源、有效期、未撤销状态、plan_hash 与 ordered_proposal_hashes 的一致性、前像和保护边界。候选集合、顺序或组合影响改变，即使每个 proposal_hash 都未变，旧计划复核和批准也不能继续使用。凭据的签发权与普通模型调用权隔离，认证材料不进入模型上下文或可复用的导出日志。具体安全机制在实现时验证，不以“不可伪造”一句话代替权限测试。

已完成请求的重复提交按第 4.10 节返回原结果，不因当前基线已推进而重复执行或误报旧请求冲突；执行中、崩溃或结果不明时先核对任务和产物。撤销或过期在开始应用前阻止执行，开始后在安全点停止，并禁止尚未完成的基线发布；已完成的历史发布不自动撤销，需要另行提出恢复计划。恢复按第 19 节处理。

复核结论、依赖有效性、批准有效性与执行绑定按第 4.7 节分别表达，不合并成一条生命周期。0.2 改稿逻辑操作的 execution_status 使用 NOT_STARTED（未开始）、RUNNING（执行中）、VALIDATING（验证中）、READY_TO_PUBLISH（待发布）、RETRY_PENDING（待安全重试）、INTERRUPTED（中断）、UNKNOWN（结果未知）、RECONCILING（正在对账），以及 PUBLISHED、FAILED、VALIDATION_FAILED、REJECTED、CANCELLED 五种终态。只有结局已确定才进入终态并生成最终 ChangeResult；一次尝试失败但仍可恢复时记录尝试结果，不提前终结整个操作。

UNKNOWN 表示无法确认执行或提交是否完成，RECONCILING 表示正在核对持久记录和实际产物，另保存 last_known_phase。未查明时只允许读取和对账，不直接重放修改或发布；对账发现已提交则返回原结果，证明未提交后才按仍有效的授权决定恢复或终止。正在对账不是副作用类型：side_effect_status 对副本修改、基线提交等具体副作用分别记录 NONE、CONFIRMED 或 UNKNOWN，并附证据，不放入 RECONCILING。取消请求也不能把结果未知的操作直接标成“确定未提交”。

导出另记未导出、导出中、已导出、失败或部分导出，不改变已经确定的改稿发布结果。批准不等于核验，核验不等于发布或交付；候选存储、内部版本生成与外部导出分别授权，不把批准改稿扩大成任意磁盘写权限。

### 4.5 操作结果与失败分类

以下是拟采用的业务结果码，用于区分处置方式，不是现有实现声明，也不是把全部失败都编码成 unsupported_operation：

| 结果码 | 适用情况 | 必须说明 |
|---|---|---|
| unsupported_operation | 当前适配器不支持该格式/对象/操作组合 | 不支持的范围；被拒绝步骤未执行；组合任务此前是否已有实际步骤和副作用 |
| environment_unavailable | 已定义能力所需的宿主、字体、依赖、许可或运行条件不具备 | 缺少的条件与未执行步骤；不假称功能永久不支持 |
| version_conflict | 源快照、前像、计划或规则绑定已变化 | 哪项冲突；旧批准/页面证据是否失效；需要重新检查的范围 |
| idempotency_conflict | 同一 operation_id 被用于不同计划、源基线或请求内容 | 已绑定的请求摘要与冲突字段；不执行第二次请求 |
| approval_required | 缺少有效用户批准，或批准已过期/撤销 | 当前计划 ID 和批准需求；不能自动代用户确认 |
| permission_denied | 路径、资源、执行或交付动作超出权限边界 | 被拒绝动作；不能通过提示词或另一接口绕过 |
| execution_failed | 已开始的解析、修改、编译或渲染步骤失败 | 已执行步骤、内部副作用、任务状态及能否安全重试 |
| validation_failed | 产物已生成但没有通过合同检查 | 未通过的检查和证据；产物留待诊断，不登记为合格版本 |

取消、中断、部分完成和部分导出使用独立任务状态，不混成全部成功或全部未执行。每项返回绑定任务、能力、合同和源快照，并列明实际 completed_steps、not_executed、side_effects、validation、evidence_refs 及 next_action；只有真正完成的读取才可列入 completed_steps。

能在执行前判断的不支持应尽早拒绝；执行中才发现不支持对象时，必须同时报告已发生步骤和副作用，不把整个任务改写成“从未执行”。重试前依据实际状态对账，不能由模型猜测是否应重复写入。提供替代路线时只作为明确的新建议，不静默执行不同合同。

UNCERTAIN 是复核结论，STALE 是有效性状态，不等同于解析失败或不支持。它们阻断本次必需步骤时返回具体检查状态、证据及人工处理入口，不伪装成通过，也不无条件停止整个项目。

UNKNOWN / RECONCILING 使用执行状态返回，不能仅因超时或响应丢失就返回确定的 execution_failed；错误结果码还须附本次尝试是否可恢复、逻辑操作是否已终结及副作用证据。已终结失败与尚待对账的请求不能混用一个“重试”动作。

### 4.6 共享项目状态与证据对象

“共享池”是有来源、版本、权限和核验状态的项目状态，不是供 Agent 任意覆写的聊天摘要。逻辑上分开保存已确认项目约束、不可变来源与证据、候选判断、复核与决定、可重建缓存；由现有核心服务统一管理。

| 概念对象 | 职责与边界 |
|---|---|
| ArtifactVersion | 不可变源工件或派生产物版本，绑定内容哈希、来源、依赖和生成环境；不可变不证明内容正确 |
| EvidenceItem | 有精确来源位置的观察、值、约束、推断或主张，标明类别与证据版本；不得隐式升级为已确认事实 |
| Baseline | 不可变项目清单，引用稿件、规则、目标和作者决定的具体版本，S2B 增加审核政策绑定；记录读取基线更新或修改产物发布的来源，当前指针仅由核心更新 |
| Task | 用户或已授权客户端请求的工作范围、输入基线、依赖版本、实际读取覆盖、执行记录与状态；不表示向某个 Agent 派单，摘要不替代源证据 |
| Proposal | 精确候选差异、依据、风险、依赖和影响位置；正式复核绑定冻结版本与 proposal_hash，修改产生新版本，不原地更改已复核或已批准候选 |
| Review | 人工、确定性检查或用户安排的 Agent 对明确版本及范围提交的核验记录，包含提交来源、方法、证据、限制与结论；S1 为读取核验，S2B 增加冻结候选/计划及实际产物审核，不代表固定复核角色 |
| Approval | 可信用户对具体执行计划的授权，绑定 plan_hash、ordered_proposal_hashes、源基线、依赖及执行范围；单候选使用单项计划，不用 proposal_hash 代替 plan_hash |
| ChangeResult | 一次已登记改稿逻辑操作进入终态时生成的最终不可变结果，引用实际产物、ValidationResult、适用的 PublicationRecord 和副作用证据；成功、终结失败/拒绝/取消都可有结果，非终态不预造最终结果 |
| CacheEntry | 可清理、可重建的解析、索引和预览结果，不能充当唯一事实或审计真源 |

以上是九类核心概念对象，不要求九个服务、数据库或文件。0.1 只实现只读基础所需部分，保留人工标注和确定性核验记录；Proposal、改稿 Approval、接力审核记录和写回 ChangeResult 随 S2B 开放。保存这些对象不要求产品托管任何 Agent。

0.2 将检查与发布分别建为可追溯记录，不再提前把它们拼成尚无最终结论的 ChangeResult：

| 关联记录 | 产生时机与内容 |
|---|---|
| ValidationResult | 对具体候选产物完成指定检查后保存的不可变记录，绑定产物版本/哈希、plan_hash、有序候选清单及证据版本、实际差异、检查范围/方法/结果和未解决项；不包含尚未发生的发布结论 |
| PublicationRecord | 一次发布尝试得到确定判断时保存，记录尝试标识、operation_id、预期/实际基线、候选与检查引用及 SUCCEEDED / CONFLICT / REJECTED 和原因；未尝试发布或结果仍未知时不伪造确定记录 |

这两种是关联记录合同，不要求另建服务。候选产物本身使用 ArtifactVersion，不再增加含义重复的 CandidateResult。重新检查生成新的 ValidationResult，不覆盖旧检查；最终 ChangeResult 对一个 operation_id 至多一份，在结局确定时引用实际发生的记录。未走到发布的终结失败保留原因与可用证据，PublicationRecord 引用为空；可恢复的尝试和 UNKNOWN / RECONCILING 只保存进度与尝试记录。

EvidenceItem 至少记录 evidence_id、evidence_version、kind、statement、value/unit（适用时）、scope、artifact_version、object_locator、content_hash、extraction_method 与工具版本、verification_method 与核验记录引用、limitations、dependencies。区分源工件、抽取观察/数值、解释性推断和稿件主张；它们可使用同一记录模型，但不能因为存进共享池或被多个 Agent 重复引用就自动成为事实。

证据内容、提取方法或适用范围纠正时生成新版本，不覆盖历史 Review 或 Approval 引用的旧记录。verification_status 由关联且仍有效的 Review 或确定性检查记录按已定义范围推导；缺少必需检查、记录冲突或证据不足不得汇总为 PASS。允许保存可重建的派生缓存/物化值，但不能把该字段作为脱离核验记录、可由用户或 Agent 直接设定的权威判定；合法人工核验须产生有身份、依据及范围的核验记录。MCP/API 不提供绕过记录直接设为 PASS 的路径，派生值缺少支持或其依据失效时重新计算，不继续返回旧 PASS。

object_locator 绑定工件版本与可复核的结构、区域和内容定位证据；页面位置还绑定渲染版本。第 5.2 节的会话 node_id 不能当作跨版本永久证据 ID。来源变化后重新定位，无法确认时标记失效或歧义，不因文字相似就挂到另一段。

接力入口按任务提供当前目标、边界、基线、规则与术语、相关原始证据、上一轮实际改动及产物、已有审核和未解决问题，不要求新 Agent 阅读全部历史对话。使用说明建议先核对这些材料再继续工作；核心依据实际版本而非模型口头承诺放行。记录已授权调用主体/客户端、服务端读取记录、实际返回版本、分页、截断与未读范围；“已获取”不等于“已理解”。模型品牌、版本和对话标识可作为来源元数据，但不作为权限或独立性证明。

#### 4.6.1 按需任务资料包

任务资料包是绑定版本的目录和组合视图，不新增事实源或要求复制整稿。先返回任务目标/范围、基线、材料条目及展开入口；条目注明来源版本与定位、纳入原因、覆盖/限制、是否已实际取用。生成目录和展开材料时均校验访问权限，不向无权客户端泄露受限材料内容或敏感元数据；资料可分页展开，展开时再核对版本，不能把另一版材料静默接到旧包中。

目录区分“已定位的相关材料”“已知相关但尚未读取”“关联尚未确认或来源缺失”。例如正文提到 Table 7 或文献 [21]，原始数据/文献未取得时保留缺口；不因没找到就省略或编造入口。不保证已找齐全部相关材料；S1 仅按目标区域、必要邻文、可核实对象关系和已登记显式引用组织，不先做语义知识图谱或自动文献抓取。

S1 提供正文/对象/页面、读取覆盖、已有证据入口及用户显式要求；S2A 加入当前绑定的已发布期刊规则、来源和适用决定；S2B 加入候选、计划与实际差异、真实产物、Review 和变更相关问题。无法支持的材料标明原因。摘要可辅助导航，不能替代源稿、页面、证据或实际差异；收到目录不算读过目录所指内容。

资料包至少返回包引用/生成时的基线、任务范围、所用关系/方法版本、条目引用与缺口。查询时展示相对当前基线的适用性；旧包可作历史入口，不自动跟随当前指针改写内容。包内文档文字、备注和建议仍是不可信数据，不变成权限、作者决定或执行指令。实际用过的版本与条目清单进入读取记录，可重建目录视图进入缓存，不需要独立服务。

#### 4.6.2 轻量接力书签

接力书签是 Task 的交接引用，可用稳定 ID 获取，不是 DOCX 原生书签，也不改稿件。保存任务范围、创建时的基线、读取范围/游标、证据与材料引用、未完成项、创建主体和时间；S2B 再引用 Proposal、实际产物、ChangeResult、Review 及变更问题。只引用已存在且有权访问的记录，不复制形成第二套事实，也不授予接收者原本没有的权限。

“已完成”由真实记录推导，明确区分已返回材料、已提交候选、已修改内部副本、文件已验证、语义已审核、已发布及已导出；不存在的阶段留空。创建时的完成描述绑定当时记录，后续进展另列，不把后来完成的步骤回写成创建书签时已经完成。Agent 自述与“建议下一步”单独标为备注，不能冒充执行结果或自动启动后续 Agent。S1 只提供读取型书签；保存内部书签是允许的元数据写入，不是稿件写入。

读取书签时比较绑定基线与当前版本：整体版本关系标 CURRENT/STALE，逐项说明仍可引用或已失效部分；“部分过期”只是这些结果的组合展示，不另造生命周期。原书签不静默重绑，新位置须重新定位；无法恢复的游标从可核实位置重新读取，不能把翻到相似段落当作已恢复。恢复读取不恢复写入许可，后续改稿仍检查当前计划及批准。

已保存书签按项目记录保留，普通缓存清理不删除；删除书签只移除交接入口，不连带删除引用的稿件、证据、审核和修改记录。源工件保留/清理由第 19 节按引用策略单独处理。书签不会分配任务、签批准、更新当前基线或触发自动执行。

### 4.7 状态维度、审核政策与接力审核

| 维度 | 值 | 说明 |
|---|---|---|
| review_verdict | NOT_REVIEWED / PASS / FAIL / UNCERTAIN | 未复核、证据支持且范围内检查通过、明确错误、证据不足或无法可靠判断 |
| validity | CURRENT / STALE | 所依赖的源、规则、方法及范围对本次使用仍有效，或已失效 |
| approval_status | NOT_APPROVED / APPROVED / REVOKED / EXPIRED | 批准当前是否有效，不表达它是否已绑定执行 |
| bound_operation_id | operation_id 或 null | 批准绑定的唯一逻辑执行；绑定后不因失败、撤销或过期自动清空或改绑 |
| binding_state（派生） | UNBOUND / BOUND | 由 bound_operation_id 是否为空推导，仅供查询和展示，不维护第二份可独立修改的绑定状态 |

复核结论、有效性和批准状态与执行绑定分别记录，只用于适用对象或执行门，不要求每个 CacheEntry 都有批准。PASS 仅对应指定版本、检查项及覆盖范围；PASS + STALE + APPROVED 仍不可执行。已绑定操作 A 的批准可以同时为 REVOKED 或 EXPIRED：保留 A 的绑定与历史，不允许继续发布，也不允许转给操作 B。首次执行需原子绑定，恢复需匹配原绑定且批准仍有效，具体见第 4.10 节。

批准状态由可信签发、撤销记录和到期时间判定；同时已撤销且已过期时对外优先显示 REVOKED，并保留到期事实，不能因绑定而隐藏任何失效原因。NOT_APPROVED 表示没有针对当前计划的批准。历史判定保留，当前有效性按依赖重新判断；NOT_REVIEWED 与已完成但 UNCERTAIN 分开。导入初始 Baseline 或更新读取基线不把“当前稿件”自动写成“已验证全文”。

S2B 由用户安排人或外部 Agent 提交 Proposal、读取材料及提交 Review。产品负责材料、记录、确定性检查及政策校验，不启动、分派或管理执行/复核 Agent。审核者可以是用户、另一 Agent 或同一模型的另一个对话；来源不同不自动表示独立，独立取证方法与实际覆盖需另行说明。

审核政策只设两个项目选项，不建设通用策略编排器：

| 模式 | 语义审核与发布条件 | 不变的边界 |
|---|---|---|
| 用户控制（默认） | 提示风险并展示已有审核与未审核项；第二人/第二 Agent 审核不强制。用户明确查看并处置未审核或争议项、批准具体计划后，可在文件验证通过时发布；语义状态保留 NOT_REVIEWED、UNCERTAIN 或实际争议结论 | 不能把授权、文件验证通过或发布成功写成语义 PASS；不允许隐去既有 FAIL 或伪造证据 |
| 项目严格 | 用户预先选择高风险修改发布前必须有针对冻结计划及所需范围的有效语义 Review；相应项须为 PASS 且仍有效，缺失、未完成、UNCERTAIN 或 FAIL 时不得发布 | 只要求审核记录，不自动找人、不要求某品牌模型或固定 Agent 数量；适用范围内冲突未解决不能只取一个 PASS |

两种模式都不能绕过：能力与权限、源版本及目标前像、批准有效性/范围、保护对象与结构、实际差异、必需改后文件/页面验证、并发基线检查及零污染。确定性文件问题与语义意见分别归类，不得把技术失败改称“语义争议”后放行。未覆盖、定位不可靠或无法验证写回安全时仍拒绝相应操作。

用户控制模式下，作者选择继续使用有争议文字须留下针对该计划和已展示问题的处置，Review 原结论不改写，依赖证据不自动升级为事实。已有证据明确的事实捏造、违反作者已确认事实边界或其他既定硬合同不因模式变化获得豁免；硬合同违例应指明具体约束与证据，不能仅因某个 Agent 给出 FAIL 就冒充已证实的硬错误。需要改变边界时另行记录作者决定和依据。稿件可成为工作基线不等于科学结论或投稿合格已获认证。

审核政策及版本由可信用户入口设置，S2B 起纳入基线绑定、plan_hash 和批准范围，模型不能自行降级。政策变化后旧计划和批准不能沿用，重新核对审核适用性并取得新批准；设置变更不抹去历史审核或将失败改为通过。批准时与发布时核对所用政策一致；无需提前在 S1 实现这两个模式。

审核材料区分执行阶段：执行前提供源版本、修改前内容、冻结候选与计划差异、相关规则/证据、影响范围及已有检查；执行后增加真实 ArtifactVersion、实际内容和差异、ValidationResult 与操作记录。尚未生成实际产物时明确标为无产物，不能用候选冒充实际改后文件。原始证据与执行者修改理由分开提供；用户要求独立审核时可先取源证据及观察，再取候选和说明。产品记录实际获取范围，不仅凭提示词或自称独立就授予独立核验标签。

单候选的正式 Review 绑定 proposal_hash、源基线、依赖和检查范围；批次 Review 绑定 plan_hash 与 ordered_proposal_hashes，并检查组合影响；实际产物审核还须绑定被检查的 ArtifactVersion/内容哈希及对应计划。候选 Review 不直接代表实际产物已通过，产物与计划的一致性另由改后验证核实。保存提交主体/客户端、提交时间、审核类型/方法、实际读取记录引用、证据、范围、结论和限制；声明的模型元数据不冒充服务端认证。登记 Review 不自动证明科学正确，核心校验依据引用、版本、范围及记录完整性；缺少这些支持不得汇总为满足政策的 PASS，不把形式校验冒充科学判断正确。旧候选、旧产物的审核不得迁移为新版本审核，冲突意见同时保留供用户处理。

用户安排高风险审核或严格政策要求审核时，材料应可回到原始实验文件、代码版本、表格、文献原文或官方资料；只重读同一解析摘要不算重新取证。审核仍通过已验证适配器读取，不为“二次核验”临时编写低覆盖解析脚本。DOCX 结构与页面主要核验抽取和显示，实验数据核对主要核验数值来源，均不自动证明科学方法成立。实际开展审核但证据不足时记录 UNCERTAIN；根本未开展则保留 NOT_REVIEWED，不能由模型补齐事实。

风险下限由操作类型和确定性触发条件给出，模型和审核者可上调，不可下调强制等级；核心取适用等级中的最高值。数字、样本量、比较方向、否定、因果、显著性、适用范围、关键引用、研究问题及摘要/结论主张的变化标记为高风险，展示相关审核材料并按项目政策判断发布条件，不触发 Agent 调度。缺少证据不因未命中词库而降为低风险；能否安全执行文件操作先按能力与保护合同判断。

低风险且不涉及事实变化的候选可依照合同使用确定性检查，仍需版本、具体批准与改后验证。NOT_REVIEWED、UNCERTAIN 和争议分别显示在待处理列表，由用户决定继续审核、修改、拒绝或在政策允许时保留；不自动分派任务，也不阻断已证明无关的其他工作。文件合同的必需检查，以及严格政策要求的语义 Review，未满足时阻止相应发布。非阻断建议和无关既有问题可注明后保留。用户批准始终不把错误、不确定或未审核改成 PASS。

### 4.8 依赖失效、方向检查与批量确认

0.1 使用显式版本依赖，范围限于 ArtifactVersion 来源与读取/派生版本关联、读取覆盖、EvidenceItem 和人工/确定性核验记录的适用性；方法变化不改写或删除不可变源工件，而使依赖旧方法的结果失效。0.2 再扩展到 Proposal、候选 Review 及相关正文主张，每个候选至少记录依赖哪些 EvidenceItem、规则和源版本，影响哪些位置。纠正源值、解析器缺陷、能力范围内的计算/核验方法、适用范围或规则时，即使原始文件哈希未变，也按相关版本关系评估失效；不能只监听文件改动。

1. 依赖已知：沿受影响关系使已开放阶段内的证据与核验结果变为 STALE；0.2 再传播到候选、候选复核及相关主张，标出表格、摘要、结论等下游位置，不自动改写这些位置。
2. 依赖不完整：标记 impact_uncertain，将重查范围扩至能说明安全边界的表格、章节、实验或任务批次；不能据“没有记录依赖”就宣称独立。必要时扩大到全篇，并说明原因。
3. 可证明独立：保留已有工作及有效分析；不一律整篇作废。分析可复用不代表旧写回计划可复用，源版本变化后仍须重新定位、前像检查及批准。

S2B 提供轻量研究方向检查材料：将当前变更、依赖证据、已确认目标/边界、相关实验及摘要/结论并列展示，供用户或其安排的 Agent 判断是否越界；已有确定性规则自动运行，未做的语义检查标为 NOT_REVIEWED。实际审核时记录结论、依据与覆盖，并按第 4.7 节处置，不宣称完成全篇科学审查。完整主张图谱与全部章节依赖后置，专业 Agent 如何安排不在产品路线内。

人工主要负责确认目标与证据边界、批量处置争议和高风险不确定项、批准具体修改批次及最终交付版本。批量批准须显示每个候选、合并影响、顺序及依赖，并绑定完整计划；不能批准“后续全部润色”。同一批次内部预先声明的步骤和中间版本不反复索取批准，临时增项或改变候选、范围、源基线、绑定规则则重建计划并重新批准。

独立源证据取证可以与候选生成并行；针对 Proposal 的正式复核只能在候选内容、依赖与 proposal_hash 冻结后开始。冻结不禁止继续编辑，但编辑必须产生新版本 B；针对 A 的 Review 不能自动覆盖 B。仍有效的源证据检查可显式复用，对 B 的差异及受影响范围另行检查，不能沿用旧候选的通过标签。

用户安排的不同冻结候选审核可以并行提交，核心只串行提交已合并、已批准且满足政策的批次，不负责启动审核任务。重叠候选先解决冲突，按执行顺序形成 ordered_proposal_hashes，并将组合方式、共同影响、审核政策版本和验证要求纳入 plan_hash；适用的批次 Review 与批准绑定这两项。无论是否安排语义审核，都必须检查整批文件影响；单项语义 PASS 不代表整批语义已审核。用户选择子集、调换顺序或修改组合方式时冻结新计划，重查受影响范围并按政策补充审核、重新批准；即使所有单项 proposal_hash 未变，旧 plan_hash 的批准仍无效。旧基线上的分析可按依赖复用，但旧授权不能迁移到新基线；同计划、同来源的安全恢复按第 4.10 节执行。

### 4.9 改后验证与条件式基线发布

~~~
绑定源 Baseline 和批准计划
→ 内部副本执行
→ 重新读取实际产物与差异
→ 结构及允许变化检查
→ 实际内容与批准计划对照，记录事实影响与适用的语义审核状态
→ 同渲染器页面检查及文件风险处置
→ 持久保存不可变候选 ArtifactVersion 与 ValidationResult
→ 在提交边界原子校验基线、依赖、候选/检查绑定、审核政策与批准有效性
→ 成功分支同一事务创建 Baseline、更新当前指针、保存 PublicationRecord 与最终 ChangeResult
→ 用户另行选择交付
~~~

计划检查通过不代替改后检查。生成的产物先使用 ArtifactVersion 登记，对指定产物完成检查后生成 ValidationResult；它证明检查实际发生过，不预告发布成功。产物“已核验待发布”也不是当前基线。执行或验证明确失败且操作决定终止时，分别记 FAILED 或 VALIDATION_FAILED 并生成最终失败 ChangeResult；仍可恢复的尝试失败只记录尝试，不能提前封死逻辑操作。诊断产物留在应用内部，不经修改发布自动成为当前稿件；用户另行明确导入为读取输入的例外仅按第 4.11 节处理，不转成已核验修改。

“文件验证通过”指本次合同必需的文件检查和允许变化核验完成，不等于语义审核 PASS、整篇研究无误或页面没有像素差异。预期重排和抗锯齿沿用第 10.3 节；结构破坏、必需文件检查 FAIL/未完成/UNCERTAIN、执行所需依赖 STALE 或批准失效均阻止发布。语义审核按第 4.7 节政策单独判断：用户控制模式可保留已明确展示和处置的未审核/争议状态；严格模式的必需 Review 未满足则不得发布。不得把审核证据缺失伪装成已有支持，也不得把计划所依赖证据的版本失效降为普通提醒。

严格模式尚待用户安排审核时，可保留已授权生成的内部候选及已有验证记录，在原有 VALIDATING 阶段记录缺少的审核项；“待审核”是列表视图，不另建执行状态。不自动召集 Agent、不提前标 READY_TO_PUBLISH，也不因暂缺记录就伪造最终失败。只有满足必需条件才继续发布；用户明确终止或实际发布请求被确定拒绝时沿用下述终态合同。已发布版本的后续审核只新增记录和问题，不改写历史结果或自动回滚；需要再改时建立新计划。

提交必须在存储层原子验证 current_baseline == task.source_baseline，并在同一提交边界校验适用依赖版本、approval_status、bound_operation_id、plan_hash 与 ordered_proposal_hashes 的一致性、审核政策版本、实际产物哈希及必需文件检查/适用审核条件；不能先读取比较、稍后无条件改指针。核心是唯一发布者，源基线使用不可复用的版本标识。版本化产物和检查记录先持久化；成功分支的新 Baseline、当前指针、SUCCEEDED PublicationRecord、最终成功 ChangeResult 及操作终态必须一致提交。昂贵的渲染与检查在事务外完成，提交时校验其具体输入、结果与有效性，不能把这些实际检查跳过。

发布结果分支必须明确：

- 成功：按上述原子边界一起提交，最终结果引用已发布基线与产物。响应丢失后仍返回这份原结果。
- 确定的基线冲突、批准失效或依赖/检查不合格：不创建新基线、不改当前指针；在不执行发布的事务分支持久记录 CONFLICT 或 REJECTED PublicationRecord、拒绝依据和最终 REJECTED ChangeResult。业务拒绝不通过回滚丢弃整份拒绝记录。
- 尚未尝试发布就终结的执行失败、验证失败或取消：保存实际发生的尝试与检查证据及最终失败/取消 ChangeResult，PublicationRecord 引用为空，不伪造一次发布尝试。
- 可恢复的临时故障：只保存尝试结果；确认未提交且仍可安全恢复时进入 RETRY_PENDING。提交是否发生不能确定时进入 UNKNOWN / RECONCILING，不提前生成最终 ChangeResult。若事务或存储故障使记录未能持久化，不能声称“拒绝已记账”或“发布未发生”，必须先查明。

ChangeResult 对每个逻辑操作只生成一次最终不可变结果。其 candidate_artifact_version 可指向实际存在的诊断产物；未生成产物或未完成检查时对应引用为空，保留实际尝试与失败原因，不虚构 ArtifactVersion 或 ValidationResult。published_baseline_id 和成功的 result_version 仅在 PUBLISHED 时有值，其余终态为空，避免把失败候选当作已发布稿件。PublicationRecord 与 ValidationResult 用引用关联，不把整个状态过程反复覆盖到同一个最终结果里。

例如两个任务都基于 V12，先完成者发布 V13，后完成者不能覆盖 V13。后者保留候选和核验材料，比较新旧基线后评估依赖、重新定位和检查，形成绑定新基线的计划并重新批准；不能用“最后写入者获胜”，也不因分析仍可复用就沿用旧写权限。

本节是 0.2 的修改产物发布合同；0.1 的首次导入和后续读取基线更新按第 4.11 节执行，不要求改稿 Proposal / Approval。两种入口都建立不可变清单并检查版本冲突，但读取基线更新不授予“改稿已核验”身份，也不能绕过本节的修改发布合同。内部发布不覆盖作者原稿，也不等于外部导出。

### 4.10 逻辑执行标识、幂等与恢复

operation_type 标识操作类别或能力，contract_version 标识合同版本；operation_id 唯一标识一次逻辑执行，execution_attempt 区分该执行中的尝试，不能把合同 ID 与执行 ID 混用。以下摘要字段各有唯一含义：

| 字段 | 固定含义与绑定对象 |
|---|---|
| proposal_hash | 一个冻结候选的源定位/前像、候选内容、依据与依赖、规则版本和影响范围摘要；单候选 Review 绑定该值，不表示批次计划 |
| ordered_proposal_hashes | 按执行顺序排列的候选哈希列表；保留数组顺序，不排序成集合；批次复核和批准必须能展开到每个冻结候选 |
| plan_hash | 完整执行计划摘要，覆盖源基线、有序候选列表、操作类型/参数/合同、组合方式及依赖顺序、共同影响和保护范围、规则/证据依赖、审核政策版本及验证要求；批次 Review、Approval、operation_id 绑定该值 |
| request_digest | 同一 operation_id 下用于识别请求内容冲突的规范化请求摘要，覆盖项目/权限作用域、operation_type、contract_version、source_baseline、plan_hash、approval_id 及其他影响执行语义的参数；不代替任何授权校验 |

即使只有一个候选，也生成含单项 ordered_proposal_hashes 的计划和独立 plan_hash，不能用 proposal_hash 代替。计划不包含自身哈希、最终批准或运行结果，避免循环引用；候选集合、顺序、组合方式、审核政策或验证要求变化须形成新 plan_hash，重查受影响范围、按政策补充适用审核并重新批准。

摘要由核心服务根据规范化内容计算或复核，不信任客户端自报哈希。阶段 0 的最小 schema 固定各摘要的字段边界、算法/规范化版本、字符编码和空值处理，并用固定向量测试；语义有序列表不得重排。request_digest 不包含 execution_attempt、传输时间、跟踪 ID 等非业务重试元数据或秘密认证凭据，普通重试不因这些信息变化产生冲突；实际执行参数变化则必须被识别。实时身份与当前请求的访问权限每次校验；开始、恢复执行及发布再检查当时的批准有效性和适用环境条件。已有最终结果的查询不因原执行批准后来失效或环境改变而改判失败，仍按后述顺序返回历史结果；摘要相等不代替任何适用检查。

逻辑执行记录持久绑定 task_id、plan_hash、ordered_proposal_hashes、approval_id、source_baseline、request_digest、execution_status、last_known_phase、side_effect_status、候选/检查/发布及最终结果引用；每次 execution_attempt 与对账记录关联同一 operation_id，不作为可清理调试日志。result_version 只表示成功发布的产物版本，另记 published_baseline_id；诊断候选使用 candidate_artifact_version，不与成功结果混用。

处理顺序如下，访问检查始终适用：

1. 核对 operation_id 与已登记的 request_digest 及其规范化请求。相同 ID 携带不同 plan_hash、来源、范围、批准引用或执行参数时返回 idempotency_conflict，不执行；不得仅比较候选 proposal_hash 而忽略批次顺序或组合变化。
2. 相同请求已有最终 ChangeResult 时优先返回原结果，不论其为成功还是终结失败、拒绝或取消，都不重新执行。成功结果即使在当前基线随后推进、批准随后撤销或过期后仍可查询；明确它是历史结果，不宣称仍为当前稿件。
3. 正在执行时返回既有进度，不启动第二个同 ID 执行；UNKNOWN 请求先进入 RECONCILING，核对持久记录、真实产物与提交账目。不能仅因超时就判断失败重跑，也不能在对账中覆盖已确认的终态。
4. 仅本次尝试失败/中断、逻辑操作尚未终结，且已证明未发布并可安全恢复时，重新核对来源、计划、证据和仍有效的批准及原执行绑定，再增加 execution_attempt，只续做必要步骤。不能向已打补丁的副本重复应用，也不能猜测上次是否提交。
5. 请求或源基线变化则建立新计划、新 operation_id 和新批准；已有最终失败结果后决定再次执行，也必须使用新 operation_id 并重新批准，不能重开原终态或复用原批准绑定。检查点说明从哪继续，幂等机制保证不产生重复效果，两者不互相替代。

首次应用前，在同一持久提交边界校验批准当前有效、计划及版本匹配，并把空的 bound_operation_id 原子绑定到本次 operation_id，同时登记执行身份；不能先绑定、后遗漏执行记录。重复绑定同一操作按幂等处理，绑定其他操作则拒绝。绑定不改变 approval_status，binding_state 从空/非空推导。

绑定后不自动释放或改绑，包括尝试失败、操作终止、批准撤销或过期。仍在有效期且未撤销的原批准只支持同一未终结逻辑操作的安全恢复；开始、恢复和发布都要检查原绑定及批准有效性。撤销/过期阻止未完成的执行与发布，不抹去既有绑定和历史成功记录。提交成功但响应丢失时返回原结果，不要求作者再次批准再改一遍。

### 4.11 读取基线更新（0.1 起）

读取基线更新（rebaseline / import binding）是独立于第 4.9 节修改产物发布的管理操作。用户通过可信桌面入口重新导入外部更新后的稿件，或修正研究目标、作者边界及已有规则版本的绑定元数据；核心服务只管理输入版本和读取状态，不修改任何稿件。模型可以提出建议，但不能通过文档指令或普通候选接口自行切换基线。v1.3 修订：本地单操作员工况下，与操作者共享同一进程令牌的本地 MCP 面视同可信桌面入口，可执行本节读取基线更新；该路径仍受同事务 expected_baseline 比较交换约束，保留的确认依据注明驱动面（browser、mcp 或 cli）构成审计记录，且本修订不授权就地修改稿件字节或发布作者决定。

1. 展示将替换的基线、源文件版本和目标/绑定差异，由可信用户确认本次具体管理动作；保留身份、时间、请求标识和决定依据，不要求 0.2 的改稿 Proposal 或可执行 Approval。
2. 源文件确有更新时只读保存新的 ArtifactVersion，重新建立本阶段支持的结构、页面、覆盖与证据；仅目标或绑定变更时引用已有工件版本，不伪造一份修改稿。
3. 生成新的不可变 Baseline 清单和来源标记。首次导入条件为当前无基线；后续更新在同一事务核对 expected_baseline 与当前指针，提交新清单、指针、管理审计与失效依据。冲突时不覆盖，显示新差异后由用户重新确认。
4. 更新后按新来源与方法判断证据有效性，必要时重新读取。失效标记可按需物化，但读取入口必须立即按新版本判断，不得在后台传播期间把旧 PASS 当作新基线的通过。0.1 仅作用于读取证据和核验范围；0.2 还使相关候选、复核和旧源绑定的写回计划失效。
5. 同一请求标识及相同内容重复提交只返回原管理结果，不重复切换基线；同标识不同内容拒绝。结果不明时先按持久管理记录对账，不需要引入 0.2 的改稿 ChangeResult 或写回能力。

0.1 允许管理已有规则版本的引用，不提前执行模板提取、规则发布或期刊合规检查；作者填写的研究边界是可追溯决定，不自动成为已验证科学事实。导入/更新成功也不等于读取完整、事实正确或投稿合格，未核验与未覆盖状态继续显示。

S2B 的审核政策设置/变更复用本节可信管理入口：保留用户决定、政策版本及新基线绑定，复用稿件原件，不伪造一次改稿。作者决定改变当前项目要求时也复用本入口，只在对应阶段开放的作用域内操作。切换按相同并发与幂等规则处理，旧源基线/政策绑定的计划和批准失效；单纯修改设置不能重开已终结操作、清除争议或把旧审核提升为新计划的通过。

内部失败候选不能借重新导入获得“已核验修改产物”身份。未经可信用户明确导入时，当前读取基线和已发布结果均保持不变；用户明确确认作为新读取输入时，可按本节切换当前读取基线，但仍标记导入来源与实际核验状态，保留已知候选/失败来源和历史记录，不登记为成功修改发布，其相同哈希不消除已有失败证据。两种情况都不得自动导出、覆盖作者文件、复用或改绑旧 Approval、清除原失败记录。

### 4.12 修改预检（S2B）

change.preflight 针对已有冻结计划，只读判断当前支持范围、定位及前置条件；具备相应读取/预检权限即可调用，不要求已经获得修改批准。它不应用补丁、不生成试改稿/PDF、不调用会改文件的宿主、不刷新域、不发布、不导出，也不创建或占用改稿 operation_id/批准执行绑定。可按既有权限写应用内部的读取、缓存与预检记录，须在结果中说明；“无稿件副作用”不宣称完全不写磁盘。

预检绑定源 Baseline、plan_hash、有序候选、合同/适配器和检查方法版本、检查时间，逐项列明：

- 操作是否属于当前已验证能力；目标是否可靠定位，源版本、前像和上下文是否匹配。
- 是否跨公式、域、引用、修订、超链接、内容控件等保护范围，整批差异与组合是否符合合同。
- 必要程序、许可、字体与环境是否可只读确认；无法安全探测的条件标未核验，不为预检启动实际渲染或修改原件。
- 所需审核政策、当前 Review/批准状态与尚缺条件；无批准只说明不能立即执行，不妨碍完成其他可做的检查。
- 改后必须运行的结构、差异、页面等验证器及当前可用性；未生成产物不能报告这些检查已经通过。

结果分别说明逐项可支持/不支持/未能确认、整批是否存在技术阻断、审核/批准等尚缺条件、检查覆盖与限制，并明确稿件是否修改、候选产物是否生成、绑定是否变化及实际内部记录写入。不能只返回一个容易被当作授权的“通过”。

例如六项里五项符合文字补丁条件、一项跨引用域，应报告整批当前不可执行且未修改任何稿件，不自动应用可行子集。用户或其安排的 Agent 可提出五项的新计划，但须新 plan_hash、重新检查及取得对应批准，不沿用原批次授权。

预检是指定时点的检查记录，不是执行保证、许可或改后验证。正式应用与发布仍分别重新核对当前源/目标前像、依赖、计划、权限、审核政策、批准和环境；其间发生变化不能靠旧预检放行。重复预检也不算重复改稿，更不能触发一次写入。正式执行可复用同一套校验实现，但不能省略执行时校验或依赖一张过期预检报告。

“试改预览”若未来开放，是在内部副本实际修改并渲染的写操作，必须单独声明能力、取得具体授权并保留候选及验证记录，默认不发布；本次 v1.2 不把它加成 S2B 新交付项。S1 已有的原稿只读页面预览不属于试改，不能借用该入口执行修改。

## 5. Word 链路技术合同

本节只具体化 DOCX 适配器；全格式的批准、版本、审核政策与记录、发布及隔离以第 4 节为准。5.1、5.2、5.7、5.8 是 0.1 的读取合同；5.3—5.5 是 0.2 的 DOCX 文本替换合同；5.6 区分基线与独立刷新；5.9 列出 DOCX 执行前的专用核验。后续格式、对象和结构操作采用第 12.6 节的独立合同，不扩大或放宽文字补丁的已有保证。所有副本和输出遵守第 19 节。

### 5.1 读取

DOCX 作为 OOXML 压缩包整包只读打开。先建立完整部件清单，再按部件和区域解析；“整包枚举完成”不等于“每个对象都已理解”。

需要单独识别：

- 正文。
- 脚注和尾注。
- 页眉和页脚。
- 文本框。
- 普通文本。
- OMML 公式。
- 域指令。
- 域结果。
- Zotero 域。
- 超链接。
- 修订和批注。
- 书签和交叉引用。
- 图片、图表、表格和题注。

布局与格式需要单独记录，不藏在文本摘要里：

- 分节、纸张、方向、页边距、分栏、显式分页与分栏符。
- 段落及字符样式、直接格式、默认值、继承链和主题字体引用。
- 缩进、间距、对齐、编号、制表位和段落分页约束。
- 表格网格、合并单元格、列宽、重复表头和跨页显示。
- 图片及绘图对象的嵌入关系、尺寸、锚点、环绕方式和叠放关系。
- 公式源结构及其页面外观；内嵌图表、OLE 等对象的资源关系和可用预览。

每项属性分别标记“源文件显式声明”“继承计算结果”“渲染观测”或“未确认”。计算结果必须保留来源链；无法解析继承关系时不得凭默认值补成已确认格式。

读取结果遵守以下边界：

- XML 顺序只作为源结构顺序，不直接宣称是双栏、浮动对象或文本框的视觉阅读顺序。
- 提取到图片不等于理解图中数据；看到公式外观不等于成功解析公式；读取题注不等于读懂表格。
- 表格等对象允许跨页；页眉等对象允许重复出现。对象到页面采用可表达多对多的关联，不强制一对象一坐标。
- OCR、视觉模型或启发式推断只能补充有标识的证据，不能覆盖源结构或伪装成精确解析。
- 未知命名空间、未处理部件、损坏关系、嵌入对象和外部依赖全部进入覆盖报告。外部资源不自动联网取回或执行；缺失依赖保持未解决状态。
- 不支持的内容必须保留原始位置与关系；能渲染时提供外观，不能渲染时说明缺口。不得把未提取到对象解释为源文件没有该对象。

python-docx 只允许用于“文件能否打开”的兼容性测试，不参与解析结果，也不参与生产写回。

OfficeCLI（iOfficeAI/OfficeCLI）同等待遇：它的 resident save 是整体序列化，无法满足 5.4 的字节合同，且有打开失败时自动重写 XML 编码声明的默认行为。它只用作独立的交叉验证和 schema 校验（validate 命令），不进解析结果、不进生产写回、不替代 Word/WPS 导出 PDF。

### 5.2 文档节点索引

每个对象至少记录以下信息；读取状态不等同于写入授权：

~~~
source_hash       源文件哈希
session_id        本次读取会话
part              OOXML 部件路径
region            body / footnote / endnote / header / footer / textbox 等
node_path         当前 XML 路径
node_id           本次解析到写回有效的临时编号
kind              text / formula / field-code / field-result / drawing / table 等
parent_relations  父对象、资源及引用关系
parse_status      parsed / partial / unsupported / failed
format_evidence   声明值、继承结果、页面观测及其来源
page_refs         零个或多个页面/区域关联及关联依据
mapping_status    verified / candidate / ambiguous / unmapped
limitations       尚未读取、解析或确认的部分
protected_reason  受保护原因；可读不代表可写
editable          0.1 恒为 false；0.2 判定后仍须作者批准
structure_hash    忽略批准可编辑文字后的结构指纹（写回阶段使用）
preimage_hash     修改前文字和上下文指纹（写回阶段使用）
~~~

坐标必须带对应 PDF 哈希、页号、坐标系及生成环境。无法可靠得到坐标时允许只关联页面或保留空列表，不填猜测坐标。源文件或渲染环境改变后重新生成关联，旧 PDF 的页号不能继续引用。

OOXML 没有跨次编辑仍稳定的文本节点 ID。node_id 只在本次解析到本次写回之间有效。

写回前必须重新检查：

- 文档结构没有变化。
- 目标节点的前像文字没有变化。
- 目标节点仍位于相同区域。
- 批准的修改计划没有过期。

任意一项不一致，整份修改计划作废。

### 5.3 可写节点

本节只适用于 0.2。0.1 的统一读取接口不提供任何写入操作。

通过保护检查且经作者批准后，自动写入只允许正文中的单个 w:t。

多个 w:t 只有在以下条件同时成立时才允许受控分配：

- 位于同一正文区域。
- 每个 w:rPr 规范化后完全相同。
- 中间没有公式、域、修订、超链接、书签、批注范围或内容控件。
- 不新增、不删除、不合并 w:r。
- 按固定规则分配，不允许模型临时决定。

固定分配规则：

1. 按 Unicode grapheme cluster 计算长度。
2. 前面的节点保持原字符数。
3. 长度差只落在最后一个节点。
4. 任一节点会变成空节点时拒绝。
5. xml:space="preserve" 必须保留。
6. 换行和制表符不能写进 w:t。

以下区域一律不可自动写入：

- m:oMath 和 m:oMathPara 内部。
- w:instrText。
- 域结果区域。
- Zotero 引用域和 Zotero 参考文献域。
- 已有的 w:ins 和 w:del。
- 超链接、内容控件和文本框中的任何 w:t。
- 公式、图片、图表、表格结构。

**命中到落点的对齐。**

规则命中的是逻辑文本（一句话或一个短语），落点必须落到具体的 w:t。解析时按区域把相邻 w:r 的文字拼成连续文本流，命中位置对齐到物理 run 序列，然后分三种情况：

1. 命中完整落在单个 w:t 内，通过保护检查和作者批准后执行单节点写回。
2. 命中跨越多个 w:t，只有满足上面的受控分配条件才执行；因空节点规则被拒绝的修改不静默丢弃，降级为“无法自动修改”。
3. 对齐后无法满足条件的（run 碎片化且 rPr 各异是真实稿件的常态），一律标记为“无法自动修改”，只报告命中位置和原因，由作者手工修改。

0.2 不合并 w:r，不重排 run。报告必须统计“因碎片化无法自动修改”的比例，分母为已批准的候选修改；这是写回可执行率指标，不是 0.1 的读取覆盖率。受控合并（rPr 规范化后相同的相邻 run 允许合并）列为后续可选改进，采用前需要先修订结构不变量。

### 5.4 写回

文字写回只在应用内部的原稿副本上进行，不在作者项目目录旁边创建工作稿或备份：

~~~
原始稿件
  -> 绑定只读源基线、证据版本和批准计划
  -> 在应用任务目录复制为工作副本
  -> 替换批准的 w:t
  -> 保存为待验证内部版本
  -> 重读实际产物，核对字节差异、结构、事实与研究边界
  -> 同环境改后页面检查，区分预期重排与风险
  -> 保存产物哈希及对应 ValidationResult
  -> 必需检查通过后，按第 4.9 节原子核验并发布新基线
  -> 用户明确选择时才导出
~~~

原稿不得覆盖、移动或重命名。内部产物通过核验但未完成条件式发布时，不得替换当前基线；失败、冲突和重试依第 4.9—4.10 节保留真实状态。

修改后的 XML 部件允许变化，但只能有批准的 w:t 文本值变化。未修改部件按原始压缩字节拷贝，不重新压缩。

注意：

- 校验未修改部件时比较部件自身，不比较整个 ZIP 文件哈希。
- ZIP 中央目录的偏移量变化不能被误判成内容变化。
- 未修改部件的压缩方法、CRC、大小、顺序和元数据必须从原始 ZIP 条目复制。

实现方式：

写回禁止“DOM 解析后整体重新序列化”——属性顺序、空白、自闭合写法和 XML 声明都会被序列化器改动，无法满足“只有批准的 w:t 文本值变化”。写回在原始部件字节流上进行：

1. 在原始 XML 字节中定位目标 w:t 元素的文本区段。
2. 对新文本做 XML 转义（& < > 及必要的字符引用）后替换该字节区段。
3. 原有实体和字符引用保持原样，不重写。
4. preimage_hash 以解码后的节点文本加相邻原始字节计算，写回前重算并比较。
5. 写回后对修改部件做字节级 diff，diff 结果必须等于批准的变更集合；不等则整份副本作废。

### 5.5 结构不变量

主要保证在 5.4：修改部件的字节级 diff 必须等于批准的变更集合，未修改部件逐字节原样保留。下面的数量核对只是第二道报警，挡不住“数量不变但内容被改”的缺陷。

写回后必须核对：

- 公式数量。
- 图片数量。
- 图表数量。
- 表格数量。
- 书签数量。
- 域和 Zotero 字段数量。
- 样式数量。
- 编号定义数量。
- 文档关系数量。
- 页眉、页脚、脚注和尾注数量。

只有批准的文字节点可以变化。

### 5.6 域刷新

0.1 基线采用 none：不主动刷新目录、编号、交叉引用或 Zotero 域，读取并记录当前域结果。必须记录渲染时实际发生的域行为；不能保证原样显示时标为未核验，不把自动重算后的结果冒充源文件已保存结果。

0.2 的独立刷新任务只允许刷新明确列入白名单的 Word 原生域：

- 目录。
- REF。
- PAGEREF。
- 页码。
- SEQ。
- 其他明确配置的 Word 原生域。

Zotero 引用不走 Word 域刷新，继续只读。

域刷新策略独立设置：

~~~
none
prompt
refresh-and-record
~~~

refresh-and-record 只能作用于 render-copy，禁止作用于生产副本或源文件副本，也不用于替换 0.1 的只读观察基线。刷新产生的域结果只进入另行标识的 PDF 和渲染报告，不反写生产稿。刷新输出与 none 基线分别留存。

如果以后调用 Zotero 插件刷新，必须作为独立写事务，并在报告中记录：

- Zotero 插件版本。
- CSL 文件和版本。
- 刷新前后文档指纹。
- 引用域数量。
- 参考文献条目数量。
- 是否触发了新的结构变化。

### 5.7 Word/WPS PDF 导出

Word 或 WPS 提供实际排版的 PDF 证据，不负责产品内部解析和写回；0.1 的输入是只读源文件，0.2 改后导出的输入才是生产副本。

导出必须使用临时渲染副本：

render-copy、PDF 和页面图像全部位于应用内部任务目录，不使用原稿所在目录作为工作目录。这里的“导出 PDF”指渲染产物；写到用户目录的交付导出是第 19.4 节的独立动作。

~~~
只读源文件（0.1）或已核验的生产副本（0.2）
  -> render-copy
  -> Word 或 WPS 打开
  -> 按已记录策略处理域与修订显示
  -> ExportAsFixedFormat
  -> 输出 PDF
  -> 丢弃 render-copy
~~~

Word 和 WPS 是两个独立渲染器，不能混合比较。

复核报告记录：

- 渲染器名称。
- 渲染器版本。
- 操作系统。
- 字体清单。
- 缺失字体、已知字体替换和无法核实的环境差异。
- 导出方法。
- 域刷新策略。
- 修订、批注、隐藏内容的显示状态。
- 输入文件哈希、输出 PDF 哈希及源文件/副本对应关系。
- 导出时间。

产品自己的 OOXML 写回不能修改 docProps。Word 或 WPS 打开的文件发生的属性变化不能反写回生产副本。

不关闭或退出用户已有的 Word/WPS 进程，不操作用户正在编辑的原稿。导出失败、缺少渲染器或字体条件不足时可以保留结构结果，但任务状态必须是部分完成/待复核，不能显示“排版正常”。PDF 只证明已记录环境下的显示效果，不能保证与作者另一台机器上的页面一致。

### 5.8 模型统一读取入口与覆盖报告

模型不靠临时脚本拼出“全文”，而是通过受控服务按需获取证据。接口名称留待实现，至少提供以下能力：

- 打开文档快照：返回源哈希、会话、部件清单、覆盖摘要及限制。
- 读取区域与对象：返回结构化内容、受保护边界、格式来源和资源关系。
- 读取页面证据：返回与当前快照绑定的页面图像、可用文本层及关联对象。
- 查询对象关联：返回结构位置与页面位置，以及 verified / candidate / ambiguous / unmapped 状态。
- 查询覆盖：按部件、区域、对象类型列出解析与渲染情况；列出未处理、未知和待人工核验项。

长内容必须分页，返回实际范围、总量或总量未知、是否截断、下一页游标。模型取过摘要不等于读过全文；记录模型实际获取的区域与页面证据，并提示尚未获取的范围。获取记录也不宣称模型已经正确理解内容。

覆盖报告分开呈现三件事：服务解析了什么、页面关联核验了什么、模型实际取到了什么。不使用一个“完整度 100%”分数混合代替。覆盖分母来自部件清单和独立标注样本，不允许只用解析器成功返回的对象自证无遗漏。

DOCX 读取也执行第 4.3 节的访问边界，0.1 至少验证一条受控接入路径；未具备隔离条件的宿主必须明确标识，不能把规范接口视为强制隔离。

### 5.9 DOCX 执行前的专用核验

实际应用修改时，先通过第 4.4 节的全局批准校验，再核对 DOCX 源快照、部件指纹、node_id 的本次会话有效性、文字前像及上下文、受保护区域和第 5.3 节的可写条件。不得因为存在有效批准就略过公式、域、超链接、内容控件或文本框保护。

文字替换只调用本节的字节级补丁路径；格式、对象或结构操作不得伪装成文字替换取得执行权限，未实现时按第 4.5 节拒绝。应用和验证均在内部副本上进行，是否交付另由第 19.4 节决定。S2B 的 change.preflight 可在尚无修改批准时只读检查相同目标与保护条件，报告尚缺授权；它不是本节执行入口，实际应用仍重新校验所有前置条件，不能持预检结果直接跳过批准。

## 6. LaTeX 链路技术合同

本节为后续独立链路，按第 15 节阶段 4 实现，不纳入 DOCX 读取首版或 Word 0.2 验收。已有源文件保护和模板编译约束继续保留。

### 6.1 读取

LaTeX 源文件就是原稿，不能从 PDF 反推源文件。

读取：

- .tex
- .bib
- \input
- \include
- \subfile
- 图片路径
- 模板和类文件

递归建立源文件依赖图，并检测循环引用和缺失文件。

### 6.2 默认保护范围

默认不修改：

- 注释。
- 数学环境。
- \cite。
- \ref。
- \pageref。
- \label。
- 图片路径。
- \input 和 \include 路径。
- \bibliography 和 \addbibresource 路径。
- \graphicspath。
- 宏定义。
- verbatim、lstlisting 等代码环境。
- .bib 条目键。

文字修改只能发生在明确识别的普通文本区域，不能跨越命令、数学环境或受保护路径。

### 6.3 编译

编译器由期刊模板决定：

- 模板要求 pdfLaTeX，就使用 pdfLaTeX。
- 模板要求 XeLaTeX，就使用 XeLaTeX。
- 模板要求 LuaLaTeX，就使用 LuaLaTeX。
- 模板使用 BibTeX，就使用 BibTeX。
- 模板使用 Biber，就使用 Biber。

latexmk 只作为构建编排器，按模板配置执行需要的编译轮数，不能把某一套引擎写成唯一通路。

LaTeX PDF 和 Word/WPS PDF 分开存储、分开复核，不做跨格式像素比较。

编译在应用内部任务目录的依赖副本上进行，日志、辅助文件、参考文献中间结果和生成图片不得回落作者目录。依赖保留必要相对关系；外部绝对路径和需执行的脚本先登记及授权。不能满足隔离时拒绝该编译任务，不直接改用原稿目录执行。编译失败的中间结果不视为成功交付。

## 7. Zotero、CSL 和参考文献

0.1 只识别和保护 DOCX 内的引用域、参考文献域及相关内容，不要求接入 Zotero 数据库或完成 CSL 核验。本节的外部库与样本管理按阶段 3 交付。

### 7.1 Zotero 的三种用途

Zotero 在产品中不只是参考文献管理器：

1. 维护参考文献条目。
2. 保存目标期刊已发表论文样本。
3. 保存作者历史稿件和已确认表达样本。

样本建议通过集合、标签和元数据区分：

~~~
journal-sample
author-corpus
reference-only
accepted-version
~~~

产品默认只读 Zotero 数据库，不直接修改 SQLite。

### 7.2 CSL

- Zotero 条目负责文献元数据。
- CSL 负责 Word/citeproc 中的引用和参考文献成文格式。
- LaTeX 通常由 BibTeX/BibLaTeX 样式负责最终排版。
- 产品保存引用对象和条目键，不把 Zotero 动态引用转成普通文本。
- Word 与 LaTeX 不承诺字节级相同，只要求引用对象、顺序、作者、年份、DOI 和条目集合一致。

## 8. 图表和实验资产

图件必须区分源文件和投稿文件。

0.1 必须登记 DOCX 内部图表对象、嵌入资源、题注关系和页面外观；本节的外部脚本、数据和图件资产管理后置到阶段 3。外部图件未登记不允许成为漏读稿内图表的理由。

### 8.1 Python 图

保存：

- Python 脚本。
- 数据文件。
- 环境和依赖版本。
- 输出的 PDF 或 SVG。
- 必要的 PNG 预览。
- 图尺寸、字体、线宽和导出参数。

正文只引用投稿文件，产品同时检查源文件和投稿文件的映射关系。

### 8.2 draw.io 图

保存：

- .drawio 源文件。
- 导出的 SVG 或 PDF。
- 导出时间和版本。

正文检查图是否被引用、题注是否一致、正文名称是否一致。

### 8.3 Origin 图

Origin 首期登记工程原件、数据与导出图之间的映射，检查已有投稿文件；后续可评估通过宿主应用接口执行受控数据和图件操作，不承诺未验证的完整工程解析能力。宿主、许可、版本或隔离条件不满足时明确不支持，不临时手改专有工程或静默切换工具。

无论人工提供还是后续受控导出，均检查投稿文件：

- 分辨率。
- 页面宽度。
- 字体是否嵌入或可用。
- 颜色和线宽。
- 文件格式。
- 与正文题注和图号是否对应。

### 8.4 图件适配器的共同约束

SVG、draw.io、Python 和 Origin 分别登记可读、可改、可导出的能力，不用最终截图替代可编辑源文件。外部脚本或图件内嵌内容不自动执行；只有批准的任务和参数可进入隔离工作目录。所有导出和检查产物先入应用内部存储，再由作者选择交付位置，不能污染图件源目录。

## 9. 学术表达检查

本节从 0.2 起生效，不是 0.1 的交付目标。“去 AI 味”是事实约束下表达检查的可能结果，不设检测分数。读取证据不足时先报告读取缺口，不对不可见内容生成改写建议。

### 9.1 不生成新事实

用户使用的 Agent 可以基于原文中已经出现的事实提出目标期刊句式，产品提供规则、证据和候选检查入口，不内置自动改写 Agent。候选不得无依据新增：

- 数字。
- 比较对象。
- 实验结果。
- 统计显著性。
- 研究范围。
- 因果关系。
- 新的文献结论。

候选改写只能作为审阅材料，不能直接写入文档。Agent 提交具体计划，产品完成前置文件检查、展示差异、风险、审核状态及影响，作者按第 4.7 节政策处置并批准；核心校验计划、版本与保护范围后，才可写回批准的 w:t。缺少支撑新事实的证据时只标缺口并建议作者补充或删除，不由产品或 Agent 补造结果。审核是否必需与文件是否可安全写入分别判断。

缺证据的空话只能：

- 标记问题。
- 说明缺少什么事实。
- 建议作者补充或删除。

不能自动编造新的结果句。

### 9.2 第一批表达规则

1. 一个对象使用一个规范名称。
2. 以证据台账中已确认的事实为准。
3. 摘要结构暂不设为目标期刊硬规则；在期刊样本完成前，只检查事实完整性、证据边界和空泛套话。
4. 实验结果回答研究问题，不把一次比较扩大成普遍结论。
5. 修改只动文字，不改变公式、图、表、引用和研究结构。

摘要三句式只是当前中文样本和本次摘要修改形成的样本倾向，不能在规则包确认前升级为期刊要求。

### 9.3 必查问题

- 缩写首次定义。
- 图、表和公式是否在正文中引用。
- 图表题注和正文名称是否一致。
- 数字和单位是否前后一致。
- 小数位和统计口径是否一致。
- 基金、作者贡献、利益冲突、伦理和数据可用性声明是否按期刊要求出现。
- 因果词、显著性词和强断言是否有对应证据。
- 结果、讨论和结论是否越过证据边界。
- 章节起句和段落职责是否符合目标期刊样本。
- 是否存在连续重复套话、泛化开头和无事实承载的评价词。

### 9.4 示例

原句：

~~~
The proposed method significantly improves security.
~~~

系统不直接生成替代句，而是提示：

- “significantly”是否有统计检验？
- 安全性对应哪个指标？
- 对比基线是什么？
- 是否存在对应的实验、表格或证明？
- 当前证据是否只支持“在当前 workload 下观察到改进”？

### 9.5 词库与表达规则分层

“去 AI 味”作为用户需求保留，执行目标定义为自然、准确、符合学科学术习惯并保持作者风格；不承诺母语级保证，也不以规避检测或检测分数作为验收。

| 规则组 | 检查范围 | 边界 |
|---|---|---|
| 语言与标点 | 语法、搭配、中英文标点、机械翻译、歧义与指代 | 按中英文、目标语体和学科配置；风格偏好不一律硬拦截 |
| 术语与作者习惯 | 规范名称、缩写、允许别名、禁用替换和作者确认新术语 | 不在词库不等于自造词；合法领域术语与例外可追溯登记 |
| 句子与段落职责 | 主题句、信息顺序、衔接、重复、套话及章节职责 | 不机械统一句长、句数和段落结构，不强行增加修辞 |
| 事实与证据 | 数字归属、比较方向、否定、因果、显著性、适用范围及引用 | 词库匹配不能独立证明语义未变，需要原文对照和人工确认 |

每条词库或模式规则记录 ID、版本、适用语言/章节/学科、检测方式、来源、例外、严重级别、正反例和建议动作。词库及项目例外保存在应用内部，不在作者目录新增散乱配置。作者确认的例外不得静默修改成全局规范。

### 9.6 候选表达的入稿流程

~~~
读取目标段落及必要上下文、对象和页面证据
→ 加载当前基线、研究目标、绑定规则、术语及相关证据状态
→ 记录实际读取范围、快照、规则与 EvidenceItem 版本
→ 用户安排的 Agent 提交含依赖、影响范围和风险的 Proposal
→ 冻结候选版本与 proposal_hash；后续修改产生新版本
→ 确定性规则与词库检查，生成事实对照及研究方向检查材料
→ 合并并冻结 ordered_proposal_hashes 与 plan_hash，完成只读预检与整批文件影响检查
→ 展示风险、审核政策及材料；用户决定是否安排人工/Agent 审核并提交 Review
→ 记录审核结论、争议与未审核项，不自动补成 PASS 或安排下一名 Agent
→ 作者查看具体批次和实际审核状态，处置阻断/提醒项后批准 plan_hash 及对应清单
→ 服务重新核对源版本、前像、环境及批准，不沿用预检许可；校验可写范围并原子执行绑定
→ 内部副本应用补丁，重读实际结果并同环境渲染和复核
→ 保存具体产物的 ValidationResult，提供实际产物审核材料，不预造最终发布结果
→ 核对适用审核政策及第 4.9 节发布条件；严格模式缺审核则保留内部候选待用户处理
→ 条件满足后发布新基线；用户可另行安排后续审核或选择导出
~~~

确定性检查只对可形式化的规则作判断；语义复核允许返回不确定，另一个模型的通过结论不能替代事实证据。比如“A 比 B 高 5%”改成“B 比 A 高 5%”，词和数字都没变也必须识别为待核验的比较关系变化。

文件保护及既定硬合同的明确违反必须阻断；证据不足、新术语或事实关系疑点进入待处理列表，语义审核是否为发布条件由第 4.7 节政策决定；风格建议可保留原文。用户控制模式不强制第二 Agent，作者查看并明确处置后仍保留未审核/争议状态；严格模式不能用批准替代所需 Review。补充证据可成为新审核输入，但批准不把 FAIL/UNCERTAIN/NOT_REVIEWED 改成 PASS。必需文件检查未完成不能发布，审核选项也不能绕过技术保护、权限及版本校验。

上述是记录与文件执行顺序，不是产品安排 Agent 的固定工作流。用户可以先审核候选再批准，也可在用户控制模式下先批准并完成安全修改，再让另一 Agent 审核实际文件；严格模式的必需审核必须在发布前满足。任何后续审核或再修改均绑定当时具体版本，不能改写旧操作已经发生的结果。

事实不足时只报告缺口，不自动补实验结果。产品不自动循环调用模型改写到检查通过；用户或外部 Agent 决定是否再提新候选，文件操作的安全重试仍按幂等合同。报告记录规则版本、确定性结果、语义疑点、实际审核覆盖及用户处置，不把换词绕过词库当作质量通过。

## 10. 读取核验与后续投稿复核

### 10.0 首版只读核验

先核实结构、实际页面和覆盖报告是否一致，再考虑是否符合期刊规则：

- 源文件哈希与快照一致，读取和渲染未修改原稿。
- 已登记部件及其关系都有处理状态，未知内容没有被清单静默排除。
- 在人工标注样本中逐项核实正文、文本框、公式、表格、浮动图、域及页眉页脚等对象。
- 页面中的已知对象能回到结构记录，或明确标为未映射；结构中的对象也有可见、隐藏或未核验说明。
- 字体、分节、分栏和位置结论能区分源声明、继承计算和渲染观测。
- 渲染失败、缺失字体、歧义映射和模型尚未读取的范围均进入报告。

本阶段不作“可以投稿”的判断。下列 10.1—10.3 在 0.2 的规则检查与改后复核中使用；所需读取证据不足时返回无法判断。

### 10.1 结构复核

- 页数。
- 页面尺寸。
- 页边距。
- 字体和字号。
- 章节和标题层级。
- 图、表和公式数量。
- 题注。
- 参考文献。
- 强制声明。

### 10.2 关键内容复核

改后文件验证以真实产物重新读取的内容为准，核实与批准计划的差异及保护范围，不能只检查待执行候选。语义审核另行记录；用户安排实际产物审核时提供下列对照项，高风险审核按第 4.7 节回源取证，未开展则标 NOT_REVIEWED。每项已完成的结论绑定对象版本、覆盖范围和检查方法，候选审核不冒充实际文件审核。

- 关键句是否保留。
- 数字和单位是否一致。
- 图表与正文是否一一对应。
- 公式编号和正文引用是否一致。
- 参考文献条目是否缺失。
- 摘要、正文和结论是否出现事实漂移。

S2B 至少生成本次改动、相关证据、已确认目标及相关实验/摘要/结论的对照材料，并运行已支持的确定性检查；语义关系由用户或其安排的 Agent 核验。材料已生成不等于语义已审核，未涉及章节不伪报已审。局部与全篇检查分别记录；必需文件验证失败和严格模式的审核缺口阻断相应发布，用户控制模式按明确展示和处置记录处理语义问题，不整篇无条件停工。

### 10.3 视觉复核

页面图像比较必须带容差：

- 字体抗锯齿不判定为错误。
- 修改段落及其正常下游重排可以是预期变化。
- 以未修改标题、图、表、公式和章节边界作为稳定锚点。
- 未修改区域的图表跑位、尺寸变化或题注漂移记为风险。
- Word 和 WPS 的 PDF 不做像素互比。

视觉差异是需分类的证据，不自动等于失败；本次必需页面检查的明确错误或未处置风险仍须阻止发布。检查项、容差、渲染环境和处置记录写入实际产物对应的 ValidationResult 与适用 Review，最终 ChangeResult 在操作终结时引用它们，不能在检查阶段提前填写发布结果，也不能仅用执行 Agent 的“看起来没问题”放行。

## 11. 输出物

本节的 outputs/ 是应用内部某次任务的逻辑产物目录，不是作者项目根目录。默认不向作者目录导出证据包、日志或报告。应用内部生成、保存版本与用户交付导出是三个不同动作；物理存储、生命周期和导出边界以第 19 节为准。

第 4.6 节概念对象与关联记录由应用内部统一管理，CacheEntry 为可重建缓存，其余按引用与保留策略持久化，不要求每个对象或每次 Agent 读取都另存一个 JSON 文件。下列文件树表示可检查或导出的逻辑视图，不建立第二套状态真源；共享状态、审计与缓存的保留策略以第 19 节为准。

### 11.1 0.1：只读证据包

~~~
outputs/
├─ source-manifest.json
├─ structure.json
├─ coverage-report.json
├─ object-page-map.json
├─ fidelity-report.md
├─ model-access-log.json
├─ workspace-audit.json          # 源目录不变与允许写入范围的验证
├─ environment.json
├─ checksums.sha256
└─ rendered/
   ├─ baseline.pdf
   └─ pages/
~~~

渲染失败时不伪造 baseline.pdf 或页面文件；环境和覆盖报告必须写明失败及其影响。原始稿件保持原路径只读，不属于修改后的输出物。

读取报告必须包含：

- 原稿哈希、快照和会话标识、解析器版本与支持范围。
- 部件、区域和对象清单，以及各自的解析状态。
- 格式声明、继承计算与页面观测的来源。
- 渲染环境、输入输出哈希、域行为和修订显示设置。
- 映射依据、歧义对象、未映射对象和缺失证据。
- 模型实际获取的证据范围、分页和截断记录；不宣称模型已正确理解。
- 本次实际使用的任务资料目录、材料选择依据/缺口及引用版本，作者显式要求的适用范围；已保存读取型书签的来源、范围与失效提示。它们引用既有记录，不要求额外复制或导出一整包文件。
- 初始或更新后的读取 Baseline、ArtifactVersion 与 EvidenceItem 的版本引用、可信基线更新决定及失效原因；区分原始观察、推断、未核验及已失效结果，导入/切换基线不隐式通过核验。
- 人工核验项、未解决项与适用限制。
- 工作目录、允许写入范围、原稿及作者目录的核验结果；发现未知变化时记录证据，不自动删除外部文件。

原始读取基线和改后证据分别保存，不用新 PDF 覆盖 baseline.pdf。规则报告与修改报告还必须包含：

- 规则版本。
- 规则来源。
- 原稿和副本指纹。
- 修改节点和修改前后文本。
- Word/WPS 渲染器信息；LaTeX 阶段另记编译环境。
- 域刷新记录。
- 结构复核结果。
- 关键内容复核结果。
- 视觉风险。
- 未解决问题。

- 如调用过修改预检，记录其具体计划、检查时版本、范围、未满足条件及限制；预检报告不替代实际执行和 ValidationResult。修改/审核型书签引用真实阶段记录，不把候选建议写成已修改。

按实际阶段保存冻结的 Proposal、Review、Approval、候选 ArtifactVersion、ValidationResult、PublicationRecord 与最终 ChangeResult 的关联，包含依赖与影响位置、实际使用的取证路径、提交来源与审核政策、复核结论、有效性、approval_status、bound_operation_id、派生绑定状态、proposal_hash、ordered_proposal_hashes、plan_hash、operation_id、request_digest、执行尝试及对账记录。最终结果未确定时只展示已有检查/尝试记录及 UNKNOWN / RECONCILING 等真实执行状态，不为了报告完整而预造最终结果。记录可以集中存储，但须能从某次已发布版本追溯所用证据、批准和检查；读取基线更新、待发布候选与已发布修改分开显示。

### 11.3 模板与规则产物

模板原件、官方资料快照、提取事实、规则候选、模板页面、每刊摘要、确认状态及新旧版本差异，保存在应用内部规则包库。一个模板版本可供多个项目引用，不为每篇稿件重复生成来源文件夹；来源变化产生新版本，不原地覆盖。

### 11.4 用户选择的交付物

导出界面先列明文件名、版本、格式、大小和验证状态，作者只选择需要的 DOCX、PDF、图件、报告或完整项目包。默认只交付选中的成品，不附带内部截图、缓存、审批凭据和日志。报告或可迁移项目包也是主动导出选项；导出含原文、个人信息或本机路径的审计材料前说明内容范围。

内部版本的批准/验证不等于已经导出。磁盘写入、校验未完成时显示导出失败或待恢复，不提前提示“交付完成”。

## 12. 推荐技术分层

### 12.0 两个入口，共用一个核心服务

- 人通过桌面工作台读取证据、管理模板、查看候选、批准计划、恢复版本和选择交付。
- 模型通过 MCP 适配层查询同一证据、提交计划并请求允许执行的操作；不能签发用户批准。
- 两个入口均调用核心服务的同一操作协议，由核心执行第 4 节共同约束，再分派给格式专用引擎。桌面不必绕行 MCP，也不得凭界面入口跳过文件引擎的保护与验证。

共享工作区、版本、批准与交付管理服务保存记录并执行文件操作约束；规则与证据服务提供依据；格式专用引擎执行原生读写、渲染和验证。用户通过不同客户端安排接力，所有客户端共用同一当前基线，不各自发布“当前稿件”。产品自动执行已授权操作的技术步骤，但不调度 Agent。这些是职责划分，不要求按对象拆成独立服务或所有操作经过同一固定链路。

### 12.1 核心层：文档读取与证据服务

- 文件快照、部件与关系枚举、区域和对象索引。
- 格式来源与布局设置解析，支持范围和未知对象登记。
- PDF 页面、图像、可用文本层及结构—页面关联。
- 覆盖报告、统一模型读取接口、分页与证据获取记录；复用这些记录形成按需资料目录、读取型书签及显式作者要求视图，不增加自动学习或语义依赖发现。
- 不可变源版本、初始及可信更新的读取基线、版本化证据与显式依赖；观察、推断、人工/确定性核验记录和可重建缓存分开，读取基线更新不借用改稿批准。
- 宿主侧原稿访问限制与受控接入测试。

本层先于规则和写入器交付。结构化表示用来读取与核验，不用来重新生成一份“近似原稿”的 DOCX。

- 改后重读、实际差异与结构/页面验证、语义审核状态展示、依赖失效、幂等执行及条件式基线发布。

### 12.5 实现载体（显式待定项）

实现选型和已确定的接入方向如下；具体库、框架及 SDK 尚未完成验证：

- 解析与结构索引：候选 lxml 等 XML 库，语言和库由覆盖样本验证决定，不因使用 Python 就禁止。DOCX 文本替换严格执行第 5.4 节字节级补丁，不使用 DOM 整部件重序列化替代；这一限制不扩展为“所有格式、所有操作一律字节补丁”。格式、对象、结构编辑与新文件生成分别验证其实现和允许差异，不能借用文本替换已通过的验收。
- 界面框架：三栏桌面界面，候选 Tauri、Electron、PyQt。
- 模型接入采用本地 MCP 入口；桌面调用同一核心服务，内部 API、辅助 CLI 和具体 SDK 留待实现。首版 MCP 对稿件只暴露读取证据能力，内部记录和报告写入单独说明；宿主隔离与服务授权分别验收。v1.3 修订：本地单操作员工况下，与操作者共享进程令牌的本地 MCP 面与可信桌面入口同权，可执行稿件捕获、读取基线更新、绑定、检查与处置记录；就地修改稿件字节、发布作者决定与登记渲染证据仍限可信人工入口，宿主隔离与服务授权继续分别验收。
- 表达候选与语义审核由用户使用的外部 Agent 或人工提交，产品不选定、托管或自动调用某个生成/复核模型。优先记录已授权主体/客户端及服务端实际读取范围；模型名称、版本和提示词引用仅在调用方提供且获准保存时作为声明元数据，不臆造未知信息，不要求保存完整聊天、隐藏思考或秘密凭据。S1 不依赖模型选型。

### 12.6 操作类型 × 允许变化 × 验证方法矩阵

本表定义跨格式的操作合同类别，具体支持范围以第 2.6 节能力记录为准。五类写操作互不替代，不把 DOCX 的 w:t 节点规则强加给 LaTeX、SVG 或其他格式。

| 操作类型 | 允许变化 | 验证方法 | 阶段与边界 |
|---|---|---|---|
| 文本替换 | 指定文本范围；保留其保护边界、关联对象和批准的事实范围 | 源版本、前像、上下文、事实对照与允许差异；DOCX 额外核验第 5 节字节差异和未改压缩部件，其他格式采用自身源范围校验；必要页面复核 | DOCX 为 S2B；LaTeX 普通文本为 S4，其他格式文本对象按 S4 候选逐项验证；禁止顺带增删结构或改格式 |
| 格式修改 | 批准的字符、段落、样式、节或图形视觉属性及明确影响范围 | 属性白名单与前后差异、结构保护、共享属性影响清单、同环境重渲染与风险核验 | S4 逐项规划；字体、间距、缩进和分栏分别验证，不笼统宣布“格式可改” |
| 对象操作 | 批准的公式、图表、数据、图件及必要资源关系 | 对象结构与关系完整性、资源哈希、数据映射、引用及页面复核；预期新增或删除的资源逐项列出 | S4 逐项候选；未支持的数学对象、图件变体或专有工程明确拒绝 |
| 结构编辑 | 批准的段落/章节/表格行列/图形节点等增删、移动及必需关联调整 | 预期节点与结构差异、父子及顺序关系、编号和交叉引用、资源孤立或悬空检查、整段影响与页面复核 | S4 候选且须单独定范围；对象数量可按批准预期变化，不套用文本替换“数量不变”证明 |
| 新文件生成 | 明确规格、模板和数据范围内的新输出文件或文件集合 | 模板符合性、来源与数据核对、结构/依赖完整性、可打开性及视觉检查；声明完整生成范围 | S4 候选；不重建原稿后冒充最小修改，保存内部资产与向外交付分别授权 |

文本替换的跨格式共同承诺是“只改变批准的文本范围”；DOCX 的字节补丁是该承诺的一种最严格专用实现，不是全产品唯一写入器。新格式不能借“专用实现”之名跳过原像、保护对象、事实与输出验证。

共享样式修改须先列出全部受影响对象，不能只展示一个段落；结构或对象操作导致编号、引用、页面位置和对象数量变化时，允许变化清单必须明确列出，不把整篇重排都无条件视为允许。文字补丁中不允许的域结果更新，仍需独立刷新合同。

一次请求涉及多种类型时拆成明确的子操作、依赖顺序和各自验证，用户看到完整影响后批准组合计划；运行期间不得临时追加未批准步骤。任何必要子操作失败，组合结果不得登记为已核验整体；内部部分产物与可恢复状态真实保留，不能假定多步骤天然事务化。

读取与检查不属于上述写操作，只产生应用内部证据；编译/渲染是受控派生产物任务，不等于编辑源稿；导出按第 19.4 节单独授权与核验。恢复先建立内部版本，资产移除只管理已选内部数据，均不授权删除或覆盖作者原件。

每个专用合同必须给出 operation_type、contract_version、source_snapshot、preconditions、target_scope、expected_diff、protected_objects、validators、approval_scope 和 failure_policy。operation_type 表示能力类别，不使用逻辑执行标识 operation_id 代替；具体执行再绑定第 4.10 节的 operation_id、plan_hash、ordered_proposal_hashes、request_digest、execution_attempt、源 Baseline、批准及结果。未知对象和不支持路径须有负向样本；未具备专用验证器的写操作不能发布为已验证。

### 12.7 项目、版本与存储服务

本服务实现第 4 节共同约束和第 19 节存储合同，统一管理核心概念对象、ValidationResult / PublicationRecord 关联记录、依赖、内部项目配置、规则绑定及交付记录，不另定义一套批准或状态规则。核心执行可信读取基线更新、依赖有效性判定、风险标记与用户选定的审核政策、冻结候选/实际产物审核记录校验、批量批准与原子执行绑定、幂等对账恢复及修改产物发布；不负责安排审核者或生成审核意见。持久化选型必须支持相应提交语义，包括拒绝记录和终态结果一致保存，但不按对象数量拆成同等数量的服务。模型不直接选择内部存储路径；内容复用不能让工作副本反向修改快照、源文件或其他版本。

原稿访问、任务写入及交付写入采用独立边界。内置模板与公开规则不带用户稿件；向远程模型发送的内容和范围须事先明确授权，不因“本地优先”而隐瞒实际外发。敏感日志、缓存和内部版本遵守项目访问与保留策略。

### 12.8 MCP 与 Agent 使用包

MCP 是模型调用核心服务的适配层，不持有另一个可以放宽规则的写回器。能力发现返回当前可用操作、合同版本和运行限制；规划中的能力不冒充可执行工具。统一请求以项目、快照、能力、操作、目标对象、参数、计划及批准引用等表达，核心服务负责解析和授权，不直接暴露任意 shell 或任意文件写接口。

操作结果遵守第 4.5 节，页面及结构证据遵守读取覆盖要求。只读检查、保存提案、请求应用和交付导出必须清楚区分；即使模型不遵循使用说明，服务仍拒绝越权和版本冲突。

按阶段提供当前基线、需求与规则、证据/来源、实际读取覆盖、候选和真实差异、改后产物、审核与未解决问题的查询。已授权客户端可提交 Proposal 或 Review，提交者身份与具体操作权限分别校验，不设置固定 Agent 团队角色。Review 按第 4.7 节绑定冻结候选/计划或实际产物，保留方法、依据与限制；同一客户端也可提交不同工作记录，但不能因此宣称独立审核。模型不能签发用户批准、改变审核政策、绕过核验记录直接设证据为 PASS 或修改当前基线指针。S1 的读取基线更新为可信桌面入口，本地单操作员工况下含共享其进程令牌的本地 MCP 面（v1.3 修订）；所有材料附版本与未覆盖项，不把不可信文档指令升级为权限。

MCP 按功能提供能力，下面的名称是设计示例而非已实现或冻结 API；不按工具数量拆服务，阶段未开放的能力不暴露为可执行：

| 能力组 | 示例入口 | 阶段与边界 |
|---|---|---|
| 共享工作区与证据 | workspace.get_current、workspace.get_requirements、workspace.get_task_materials、evidence.query | S1 起查询当前输入、作者显式要求、按需资料目录与证据；S2A 加规则，S2B 加修改/审核材料；目录命中不算已读取 |
| 决定与接力书签 | decision.list、handoff.save、handoff.get、handoff.list | S1 保存用户显式决定并提供读取查询，客户端仅在授权范围保存/取得读取型书签；S2B 扩展局部表达决定与修改型书签。MCP 不直接确认作者决定或以书签更新基线 |
| 文件读取与页面 | document.inspect、document.read_region、document.render、document.get_coverage | S1 的已声明读取/渲染能力，返回真实覆盖与限制 |
| 变更与验证 | change.get、change.get_diff、change.propose、change.preflight、change.apply_approved、change.verify | S2B 起；preflight 仅检查当前计划、无稿件改动或批准绑定，应用须已有批准并重新校验；计划差异与实际差异分开，verify 运行验证器而非接受客户端传入 PASS |
| 审核材料与记录 | review.get_materials、review.submit、review.list | S2B 起提供执行前/后的材料与人工/Agent 记录，不自动调用审核者 |
| 问题与版本 | issue.list、version.list、version.compare | 按阶段列出已存在的问题与版本，待处理列表不自动派单 |

审核材料是第 4.6.1 节通用任务资料包在 S2B 的特定视图，至少带任务目标/范围、源版本、修改前内容、候选或实际改后内容及相应差异、规则与源证据、已有技术检查、未读取/无法确认项。来源说明、执行者自我解释和历史语义审核分开取用；用户要求独立审核时可先不读取解释或历史意见，随后按需获取。资料目录和书签 ID 只是访问入口，每次展开仍校验权限与版本；不把“提供入口”算作“Agent 已读完”。

产品不提供 agent.spawn、agent.assign、reviewer.schedule、debate.start、consensus.wait、team.orchestrate 等 Agent 管理能力，也不维护 Agent 任务租约。外部 Agent 工具可用上述能力自行组织接力，仍须通过相同版本、权限、批准和验证合同。

Agent 使用包包含 AGENTS.md、Skills、用户安排接力与审核的示例、支持范围及错误处理说明，指导先读取书签/资料目录并展开所需原始证据、核对规则与作者决定，再提案、预检、等待具体批准和按真实结果处理；不把示例写成产品会自动召集下一 Agent，也不把预检或书签当作执行许可。使用包与核心协议和规则版本关联，但只是使用说明，不是规则真源或权限实现。

使用包默认放在应用管理的安装或配置空间，不自动写入作者项目目录。用户主动要求某宿主在指定位置安装时，应单独预览文件清单并授权，不能借“接入模型”绕过第 19 节零污染约束，也不覆盖用户既有 AGENTS.md 或配置。

## 13. 分阶段验收标准

第 13.1—13.3 节分别验收读取、Word 文字写回、模板与表达；第 13.4 节零污染与第 13.5 节共同合同对各阶段已开放能力同时生效；第 13.6 节按标明阶段验收共享工作区、用户安排的接力审核、政策与发布保护；第 13.7 节验收 v1.2 的资料包、作者决定、预检、缓存与书签。尚未开放的写操作不要求在 S1 实现，示例接口不能出现在当前已验证能力清单中。

### 13.1 MVP-Docx-Fidelity-0.1：读取验收

以 IJAM 英文工作稿和第 18 节独立标注的复杂样本共同验收。不采用“任意 DOCX 完整读取”的无法验证承诺，也不允许把所有对象标成不支持来通过验收。

1. 测试前锁定能力矩阵：必需结构解析、仅登记原对象并提供页面外观、暂不支持三档。正文、区域文字、基本表格网格、OMML 源结构、域边界、图片关系、样式来源和分节分栏设置必须有结构结果；具体复杂变体逐项声明。
2. 人工标注样本中的对象逐一对账。漏登记任何已知对象即失败；必需解析项被标为不支持也失败。范围外对象至少记录原始位置、关系、限制和可用页面证据。
3. 文字不能吞并公式、引用域或跨区域拼接；页眉页脚、文本框和脚注等不得混成普通正文。
4. 格式结论能追溯到声明值、继承链或页面观测。未知格式不填成已确认默认值，XML 顺序不直接冒充视觉阅读顺序。
5. 在已指定且具备所需字体的至少一个 Word/WPS 环境中成功生成 PDF 和页面图像；记录源哈希、渲染器、版本、字体、域行为与修订显示设置。
6. 标注样本内的关键标题、图、表、公式和引用建立可核验关联；多页、重复和歧义对象按实际关系表示。精确定位未经验证不得标为 verified，错配比未映射更严重。
7. 注入缺失字体、失败渲染、未知对象、不可映射等情况时，报告必须变为部分完成或待复核，不得仍显示全部通过。
8. 模型接口同时提供结构、页面和覆盖证据；分页、截断及未读取范围显式返回，不用纯文本输出替代这些信息。
9. 验证一条受控模型接入路径：该路径不能直接读取原稿，只能访问已授权的证据接口；其他不具备隔离条件的宿主明确标为非强制接入。
10. 读取与渲染前后原稿哈希不变；不产生修改稿、不刷新 Zotero、不执行文档内嵌代码或自动获取外部内容，不关闭用户已有的 Word/WPS 会话。
11. 通过独立标注对照复核以上结果，而非让同一个解析器自报数量自证正确；报告保留未解决项和每类能力的实际结果。
12. 读取、预览、渲染与报告任务同时通过第 13.4 节零污染验收；应用内部产生证据不等于允许在作者目录新增文件。
13. 能力发现仅返回本阶段实际已验证的操作及环境限制，未发布写操作不可调用；桌面与 MCP 的读取、证据覆盖及错误结果通过第 13.5 节对应检查。
14. 持久保存初始/更新后的读取基线、源版本、读取覆盖和能力范围内的 EvidenceItem 及人工/确定性核验记录；观察、推断、核验及缓存不混用，导入不自带 PASS。可信读取基线更新有用户决定、并发检查、失效与重复请求处理，不依赖 S2B 的改稿批准。第 13.6 节及第 13.7 节 S1 项通过；轻量目录、用户显式要求、读取书签和有效性缓存只复用这些基础记录，不提前实现修改预检、表达例外、候选或审核模式。自动 Agent 编排不属于任何阶段的产品能力。

覆盖、映射、模型获取范围分别计量。首版最重要的失败类型是“漏读却宣称已经读全”，不以文字提取量、规则命中数或改写数量作为成功指标。

### 13.2 MVP-Word-0.2：规则与写回验收

在 0.1 合格基线上增加：

1. IJAM 规则包按来源、版本和适用阶段绑定；每项问题可回到读取证据，证据不足返回无法判断。
2. 仅作者批准且符合 5.3 的文字范围可写。受控多节点替换按合同执行，跨格式或受保护边界必须拒绝。
3. 结构、前像或源文件版本变化使修改计划整体失效。
4. 修改 XML 的字节差异等于批准集合；未改部件保留原始压缩字节，数量核验仅作辅助报警。
5. Zotero 域、公式、图表结构、样式和编号不被写回破坏；读取器与写入器均不以 python-docx 作为生产依据。
6. 域刷新只作用于另行标识的 render-copy，不回写生产稿；改前改后在同一环境重新渲染。
7. 复核区分批准变化、正常重排和风险，不把抗锯齿直接判失败。
8. 问题来源、批准记录、修改差异、事实影响和拒绝写回原因可追溯，原稿始终不覆盖。
9. 模型不能自产批准凭据；候选内容、源快照、规则版本和执行范围变化后旧批准失效。approval_status 与 bound_operation_id 分开，批准绑定后仍能表达撤销/过期，重复请求不得重复应用或改绑。
10. 执行中断、验证失败或磁盘空间不足时不得伪报已核验或已发布，不覆盖当前基线；检查生成 ValidationResult，发布确定后保存 PublicationRecord，逻辑操作终结时才有最终 ChangeResult。实际写后内容重新取证，必需文件检查及适用审核政策满足，且提交边界核验源基线、依赖、批准及绑定仍有效后才能发布；未审核不能冒充语义通过，响应不明用 UNKNOWN / RECONCILING 对账，不能预判最终失败。
11. 第 13.3 节模板与表达验收、第 13.4 节零污染验收，以及第 13.5—13.7 节对本阶段开放操作的验收通过，才算 0.2 完成。S2B 预检须验证无稿件副作用和执行时重新校验，不以预检通过替代写后验证；格式、对象、结构编辑和新文件生成不自动进入本版本。

LaTeX 编译、外部 Zotero/CSL 完整核验与图件资产管理不影响上述两个里程碑各自的完成判断。

### 13.3 模板与表达验收（0.2）

第 1—4 项在 S2A（模板与规则）验收，第 5—7 项在 S2B（表达与文字写回）验收；第 13.4—13.5 节共同合同及第 13.7 节适用项同时生效，S2A 不以完成修改预检或改稿状态机为前提。

1. 一个经核验的期刊模板可从首次导入走通解析、渲染、事实提取、候选规则、确认发布、每刊摘要；保存原件与来源，不要求作者重新手录已可解析的属性。
2. 第 3.6 节每个属性类别都能返回事实或明确缺口；观察、推断、已确认要求分开，不把样例的偶然格式升级为硬规则。
3. 初审、录用稿、文章类型和语言可区分；文献、图表、公式、章节及脚注引用分别配置，不全局强制上标。
4. 新版模板产生新规则包和可核对差异，旧项目不静默升级；冲突及待确认项能出现在明细和摘要中。
5. 候选修改绑定已读取的上下文、证据与规则版本，单候选正式复核针对冻结的 proposal_hash，批次复核针对 plan_hash 与 ordered_proposal_hashes；改动产生新候选或计划，不沿用不匹配的通过标签。合并批次检查共同影响与最终计划；词库未命中不等于通过全部检查。
6. 使用机械翻译、合法新术语、套话、否定改变、比较方向颠倒、数字归属改变等正反例，验证规则检测与风险提示；接入预置人工/Agent Review，核验两种政策下未审核、争议与通过的处置。文件硬失败必须阻断，语义无法确认或尚未审核不得伪报通过，不要求产品自己启动模型进行审核。
7. 候选不自动入稿；批准由可信用户通道产生，技术保护不能通过模型批准或审核选项绕过。提交新候选由用户或外部 Agent 发起，产品不自动循环生成、不通过反复换词规避检查。

### 13.4 工作区零污染验收（所有阶段）

以受控测试目录、预置哨兵文件和目录清单执行，真实用户目录不通过制造垃圾来测试：

1. 导入、读取、预览、检查和模板更新，以及本阶段已开放的资料包/决定/书签保存与查询、修改预检后，作者目录文件清单、文件内容哈希和受保护属性不被任务改变；不生成隐藏配置、备份、截图、临时脚本、锁文件或编译文件。允许的内部记录写入明确列出，系统自动访问时间变化不等同于应用写入。
2. 模拟解析失败、外部程序失败、取消、崩溃、重试及空间不足，未授权交付的源目录仍不新增或损坏文件；半成品只留在应用内部任务目录，不能报成功。已明确授权的交付任务另按第 3—5 项核验，不把多文件部分提交隐藏为无变化。
3. 只有显式导出才写用户选定的目标，成功后新增文件集合严格等于选择的交付物；同名未经确认不得覆盖，也不擅自产生编号副本。
4. 导出前出现外部并发修改、目标存在状态改变或路径解析越界时中止并重新确认；不能把一项文件批准扩大成整目录写权限。
5. 单文件导出准备与校验失败时既有目标保持不变；跨文件交付如不能保证整体原子性，须保留真实提交清单并标明未完成，不宣称全部成功。
6. 外部渲染、LaTeX、图件适配器全部验证实际写入边界。对符号链接、目录联接、绝对输出路径等绕过方式拒绝越界；未能证明隔离的适配器不进入强约束模式。
7. 清理可重建缓存后，已承诺保留且未导出的修改、已核验版本、规则绑定和必要批准记录仍可恢复；清理不会删除源文件或用户已有交付物。
8. 用户能查看存储占用、清理范围、保留期限及删除影响。待执行任务和恢复所需资产不会因自动清理丢失。
9. 发现不明外部文件或并发变化时只报告及阻止不安全操作，不自动“清理”作者目录；能够把应用导致的越界与外部变化分开说明。

### 13.5 能力声明与共同合同验收（按已开放操作执行）

1. 第 2.6 节矩阵中的每项发布能力都有独立能力记录、合同版本、适用环境和回归样本；规划、开发中、已验证与运行时可用状态分开。换版本或环境后按影响复核，不沿用不适用的已验证标记。
2. 桌面与 MCP 对同一源快照、身份权限、计划和操作合同得到一致的保护及校验结果。桌面有可信批准通道不代表其文件操作可跳过合同；模型接口不能签发用户批准或用任意文件写路径绕过。
3. 0.2 及后续写操作验证缺少批准、伪填已批准、绑定后过期/撤销、并发绑定、计划变化、源文件变化、重复提交及中断恢复。修改内容或范围变化使旧批准失效；非终态可恢复尝试与已有最终失败结果分开，重试不重复应用、不改绑或重开终态。
4. 分别注入不支持对象、缺少运行环境、版本冲突、权限不足、执行失败和验证失败，结果码、完成步骤、副作用和下一步与真实状态一致。已执行失败不能伪装成全部未执行或已成功。
5. 每个写操作按第 12.6 节自身合同验收：文本前像与范围、格式属性及共享影响、对象关系与资源、结构与引用、新文件符合性。DOCX 文本替换的字节级保证不能被其他合同放宽，也不被错误推广为全格式要求。
6. 混合操作预先列出子操作及依赖、允许差异和检查器；中途缺少能力或检查失败不会临时扩大批准范围，组合任务不得伪报整体通过。
7. Agent 使用包即使缺失、过时或被模型忽略，核心权限与保护检查仍执行；其安装不自动污染作者目录，版本不匹配须说明能力限制。
8. 所有已开放能力同步通过第 13.4 节及对应格式回归。第 4 节共同约束是全局规则，第 19 节是存储与交付规则，不允许适配器用局部配置取消。

### 13.6 共享工作区、接力审核与发布验收

使用人工标注或确定性预置的测试工件；测试数据放在应用管理的测试空间，不修改作者原件。PASS 只对指定检查范围成立，不能仅凭多 Agent 意见一致验收。

本表阶段表示场景必须完成的验收节点：S1 为阶段 1（0.1），S2B 为阶段 2B（0.2 的表达与文字写回）。S1 基础 / S2B 扩展分别验收当时已开放部分；S2A 的模板与规则验收见第 13.3 节，不要求提前实现改稿、逻辑执行与发布状态机。所有已开放能力仍遵守共同权限、存储和零污染合同。

回归夹具在运行前固定输入版本、方法版本、依赖与期望结果，不根据系统输出事后修改答案。依赖夹具至少给出 expected_impacted_ids、expected_preserved_ids、dependency_completeness 和 fallback_scope；两个期望 ID 集合不得相交。完整依赖与缺失依赖分别预置应失效集合、应保留集合及缺失时扩展范围，漏失效、误失效或超出预定范围均记录为不符合，不能用“更保守”自动通过。语义/审核夹具预置输入材料、Review（有时）、expected_verdict、审核政策版本/模式、问题类别、用户处置及适用场景的唯一 expected_publication_decision，分别覆盖未审核、明确越界、证据不足和证据支持；不根据输出事后更改政策，也不得以“阻断或待核验任选其一”通过同一夹具。确定性检查按其声明能力实际运行；外部语义 Review 采用独立人工标注的固定输入，不把外部模型的科学判断能力当作本产品已实现的能力。

| 检查、发布与最终结果时序 | S2B | 已验证待发布阶段保存产物和 ValidationResult，不预填最终 ChangeResult；成功时基线/指针/发布/最终结果一致提交。确定冲突或拒绝仍保存 PublicationRecord 与最终拒绝结果，不因业务回滚丢记录；未尝试发布就终结的失败有最终失败结果，但不伪造发布记录，失败结果无已发布版本 |
| 并发基线提交 | S2B | 两任务从 V12 出发，先发布 V13 后，另一任务不能覆盖；检验发生在原子提交边界而非仅执行前读取，后者保留材料并重建计划 |
| 崩溃与重复执行 | S2B | 在批准绑定、补丁应用、验证及提交前后注入中断；恢复先对账，同一逻辑操作仅产生一次发布效果，不重复打补丁 |
| 未知结果与对账 | S2B | 响应丢失且无法确认结果时进入 UNKNOWN / RECONCILING 并保留 last_known_phase；未查明不重放写入、不预造最终失败。查出已提交返回原结果，证明确未提交且授权仍有效才可恢复，取消请求也不掩盖未知副作用 |
| 可恢复尝试与最终失败 | S2B | 临时故障只记尝试结果，确认安全后同 operation_id 增加 attempt；已有最终失败/拒绝/取消结果的重复请求只返回原结果，不能重开执行；重新启动需新操作及新批准，旧绑定保留 |
| 同 ID 不同请求 | S2B | 同 operation_id 改 plan_hash、来源、批准引用或执行参数导致 request_digest 不同并返回 idempotency_conflict；仅执行顺序变但单项 proposal_hash 不变也必须识别。保持业务请求不变，只更新尝试计数、传输时间或跟踪 ID 时摘要不变，不误建第二个逻辑操作；查询仍检查访问权限，实际恢复/发布另查批准与环境，不以旧批准过期阻断有权读取的历史结果 |
| 提交成功但响应丢失 | S2B | 重试返回原结果与版本；即使当前基线又已推进也不二次应用、不误报为旧请求版本冲突，明确原结果不一定是当前稿件 |
| 发布前撤销或失效 | S2B | 已绑定操作 A 后批准变 REVOKED 或 EXPIRED，原 bound_operation_id 仍为 A，恢复/发布被拒且不能转给 B；依赖失效或必需检查未通过也阻止发布，历史成功结果仍可查询 |
| 批准并发绑定 | S2B | 两个不同操作同时请求同一批准时至多一个原子绑定成功；绑定与执行身份一致持久化，相同操作重复请求返回既有进度或结果，不出现双执行或孤立绑定 |
| 失败候选重新导入 | S2B | 两个固定子场景：未经用户明确导入时当前基线不变；用户通过可信入口明确导入时允许切换为新的读取基线，显示来源及实际核验状态，不生成成功修改发布记录。两者均不自动导出、不覆盖作者文件、不复用或改绑旧 Approval、不清除原失败记录 |
| 用户安排接力与提交来源 | S2B | 已授权客户端 A 提交候选后，不提供历史聊天也能由用户安排的客户端 B 取得正确基线、规则、原始证据、实际读取范围和问题；服务保留真实客户端身份与提交来源，声明模型信息不当作认证。全程不自动启动或调度 Agent，客户端不能签批准或更改政策 |
| 执行前后审核材料 | S2B | 未执行时只返回候选与计划差异，实际产物明确不存在；已执行时返回真实产物/哈希、实际差异、ValidationResult 和相应计划。产物审核缺少实际版本绑定则拒绝作为该产物的有效审核，候选审核不得显示为实际文件已通过；执行者解释和历史意见可按需另取 |
| 用户控制模式的未审核发布 | S2B | 预置高风险但不违反硬合同的候选，无语义 Review；材料显示 NOT_REVIEWED，用户明确知晓并批准具体计划、全部必需文件验证通过且版本有效时允许发布。仍显示 NOT_REVIEWED / 文件验证 PASS / 授权 APPROVED，不自动生成 Review 或语义 PASS；未批准不得执行 |
| 严格模式与政策变更 | S2B | 高风险候选在无审核、审核过期、范围不匹配、UNCERTAIN/FAIL 时不得发布，不自动找审核者；针对完整适用范围的有效 PASS 且其他条件满足时才允许。普通客户端修改政策被拒；可信用户变更政策后旧 plan_hash/Approval 不可沿用，须重建计划、重查并重新批准，旧审核不被删除 |
| 两种模式的文件保护 | S2B | 对相同计划逐项注入源版本/前像不匹配、批准失效、越权、超范围实际差异、结构破坏、必需页面验证失败及发布基线冲突；两种模式均拒绝相应执行或发布，不以语义未审核、用户接受争议或 Review PASS 绕过 |
| 已发布版本的后续审核 | S2B | 用户安排的客户端对已发布产物提交审核，新增绑定真实版本的 Review 与问题但不改写原 ChangeResult、不自动回滚/改稿；再修改须新计划与批准。当前稿已推进时，旧版本审核显示历史适用范围，不覆盖当前稿状态 |

接力验收使用固定客户端请求和审核记录，不要求搭建真实 Agent 团队。后续可在用户实际使用中记录查找材料耗时、错误漏过、人工处理时间和返工量，评估共享工作区是否有用；外部 Agent 的安排与模型评测不成为本产品调度能力或首版前置条件。

### 13.7 五项接力体验能力验收（v1.2）

本节复用现有项目/版本/证据及测试空间，不要求五个新服务或真实 Agent 团队。每条按已开放阶段执行，测试前固定材料与权限、期望条目/缺口、决定适用范围、缓存应失效/应保留集合及写入允许清单，不根据系统输出事后调整答案。

| 场景 | 阶段 | 必须观察到的结果 |
|---|---|---|
| 按需目录、缺口与实际读取 | S1；S2A/S2B 按材料扩展 | 指定区域夹具能列出预置邻文、关联对象/页面和选择原因；已知相关但未读的材料、缺失数据/未定位引用仍显示缺口。只取目录不把所指内容记为已读；分页返回真实覆盖，旧包展开不静默换到新版本，越权引用不泄露内容。S2A 加规则，S2B 加候选/实际产物/审核，不提前伪造这些材料 |
| 显式作者决定与作用域 | S1；S2B 扩展 | S1 的用户确认术语/目标仅在指定 DOCUMENT/PROJECT 和条件内出现，不从聊天或文档指令自动学习。普通客户端不能把建议直接设成作者决定或事实 PASS；表达偏好和事实相关决定分开。S2B 一次拒绝只作用本次问题，持久 LOCAL/SECTION 例外须明确确认且绑定位置；更新形成新记录，不扩大为 PROFILE |
| 规则升级与作者例外 | S2A | 用户升级规则绑定后，固定夹具中受影响决定标待确认/失效，无关偏好保留；旧例外不自动适用新规则。针对样本倾向的合法例外可展示，试图用作者偏好覆盖官方硬要求不得显示合规；原件/页面的无关缓存不连带废弃 |
| 问题去重而非意见投票 | S1 读取问题；S2B 表达/审核 | 同版本、同位置、同检查项的重复记录合为一个显示项，原始来源与记录仍可查；规则/前像变化时不误合并，定位不明不靠相似文字合并。S2B 同一问题的 FAIL 与 PASS 同时保留为冲突，不相抵、不自动解决或隐藏硬错误 |
| 读取书签与版本变化 | S1 | 书签只指向真实基线/任务/材料和已获取范围，未读区域不得写为完成。当前基线变化后旧书签展示 STALE 与逐项仍有效/失效依据，不重绑或自动执行；删除书签仅移除入口，稿件、证据与其他记录不减少 |
| 修改/审核书签的完成阶段 | S2B | 分别预置仅候选、已改内部副本、文件验证通过、语义未审核、已发布、已导出记录，书签展示必须逐项匹配；没有真实产物时不写“已修改”。Agent 自述/下一步备注不改变阶段、基线、授权或触发任务，旧稿审核不挂到新稿 |
| 预检范围与无稿件副作用 | S2B | 分别预置唯一结果：六项中一项跨引用域 → 整批技术阻断且定位该项；必需字体/程序确实缺失 → 列明缺少条件；条件无法安全探测 → 标未核验而非已可用。不得在这些结果间任选其一，不执行可行子集。调用前后原稿/生产副本不变、未新增修改稿或试改 PDF、基线与批准绑定不变、未创建改稿逻辑执行；允许的内部读取/缓存/预检记录逐项报告，不伪称完全无磁盘写入 |
| 预检不替代执行检查 | S2B | 无修改批准时可完成有权限的预检并报告缺授权，但 apply 必须拒绝；预检后改变源/前像/环境/政策/批准状态，实际应用或发布重新核对并拒绝不满足合同的请求。选择可行子集后 plan_hash 改变，旧批准不可用；预检不产生写后 ValidationResult，试改请求不能借 preflight 或 S1 页面预览执行 |
| 缓存有效性与依赖隔离 | S1；S2A/S2B 扩展 | 分别改变稿件、解析器/提取方法（含源不变修复）、Word/WPS 版本、相关字体/显示条件和 PDF 哈希，实际失效/保留集合等于预置集合，旧页面定位不沿用。S2A 加规则/决定升级，S2B 加已知依赖的检查复用；仅下游规则变化不使无关结构/页面失效。覆盖不足或缺依赖不能命中；缓存命中本身不生成语义 PASS 或模型已读记录；实际向客户端返回材料时仍登记真实获取范围 |
| 清理与历史接力可恢复 | S1；S2B 扩展 | 清理缓存和重建目录/去重索引后，已保存决定历史、书签、实际读取清单及引用证据仍可查，重建结果与引用版本一致；S2B 保留被执行/批准/核验记录引用的预检与修改审核材料。删除书签不触发引用对象连带删除，作者目录不新增或删除文件 |

本节验证工具的组织、记录、预检与复用行为，不声称自动找齐全部证据、理解全文或证明研究结论。S1 不以实现 S2A/S2B 的规则、表达例外、预检或改稿结果为前置条件；跨项目偏好学习、完整依赖图与试改预览均不在这些新增验收内。

## 15. 实施顺序

本节只规定开发顺序，不重新定义长期产品边界，也不把规划中的矩阵单元直接视为可交付功能。本次更新保持 0.1 可靠读取及最小证据状态、0.2 模板与受控文字修改的范围；共享工作区支持用户安排的接力，不实现 Agent 编排。阶段 4 的候选能力按独立合同逐项排期，不在本轮整体承诺。

v1.2 在 v1.1 已明确的“用户安排 Agent，产品提供文件工具与共享记录”边界上补五项体验能力，不增加产品模块或 Agent 调度。S1 只做现有读取结果的目录、用户显式要求、读取书签与正确缓存复用；S2A 扩展规则与适用决定，S2B 再做修改预检、局部表达决定、变更/审核资料和书签及已验证的检查复用。自动学习、跨项目 PROFILE、完整语义依赖图、段落级智能增量和试改预览均不是新增首版完成线。

文件保护、批准身份、审核政策、幂等恢复与零污染不放宽。冻结的是需求边界和技术合同，不是实现或验收状态。下一步仍进入阶段 0；S1 的估算口径仍是“DOCX 可靠读取引擎 + 最小项目状态与证据基础设施”，五项能力按下述最小范围复用已有记录，不按五个子系统估算。

### 阶段 0：读取样本与能力边界

- 将第 2.6 节矩阵细化为能力记录，锁定第一批对象、操作、环境、合同版本和标注样本；全部先标规划中，不以方案完成代替实现完成。
- 明确应用数据根目录、任务隔离、源目录只读和显式导出边界；先设计版本及清理策略，不向作者目录落配置与日志。
- 明确证据、基线和依赖的版本语义，分开复核结论、有效性、批准状态、执行绑定及执行阶段；区分读取基线更新和修改产物发布，为后续检查/发布/最终结果记录及幂等对账预留一致的持久合同，不提前实现 S2B 的候选、审核模式与写回功能，也不建设 Agent 编排。
- 锁定 S1 最小数据 schema、来源与读取基线请求语义、覆盖与核验记录；区分 proposal_hash、ordered_proposal_hashes、plan_hash、request_digest 的后续字段边界和固定摘要测试向量，不要求阶段 0 实现 S2B 状态机或全套数据库。
- 固定 IJAM 英文工作稿快照、源哈希和对应渲染环境。
- 建立第 18 节的复杂对象样本矩阵，由人工独立标注预期内容及页面。
- 为每类对象确定必需解析、只登记与展示外观、暂不支持的边界。
- 选定一种可用渲染器和一条受控模型接入路径，确定字体、字段和修订显示条件。
- 用真实失败案例定义验收：漏掉文本框、公式或浮动图、双栏读序混乱、样式继承误判、截断后自称全文等。
- 固定夹具的输入和期望记录格式，预置受影响/保留 ID、依赖完整性、fallback_scope 及唯一 expected_verdict；补第 13.7 节 S1 的资料条目/缺口、书签真实读取范围、显式作者决定与缓存命中/失效期望。只定义相应阶段验收，不为筹备 S1 提前完成 S2B 的预检、局部例外或审核。
- IJAM 与 Engineering Letters 规则采集可以并行，但不得成为开始读取工作的前置条件。

阶段 0 的完成线是样本及独立标注、能力与环境边界、最小 schema/摘要约定、夹具判定方式和第一条 DOCX 只读闭环的验证计划均已明确。首条闭环限定为一个登记样本经部件/结构读取、指定环境渲染、覆盖报告及源目录不变核验；实际实现与运行结果在阶段 1 验收，本方案冻结不冒充闭环已跑通。

### 阶段 1：MVP-Docx-Fidelity-0.1

- 包清单、区域与对象索引、格式来源、布局设置。
- 原稿只读检查和 render-copy 隔离。
- Word/WPS 指定环境的 PDF 与页面图像。
- 结构—页面关联、歧义和未覆盖状态。
- 模型按需读取接口、分页和证据获取记录；按目标区域、邻文与已知显式关系组织轻量资料目录，展示已定位/未读/缺失及纳入原因，不保证找到全部语义相关材料。
- 保存用户明确填写的 DOCUMENT/PROJECT 术语、目标与边界，记录类型与适用性；读取型书签引用任务、实际获取范围和证据入口。不开自动偏好学习、局部表达例外或修改预检。
- 三栏只读复核界面与覆盖报告。
- 应用内部不可变源快照、初始基线、任务及版本化 EvidenceItem；保留人工/确定性读取核验，已确认观察、推断和未核验内容分开，证据定位绑定源与渲染版本。
- 可信桌面读取基线更新：外部稿件更新或目标/边界/已有规则引用调整，保留具体用户决定，并发检查与重复请求处理，不修改稿件、不调用改稿 Proposal / Approval，不提前执行期刊规则检查。
- 桌面与 MCP 共用核心读取和状态服务，记录实际读取覆盖，提供能力发现及明确错误结果；显式依赖失效限于本阶段源/派生版本关系、覆盖、EvidenceItem 及核验记录的适用性，可重建缓存与持久证据分开。

## 16. 最终判断

产品是供用户与不同 Agent 共用的科研文件工具箱和共享工作区，不是开放式论文生成器、只读检查器或 Agent 调度平台。用户安排谁修改、谁审核及何时接力；Agent 分析并提出请求；MCP 统一接入；共享工作区保存依据和记录；文件引擎可靠执行；核心保护版本、权限、批准和验证。能力矩阵、操作合同与阶段路线分别定义范围、允许变化和交付顺序，不互相代替。内部状态由应用管理，不把作者目录当临时工作区。

~~~
MVP-Docx-Fidelity-0.1
源快照 → 结构与格式 → 指定环境页面 → 关联与覆盖 → 模型统一读取
初始/可信更新的读取基线 → 版本化证据与实际读取记录 → 本阶段依赖失效 → 持久数据/缓存分离
轻量资料目录 + 用户显式要求 + 读取型书签；缓存只在相关输入与覆盖仍适用时复用

MVP-Word-0.2
模板导入/更新 → 渲染与规则发布 → 每刊摘要与项目绑定
版本化读取证据 → 用户安排 Agent 提交冻结候选 → 确定性检查、风险与审核材料
→ 修改预检与整批影响检查 → 用户按项目政策决定审核与处置 → 批准具体计划 → 执行前复验
→ 原子执行绑定 → 内部副本补丁 → 实际重读、差异与同环境验证 → ValidationResult
→ 满足文件保护及适用审核政策后条件式发布 → 保存发布与最终结果 → 用户选择交付
资料包、适用作者决定与修改/审核书签引用真实记录；预检不是批准，书签不自动执行
用户可另行安排对实际产物的审核，产品保存记录，不自行组织下一 Agent

后续
外部参考文献与图件管理；LaTeX、SVG、draw.io、Origin 等独立适配能力
格式、对象、结构编辑、新文件生成等操作分别授权与验证
完整主张依赖和更广的全篇一致性检查另行验证；自动 Agent 团队不在产品路线

贯穿全部阶段
原稿目录只读 → 应用内部任务和版本 → 明确选择才向指定目标导出
来源/版本/核验状态可追溯；批准有效性与绑定分开；未知结果先对账，恢复不重复执行
~~~

首版成立的判断是：用户与模型能够核实原稿内容与版面、找到对应证据，并知道还有哪里没读到或不能确认。它是第一个验收点，不是完整产品的能力上限；期刊检查和语言处理不能掩盖读取层的问题。

共享工作区让新 Agent 不读全部聊天也能取得正确版本、实际改动和原始依据；未确认判断不升级为事实，旧记录不覆盖新稿，恢复不重复修改。用户决定接力与审核，只需查看具体批次及必要问题，不必逐次确认读取和技术检查。审核可选不等于验证可跳过，用户批准不等于语义 PASS；产品不为了实现这些保护再建设 Agent 管理平台。

后续再让稿件：

- 符合目标期刊规则。
- 表达承担正确的论证职责。
- 术语和数字前后一致。
- 结论不超过证据边界。
- Word、LaTeX、PDF 和图表之间可追溯。
- 每一次修改都能解释、核对和回滚。
- 每一项结论说明使用了什么证据、核验到什么范围、是否仍有效；候选与复核分离，用户批准不替代事实检查。
- 作者目录只出现本人选择的交付物，不堆放备份、缓存和调试产物。

## 19. 工作区零污染与受控交付（全阶段硬约束）

### 19.1 三类空间严格分开

“作者目录”指作者提供的稿件、数据、图件及依赖所在工作区，不是应用自己的任务目录。零污染指本产品及其受控子任务不在作者目录产生未经授权的写入，不承诺阻止作者或其他独立程序的操作。

| 空间 | 用途 | 默认写权限 |
|---|---|---|
| 作者原始工作区 | 原稿、图件工程、实验数据、作者既有配置及依赖 | 只读；不覆盖、不改名、不移动、不删除、不创建旁挂文件 |
| 应用专属数据空间 | 源快照、内部版本、项目记录、规则库、缓存、渲染及任务日志 | 应用按项目和任务管理；不位于作者工作区内部 |
| 明确授权的交付目标 | 作者选定的成品、报告或项目包 | 仅指定文件及本次明确批准的动作，不授予整个父目录任意写权限 |

默认不在作者目录建立 outputs/、rulepacks/、.cache、.backup、.app、临时解压目录、project.yaml、AGENTS.md 或其他隐藏配置。内部项目绑定、索引和 UI 状态也存应用数据空间；隐藏不等于不污染。

应用不擅自清理作者已有的备份、缓存和日志，也不为了减少文件数覆盖原稿。已有杂乱文件不在自动整理范围，本次方案更新同样不授权清理这些文件。

### 19.2 内部存储与版本关系

下列为应用专属数据根目录下的逻辑结构，不是要求在作者目录创建这些文件夹；具体平台路径在实现时确定，并经验证不得落在作者工作区内：

~~~text
app-data/
├─ projects/       # 项目/证据/任务记录、规则绑定、基线指针及交付索引
├─ objects/        # 不可变源快照及去重复用的内容
├─ versions/       # 不可变版本、基线清单及候选/已核验/已发布关系
├─ rulepacks/      # 模板、官方来源、规则、页面和每刊摘要
├─ tasks/          # 独立工作副本、render-copy、编译及导出暂存
├─ cache/          # 可重建索引和预览
└─ audit/          # 复核、批准、幂等执行、发布与交付记录
~~~

备份以应用内版本管理呈现，不生成“修改版2”“最终版_备份”散文件。相同不可变内容可以复用，版本关系记录差异、来源、审批和状态；不强求每一步复制整份文档，也不能为省空间失去可恢复原件。

以上仍是逻辑划分，实际可采用一个支持事务的元数据存储与不可变内容存储，不按概念对象数量创建文件夹，也不要求每次交接复制整稿。ArtifactVersion（源及派生产物版本）、EvidenceItem、Baseline、Task、Proposal、Review、Approval、ChangeResult，以及 ValidationResult、PublicationRecord、读取基线更新的用户决定和管理记录，S2B 的审核政策版本及绑定、提交来源、审核材料/实际读取记录和未审核或争议项的用户处置，均按引用与保留策略作为持久项目数据管理；CacheEntry 不进入这份持久成果清单。

逻辑操作登记、request_digest 及其对应的规范化业务请求、plan_hash 与有序候选引用、execution_attempt、批准/执行幂等绑定、last_known_phase、逐项 side_effect_status、对账过程及结果，是持久执行记录，不是可清理的普通任务日志。S1 的读取基线管理请求与提交对账记录同样持久保留；S2B 才增加改稿逻辑执行记录。普通调试日志可轮转，但不能连带删除用于判断“是否已执行、绑定给谁、应返回哪个结果”的唯一依据。已保存作者决定及历史、接力书签、实际读取记录中的资料版本清单、被批准/核验记录引用的预检记录同样是持久项目材料；临时目录视图与索引可重建，不按每个资料包复制原稿。归档或删除这些持久记录须遵守明确的项目保留与引用策略，不能由缓存配额触发。

被保留版本、核验或恢复记录引用的源/派生产物必须可恢复，普通缓存清理不得删除；不要求所有无人引用的临时派生文件永久保留。当前基线指针只有一个权威来源，读取更新与修改发布共用该指针并分别留下来源；Agent 缓存不能另存可独立发布的真源。

可写工作副本必须独立于不可变快照和作者原件，不能通过共享可变对象或硬链接把修改传回原稿。恢复默认在应用内部建立可查看、可核验的版本，不静默恢复覆盖作者文件。

### 19.3 模型与外部程序的执行边界

模型提交对象 ID、操作意图及参数，由服务解析到授权资源；不得把用户输入的任意路径直接当作可写目标。提示词中“不写项目目录”不能替代实际访问限制。

每个任务在应用内部独立目录执行。Word/WPS 打开的文档、LaTeX 编译源树、图件工程和脚本输入均使用受控副本及已登记依赖；设置受控工作目录、输出位置和适用的临时目录，禁止任务回到原稿位置旁写文件。批准的图件脚本也不能因此获得任意文件写权限。

执行前解析真实路径、依赖和链接关系，拒绝通过路径穿越、符号链接、目录联接或不受控外部输出参数写出范围。执行时限制权限，执行后核验实际结果；仅靠执行后扫描发现污染不算已经实现预防。

对无法约束写入行为的宿主或适配器，强约束模式下拒绝执行并说明原因，不先产生污染再静默删除。不能通过关闭用户现有应用来伪装隔离，不能调用用户正在编辑的原稿作为渲染输入。系统自身的正常缓存与访问时间等不属于作者目录成品，但已知副作用与隔离限制应明确记录。

### 19.4 导出是单独的授权与提交动作

1. 先在应用内部生成并验证交付版本，明确是已核验成品还是用户主动选择的诊断材料。
2. 作者选择要导出的文件、版本、格式和目标位置；应用显示最终清单，不默认附带备份、缓存、页面截图和日志。
3. 检查真实目标路径、可用空间、权限、同名文件和原稿保护范围。交付目标不得覆盖登记为受保护原件的路径。
4. 同名时由作者选择覆盖该交付文件、另选名称或取消。默认不覆盖、不自行编号，也不为了凑“成功”悄悄改到别处。
5. 执行前再次核对目标存在状态及必要指纹，外部变化后重新确认；授权仅对指定产物及目标有效。
6. 采用适用存储环境能够支持的安全提交方式，提交后验证目标内容并记录版本、路径、哈希和结果。只有此时标记 exported。

单文件交付必须先准备和验证，再安全提交，不能边生成边写最终目标。覆盖只有在能够保证既有目标不被失败写入破坏的条件下启用；不满足安全提交条件时拒绝该导出并请作者选择其他目标，不声称跨卷或所有文件系统都能原子提交。暂存文件位于应用管理的合适位置，不在作者目录增加 .tmp、.bak 副本。新增交付也必须防止与外部文件并发冲突，不得因目标原先不存在而忽略执行时的状态变化。

多文件导出不承诺天然整体原子性。先完成内部准备和检查，逐项记录真实提交情况；中断后明确已提交、未提交和冲突项，不报整包成功。需要回退时仅按已登记且内容仍匹配的本次产物执行；有外部改动时停止，不删除作者文件来“恢复干净”。需要单个交付文件时提供用户主动选择的项目包导出。

### 19.5 缓存、恢复数据与保留策略

| 数据类别 | 默认治理原则 | 删除约束 |
|---|---|---|
| 可重建缓存 | 容量配额、按使用情况与时间清理 | 必需来源及重建条件仍在才清；不得删除恢复版本或唯一核验证据 |
| 成功任务临时文件 | 产物验证并纳入版本记录后清理 | 不提前删除尚未提交或仍在使用的任务输入 |
| 失败任务与诊断 | 保留必要记录和有限期诊断材料，展示期限 | 不包含无必要的整稿重复件；到期不删除恢复所需唯一内容 |
| 未导出的已批准修改、已核验版本 | 作为恢复数据保留，不当缓存 | 自动清理不得丢弃；删除须明确说明损失并确认 |
| 源及派生 ArtifactVersion、版本化证据、基线与作者决定 | 随项目、核验与版本关系保留，不属于可随时清理的缓存 | 被保留记录引用时不得删除；失效证据/决定保留历史关联，不覆盖旧版本或伪装仍有效 |
| 已保存接力书签、实际用过的材料清单及所引用的预检记录 | 作为项目交接或核验依据保留；临时组合视图/去重索引可重建 | 缓存清理不删已保存书签；删除书签不连带删除源件、证据、Review 或修改记录，亦不授权清理作者目录 |
| 任务、候选、复核、批准、逻辑操作/request_digest、执行尝试、幂等绑定、对账、检查/发布/最终结果和读取基线更新记录 | 作为可追溯工作与恢复账目按项目策略保留，不归类为普通任务日志 | 缓存清理和调试日志轮转均不得删除；清除持久记录须说明影响并遵守引用关系与用户确认；未终结操作不预造最终结果 |

具体容量与期限在实现时配置并显示，不编造已经生效的默认数值。空间不足时先停止新任务并提示可安全清理范围，不牺牲唯一恢复版本、不转存到作者目录。

缓存按结果类型登记实际依赖，不给每条缓存强绑所有字段。相关源/派生工件哈希与版本、工具/方法版本、规则或作者决定、渲染/字体环境、参数、EvidenceItem 依赖按需纳入键或适用性校验；每条结果另记覆盖范围、限制、生成时间及失效原因。生成时间用于展示和清理，不以“刚生成”代替有效性检查；命中不授予访问权限。

| 结果类型 | 必须纳入或核对的相关输入 | 不应无条件绑定的输入 |
|---|---|---|
| 源结构解析 | 源工件版本/哈希、解析器及方法版本、影响结果的解析配置 | 仅用于下游表达检查的规则、未参与解析的字体/渲染条件 |
| 页面/PDF 派生与映射 | 源工件、Word/WPS 等渲染器及版本、所用字体与显示/域配置；映射另绑实际 PDF 哈希、映射方法和结构输入 | 与页面生成无关的风格建议规则 |
| 规则检查 | 被检查的读取/证据版本、规则包与检查器版本、适用作者决定、语言/范围等配置 | 未被检查方法使用的无关工具配置 |
| 资料目录与去重视图 | 基线及已用关系/对象/问题版本、选择或指纹方法、请求范围、可见材料权限 | 无关区域或未参与本视图的结果 |
| Review、Approval 与核验证据 | 按持久记录合同保存，适用性另判；状态展示可以有可重建派生缓存 | 不作为普通缓存条目删除或覆盖 |

复用前检查实际依赖仍匹配/适用、相关证据 CURRENT、覆盖满足本次请求；缺依赖、缺版本或不知环境是否一致时，标明无法复用并重查，不用默认值凑命中。源文件未变但提取方法或工具缺陷已修正时相关结果仍失效；PDF 哈希变化后旧映射和页面定位不可继续当作当前证据。缓存可避免重复计算，不证明论文内容正确，也不代表 Agent 已获取这些内容；实际从缓存返回材料时同样记录该次真实获取范围，不因命中而省略读取记录。

S1 先做到正确的命中/失效判断和清理，不要求段落级智能增量或完整依赖图。S2A 加入规则/决定依赖，S2B 在已知且验证过的依赖范围内复用未受影响检查；影响不明时按第 4.8 节扩大重查并说明原因，不承诺“改一句只查一句”。仅下游规则变化时不无故废弃无关源解析与页面缓存；是否可保留由预置依赖与回归样本验证，不靠猜测。

清掉 CacheEntry 不清掉持久 EvidenceItem、作者决定、书签和核验历史；作为某次核验唯一依据的页面、输出、实际材料版本清单或中间证据须按持久引用保留，不能以“理论上可以重建”为由删掉实际用过的证据。

界面展示总占用、按项目及类别占用、可释放容量、保留期限和删除后果。用户可以固定重要版本、主动清理缓存或归档项目；删除内部项目必须说明是否含未导出成果，不能顺带删除原始工作区或已有交付物。

### 19.6 崩溃恢复、迁移与异常处置

任务、operation_id、request_digest、plan_hash、有序候选清单、批准状态及 bound_operation_id、execution_attempt、实际产物、ValidationResult 和发布记录建立持久可核对关系。崩溃后使用第 4.4 节执行状态，未知结果记 UNKNOWN，进入 RECONCILING 时保存 last_known_phase 与对账记录；导出状态另行记录。按第 4.9—4.10 节核对真实文件、指纹和持久提交账目，不以可被轮转的调试日志作为唯一依据，未查明前不重放写入、不提前填写最终失败或取消结果。

查出发布成功时返回原 ChangeResult，即使基线已推进或批准已撤销也不重复应用。确认是非终态的可恢复尝试后，才在原执行绑定且批准仍有效的条件下恢复；已有最终失败/拒绝/取消结果不再重开，重新启动需新操作和新批准。绑定不因崩溃、失败或失效而清空。成功分支的基线指针、PublicationRecord、终态与最终结果一致提交；确定拒绝分支同样持久保存拒绝记录，而不是回滚后丢失证据。未引用的内部暂存产物按保留策略清理。

0.1 的读取基线更新单独按第 4.11 节的请求标识、管理决定与提交记录对账，重复请求返回原管理结果；它不需要 0.2 的改稿 ChangeResult，但同样不能在结果不明时反复切换当前基线。

项目迁移通过作者主动导出的自包含项目包完成，明确是否包含源/派生 ArtifactVersion、依赖、规则版本、证据、基线清单、作者决定、接力书签及其实际材料引用、候选/复核/检查/发布/最终结果和必要审计；为可恢复的保留版本包含必要来源，不包含可重建缓存和可重用凭据。重新导入后核验完整性和引用关系，环境差异导致的渲染变化单独报告，不声称页面必然一致。历史 Approval 及绑定作为审计材料保留，不自动授权新环境的新执行；结果未知的旧操作先查明，不能借迁移绕过对账。确需在新环境启动的工作重新检查计划、建立新逻辑执行并取得新批准，不改绑旧 Approval；已完成记录保留原逻辑执行身份以防误重放。
